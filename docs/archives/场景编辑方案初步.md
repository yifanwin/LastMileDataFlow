# Case → 场景编辑 Pipeline：初版完整设计


## 1. 初版的目标与范围

### 目标

输入：

> 抽象 case 描述 + 一个具体场景 + 机器人/任务上下文。

输出：

> 多个经过物理检查和视觉复查的编辑场景，以及对应的模板、编辑方案和具体参数。

整个过程不再需要人工指定场景中的目标实例、支撑实例或具体编辑坐标。

### 初版做什么

- 每次将自然语言描述规范化为 Case Template。
- 从实际场景建立 Scene Graph。
- 生成多种编辑策略。
- 对连续参数进行几何约束采样。
- 执行移动、旋转、添加、删除。
- 检查编辑前后支撑关系与编辑后物理位置。
- 拍摄前后三角度 RGB 图。
- 通过 Agent3 检查编辑效果。
- 在数量或预算达到上限时结束。

### 初版不做什么

- 历史 case 检索。
- 最小编辑优化。
- 对象级 `editable/protected` 权限管理。
- 资产人工资格审批。
- 每个样本的完整文件审计、逐字节恢复审计。
- 自动证明机器人真实不可达或任务成功。

最后一项可以交给后续机器人试验阶段，**不阻塞初版场景生成**。

---

## 2. 总体流程

```text
原始 case 描述 + 任务上下文
                │
                ▼
      Agent1：每次规范化
                │
                ▼
          Case Template
                │
                │       具体场景
                │          │
                │          ▼
                │   加载、初始化、静置
                │          │
                │          ▼
                └───── Scene Graph₀
                           │
                           ▼
              Agent2：多个编辑提议
                           │
                           ▼
                  Symbolic DSL
                           │
                           ▼
          程序：角色解析、联合采样、编译
                           │
                           ▼
                 Executable DSL
                           │
                           ▼
             从原始基线创建编辑试次
                           │
                           ▼
                执行整组编辑、静置
                           │
                           ▼
            实际 Scene Graph₁ + 规则检查
                           │
                 ┌─────────┴─────────┐
                 │                   │
               不通过               通过
                 │                   │
           回滚、记录原因      前后三角度 RGB
                 │                   │
                 │                   ▼
                 │              Agent3 复查
                 │                   │
                 │         ┌─────────┼─────────┐
                 │        通过      不通过     不确定
                 │         │         │          │
                 │      保存场景    回滚      有限补图
                 │         │         │          │
                 └─────────┴─────────┴──────────┘
                           │
               数量达到目标或预算耗尽
```

**默认每个样本都从同一个静置后的基线场景生成。**

不默认在上一个成功样本上继续修改，避免相对旋转累积，也方便比较不同编辑方案。这不是最小编辑限制：每个试次内部仍然可以大幅修改场景。

## 3. 输入与运行配置

### 业务输入

| 输入 | 内容 |
|---|---|
| `case_description` | 抽象现象描述，不含具体实例 ID 或坐标 |
| `scene_source` | 场景文件及元数据 |
| `task_context` | 机器人、任务、初始站位等 |
| `difficulty_profile` | 可选的统一难度参数配置 |
| `generation_config` | 数量、采样、预算、种子 |

初版可以采用以下运行配置，数值只是起始示例：

```json
{
  "target_scene_count": 10,
  "proposals_per_round": 4,
  "samples_per_proposal": 16,
  "max_rounds": 5,
  "max_samples": 200,
  "max_agent_calls": 40,
  "timeout_s": 600,
  "seed": 42
}
```

其中：

- `target_scene_count` 统计**去重后验收通过的编辑场景**。
- `max_samples` 统计候选参数试次，包括没有找到合法位置的试次。
- Agent 调用、补图和重试共享累计预算。
- 操作数量可以影响执行成本，但**不影响候选偏好**。

## 4. Scene Graph：描述实际场景

### 4.1 节点

初版包含三种节点：

| 节点 | 主要字段 |
|---|---|
| 物体实例 | 稳定实例 ID、类别、资产 ID、世界位姿、碰撞几何、部件信息 |
| 放置区域 | 区域 ID、所属支撑物、局部坐标系、边界、表面高度 |
| 初始站位 | 站位 ID、机器人初始位置与朝向 |

`robot_start` 是任务上下文中的站位节点，不是一个待移动的家具对象。

### 4.2 关系

优先维护：

```text
part_of(part, object)
supported_by(object, support)
has_region(support, region)
inside(object, container)
```

距离、夹角、间隙等数值关系按需计算，不必提前建立所有物体两两之间的边。

需要特别区分：

- `part_of` 可以来自模型结构或元数据。
- `supported_by` 应来自几何、接触和静置后的实际状态。
- “准备放到桌上”不能直接写成已经被桌子支撑。

### 4.3 更新方式

初版先采用简单可靠的方式：

1. 加载并静置后构建 `Graph₀`。
2. 执行编辑并静置后重新构建 `Graph₁`。
3. 回滚后重新读取当前实际状态。

Agent2 可以使用预测关系辅助规划，但 **Agent3 和规则验收使用实际 `Graph₁`**。

实例引用使用稳定名称。添加、删除或重编译后，重新解析底层 `body_id/geom_id`。

## 5. Agent1：每次把描述规范化成模板

### 输入

```text
原始 case 描述
+ 任务上下文
+ 可用谓词说明
+ 可选难度参数配置
```

### 输出

Case Template 中只包含：

- 想构建什么现象。
- 需要哪些角色。
- 编辑后的数值/关系要求。
- 编辑前后必须保持的关系。
- 视觉可检查的语义条件。
- 尚待机器人试验确认的假设。

**不包含具体场景实例、编辑操作或精确坐标。**

### 模板示例

下面的距离范围沿用之前的讨论示例，不表示已经校准过的真实困难阈值。

```json
{
  "template_version": "0.1",
  "case_type": "distance_difficulty",
  "intent": "目标在初始站位操作困难，但换到其他站位可能完成任务。",

  "roles": {
    "target": {
      "type": "manipulable_object",
      "required": true
    },
    "support": {
      "type": "support_surface",
      "required": true
    },
    "robot_start": {
      "type": "robot_station",
      "required": true
    }
  },

  "parameters": {
    "distance_band": {
      "range": [1.0, 1.5],
      "source": "difficulty_profile"
    }
  },

  "requirements": [
    {
      "id": "target_distance",
      "predicate": "distance_xy",
      "args": ["$robot_start", "$target"],
      "range": {
        "parameter": "distance_band"
      }
    }
  ],

  "invariants": [
    {
      "id": "target_supported",
      "predicate": "supported_by",
      "args": ["$target", "$support"],
      "value": true
    }
  ],

  "semantic_checks": [
    "目标仍处于合理的支撑场景中"
  ],

  "pending_hypotheses": [
    "current_station_difficulty",
    "alternative_station_success"
  ]
}
```

### 参数来源

抽象描述没有具体数值时：

- 优先使用输入的统一难度配置。
- 可以使用明确标为启发式的默认配置。
- 不把模型临时猜出的范围当成真实可达性依据。

这样仍能自动生成场景，只是输出的 `case_condition` 保持 `unknown`。

模板作为本次运行产物保存，**不建设检索库，也不进入复用判断**。

## 6. Agent2：绑定角色并生成多个 Symbolic DSL 提议

### 输入

```text
Case Template
+ Scene Graph₀
+ 可用资产摘要
+ 编辑操作与谓词说明
+ 已失败样本的简要反馈
+ 已接受布局的简要摘要
```

### 输出

每个提议包含：

- 角色到实际实例的绑定。
- 一组编辑操作。
- 搜索空间。
- 可选的额外目标或 invariant。
- 参数采样方式。

**允许编辑目标、支撑物、家具和邻近物体，不限于模板中出现的角色。** 需要操作额外对象时，在提议中增加绑定即可。

### 提议示例

```json
{
  "dsl_version": "0.1",
  "proposal_id": "proposal_001",

  "bindings": {
    "target": "cup_demo",
    "support": "table_demo",
    "robot_start": "station_start"
  },

  "description": "在桌面上重新布置目标，并采样其相对朝向。",

  "operations": [
    {
      "op": "move",
      "subject": "$target",

      "search_space": {
        "support": "$support",
        "region": "table_demo:top",

        "xy": {
          "mode": "candidate"
        },

        "rotation": {
          "frame": "world",
          "axis": [0, 0, 1],
          "angle": {
            "range": [-3.1415926536, 3.1415926536]
          }
        }
      }
    }
  ],

  "goals": [],
  "invariants": [],

  "sampling": {
    "selection": "coverage",
    "max_samples": 16
  }
}
```

这里的 `goals/invariants` 是**附加条件**。程序最终检查：

```text
模板 requirements + 提议 goals
模板 invariants   + 提议 invariants
```

不能通过输出空数组取消模板要求。

### 多个提议要体现策略差异

例如距离 case 可以提出：

- 在当前桌面上重新布置目标。
- 移动桌子并同时重新布置桌面物体。
- 调整周围家具，为新的目标布局腾出空间。
- 更换目标实例或支撑组合。

最后一种是否成立，取决于模板语义：如果明确要求同一支撑物，不能静默换成另一个。

**不设置“优先移动目标”“优先少改物体”“优先小角度”等默认偏好。**

## 7. DSL 操作和位姿语义

### 7.1 单位与坐标约定

统一为：

```text
长度：m
角度：rad
时间：s
质量：kg
线速度：m/s
角速度：rad/s

世界坐标系：右手系，z 向上
四元数顺序：[w, x, y, z]
```

所有方向性描述都必须有参考坐标系。不能把相机画面的“左边”直接解释成世界坐标的“左边”。

### 7.2 基础操作

| 操作 | 语义 |
|---|---|
| `move` | 在指定区域或空间中搜索新位置，默认保持朝向，也可附带相对旋转 |
| `rotate` | 绕指定坐标系中的轴进行相对旋转，默认保持物体原点位置 |
| `add` | 从资产集合选取对象，采样位置与初始朝向并加入场景 |
| `remove` | 删除指定实例及其固有模型部件 |

`set_pose` 可以保留为底层执行函数，不必暴露为 Agent2 的主要操作。

### 7.3 相对旋转的精确定义

角度相对于**该操作开始时的物体朝向**，不是相对于世界零朝向。

以旋转矩阵表示：

```text
world 轴：
R_after = R_delta × R_before

object 局部轴：
R_after = R_before × R_delta
```

默认旋转中心是物体模型原点。多个旋转按操作列表顺序组合。

MuJoCo 提供轴角转换和四元数乘法，可在适配层实现这些组合。[MuJoCo 四元数 API](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#quaternions)

编译后的最终位姿可以使用世界坐标下的绝对四元数，**这只是执行表示，不改变输入指令的相对旋转语义**。

### 7.4 家具与支撑物编辑

移动支撑物时，可以：

- 显式同时编辑其支撑对象。
- 使用 `carry_supported: true`，由程序根据实际支撑图展开联动对象。
- 重新安排这些对象到其他合法位置。

不通过权限检查禁止移动桌子，也不默认禁止邻居变化。

但是如果最终导致悬空、严重碰撞或模板 invariant 不成立，仍然不能接受该样本。

## 8. 程序：联合采样与编译

程序不是把每个区间独立变成随机数字，而是生成**同时满足约束的布局候选**。

### 编译步骤

1. 解析角色引用和具体实例。
2. 选择需要添加的资产。
3. 生成相对旋转、位置等参数候选。
4. 根据对象足迹和支撑区域计算合法落点。
5. 计算放置高度。
6. 处理操作顺序和支撑物联动。
7. 输出具体操作列表。

对于多个连续操作，后面的计算要使用前面操作产生的**临时布局**。例如桌子先移动，杯子的放置位置必须基于移动后的桌面计算。

### 采样方式

初版支持：

- `uniform`：随机覆盖。
- `grid`：离散网格。
- `candidate`：根据几何构造候选。

通常先生成：

```text
区域内的合法落点
∩ 目标足迹与边缘约束
∩ 几何避让约束
∩ 距离、方向等 case 要求
```

再随机选择或进行覆盖性选择。

**不存在移动距离、旋转角度或操作数量惩罚。** 也不把当前位姿自动排在第一位。

### Executable DSL

编译结果示意：

```json
{
  "dsl_version": "0.1",
  "proposal_id": "proposal_001",
  "sample_id": "sample_017",

  "sampled_parameters": {
    "rotation_angle_rad": 0.5235987756
  },

  "operations": [
    {
      "op": "move",
      "instance": "cup_demo",

      "pose": {
        "frame": "world",
        "position": [1.24, -0.73, 0.91],
        "quaternion_wxyz": [
          0.9659258263, 0, 0, 0.2588190451
        ]
      },

      "region_id": "table_demo:top"
    }
  ]
}
```

上述坐标仅用于展示格式。执行器只读取结构化字段，不依据 `description` 执行。

### 保留哪些检查

不做对象权限检查，但仍需要：

- JSON 和字段类型有效。
- 引用的对象、区域存在。
- 位姿是有限数值，四元数有效。
- 资产能加载和编译。
- 操作函数已经实现。

这些是**执行正确性检查**，不是对象审批或权限审计。

## 9. 执行、Invariant 与物理校验

### 9.1 一次试次执行整个方案

```text
检查编辑前 invariant
→ 保存构建检查点
→ 按顺序执行整组操作
→ 更新模型与状态
→ 真实静置
→ 重建实际 Scene Graph
→ 检查编辑后 invariant 和 goals
→ 视觉复查
→ 保存或回滚
```

**不要求每个操作结束后都完成一次静置和验收。**

例如“先移动桌子，再移动杯子”可以作为同一组操作执行，只检查整组方案的前后端点。

这里的 `move` 是布局编辑，不是模拟机器人搬运物体。因此初版不检查中间搬运路径，也不要求编辑过程中持续被支撑。

### 9.2 Invariant 的统一语义

```text
before：编辑前已经静置的实际场景
after：整组编辑执行并静置后的实际场景
```

对于：

```text
supported_by($target, $support)
```

两端都必须被指定支撑物支撑。**支撑物本身可以移动**，只要关系仍然成立。

如果只要求“前后都有某种支撑”，可以使用：

```text
supported($target)
```

再用编辑后 goal 指定新的支撑物。

另外：

- 新增对象没有 before 状态，其支撑要求放入编辑后 goals。
- 删除对象不能同时被要求在 after 中存在或满足支撑 invariant。
- 这种冲突属于方案与目标不一致，不属于越权。

### 9.3 低成本物理检查

初版检查：

- 严重穿透和碰撞。
- 目标与新增物体是否正确落在支撑区域。
- 静置后是否仍明显运动、倾倒或飞离。
- 状态是否出现非有限值。
- 编辑实际影响到的邻近对象是否出现明显物理问题。

**不检查“所有未显式编辑物体都必须保持原位”。** 邻居发生合理变化可以接受。

正常支撑接触不算错误。包围盒重叠只用于筛查，不能直接作为严重穿模结论。

物理阈值由统一配置管理，初版可沿用当前静置检查的阈值。Agent 不负责更改这些阈值来让失败样本通过。

## 10. 三角度 RGB 与 Agent3

### 10.1 相机设置

默认三种视角：

1. 俯视。
2. 一个斜视角。
3. 另一个斜视角。

根据**编辑前后受影响区域的并集**决定取景，而不是每次都重新追踪目标中心。

前后图使用相同的：

- 相机位姿。
- 视场或内参。
- 分辨率。
- 光照设置。

距离 case 的取景应尽量同时覆盖目标、支撑物和初始站位。无法覆盖时，可补一组上下文视图。

如果静置后的物体超出原取景范围，扩大范围后重拍两端。不能只放大 after 图。

### 10.2 Agent3 输入

```text
原始 case 描述
+ Case Template
+ Symbolic DSL
+ 实际 Executable DSL
+ Scene Graph₀ / Graph₁
+ 规则检查结果
+ 前后三角度 RGB
```

原始描述必须保留，避免只检查“是否执行了一个本来就理解错的提议”。

### 10.3 Agent3 输出

```json
{
  "sample_id": "sample_017",
  "verdict": "pass",

  "checks": [
    {
      "item": "edit_matches_proposal",
      "status": "pass",
      "views": ["top", "oblique_1"],
      "reason": "目标位置变化与提议一致。"
    },
    {
      "item": "reasonable_support_context",
      "status": "pass",
      "views": ["oblique_1", "oblique_2"],
      "reason": "目标仍位于合理支撑面上。"
    }
  ],

  "unverified_claims": [
    "current_station_difficulty",
    "alternative_station_success"
  ]
}
```

`verdict` 为：

```text
pass / fail / uncertain
```

含义是编辑效果的视觉复查结果，不是机器人任务结果。

- `pass`：允许保存。
- `fail`：回滚，反馈给 Agent2。
- `uncertain`：有限补图；仍不确定则不计入通过数量。
- 程序物理检查失败时，不需要再调用 Agent3 来投票。

## 11. 循环、反馈与结果

### 11.1 主循环示意

以下是编排伪代码，不是现有可运行接口：

```python
template = agent1.normalize(description, task_context, profile)
baseline = prepare_and_settle(scene)
graph_before = build_scene_graph(baseline)

accepted = []
feedback = []

for round_index in range(max_rounds):
    if budget.exhausted():
        break

    proposals = agent2.propose(
        template,
        graph_before,
        feedback,
        summarize_layouts(accepted),
    )

    for proposal in proposals:
        for sample in sample_and_compile(proposal, template, baseline):
            if budget.exhausted():
                break

            # 内部负责前置 invariant、整组编辑、静置及失败回滚。
            trial = execute_from_baseline(baseline, sample)

            save_trial_result(trial)

            if not trial.rule_checks_pass:
                feedback.append(trial.failure_summary)
                continue

            review = agent3.review(
                description, template, proposal, trial
            )

            review = bounded_view_retry_if_needed(review, trial)

            if review.verdict != "pass":
                feedback.append(review)
                continue

            if is_duplicate_or_unchanged(trial, accepted, baseline):
                continue

            accepted.append(save_edited_scene(trial))

            if len(accepted) >= target_scene_count:
                return completed(accepted)

return finished_with_available_samples(accepted, budget)
```

### 11.2 失败如何处理

| 失败 | 下一步 |
|---|---|
| DSL 格式错误 | 将具体字段错误反馈给 Agent2，有限重生成 |
| 绑定对象不存在或类型不匹配 | 重新绑定 |
| 未找到几何候选 | 换采样或换提议 |
| 物理不通过 | 回滚，尝试其他参数 |
| 编辑目标不满足 | 换参数，必要时换策略 |
| 视觉语义不通过 | 将不一致点反馈给 Agent2 |
| 视图不足 | 有限补图 |
| 模型服务或渲染异常 | 标记设施异常，不解释为场景不合法 |

有限采样没有成功，记为 `search_exhausted`，**不宣称场景数学上无解**。

### 11.3 输出结果分开记录

```json
{
  "scene_validity": "valid",
  "edit_satisfaction": "pass",
  "semantic_alignment": "pass",
  "case_condition": "unknown"
}
```

初版的“接受样本”指前三项通过。

距离条件成立、RGB 看起来合理，仍不能证明机器人真实够不到。后续机器人试验可以更新独立的 case 判定，但不修改原有构建结果。

去重依据最终对象、资产和布局，不依据 `proposal_id/sample_id`。无实际变化的样本可以作为基线，不计入编辑生成数量。

### 12.1 保存什么

```text
outputs/case_edits/<run_id>/
├── request.json
├── template.json
├── baseline/
│   ├── scene/
│   └── graph.json
├── samples/<sample_id>/

│   ├── rgb/
│   └── scene/             # 通过样本的编辑场景

```

`sample.json` 合并保存：

- 提议与角色绑定。
- 实际采样参数和具体操作。
- 种子。
- 规则检查结果。
- Agent3 结果。
- 接受或拒绝原因。

失败样本保留已经产生的结果和图像，不增加独立审计链、审批文件或重复报告。

### 12.2 推荐模块划分

```text
agents/
  case_normalizer.py      # Agent1
  edit_proposer.py        # Agent2
  edit_reviewer.py        # Agent3

scenes/
  graph.py                # 实际场景图

construction/
  case_schema.py          # Case Template

  compiler.py             # 角色解析、位姿计算、操作展开
  sampling.py             # 联合采样

validation/

  edit.py                 # 前后 invariant、goals、物理检查

workflows/
  case_edit.py            # 主循环
```

执行仍复用现有构建事务、静置和回滚机制。家具、添加、删除等模型编辑继续走 `MjSpec` 修改与编译，而不是直接改原始 XML。[MuJoCo 模型编辑说明](https://mujoco.readthedocs.io/en/stable/programming/modeledit.html)

### 12.3 当前代码需要调整的关键点

- [`candidates.py`](LastMileDataFlow/src/lastmile_dataflow/construction/candidates.py)：去掉移动距离、朝向等最小编辑排序项。
- [`config.py`](LastMileDataFlow/src/lastmile_dataflow/construction/config.py)：新流程不沿用 `editable/protected` 配置，改用通用模板与 DSL。
- [`build_session.py`](LastMileDataFlow/src/lastmile_dataflow/runtime/build_session.py)：将对象权限策略与执行正确性检查分开；新流程取消前者，保留事务能力。
- [`placement.py`](LastMileDataFlow/src/lastmile_dataflow/validation/placement.py)：不再以“所有未编辑对象不得变化”为默认验收规则。
- Agent 接口不能直接沿用“只能从既有候选中选择”的旧协议，需要支持规范化、提议和复查三种输出。

实现后的核心验收是：

> **同一份抽象描述，能够自动绑定不同实例、提出不同布局策略、采样并生成多个合格场景；无需人工填写实例 ID 和坐标，也不因改动较大而被排序压制。**

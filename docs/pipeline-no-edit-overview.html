在 ProcTHOR val 原始场景里不做任何场景编辑，自动找出「拿杯子」「开冰箱」这类任务， 在目标周围 2 m 圆盘上撒一圈站位，每个站位跑 5 次真实物理操作， 用实测成功率画出热图，挑出「难站稳的起点 S0」和「能成功的终点 S1」， 最后让机器人 自己从 S0 导航过去、再完成操作，把成功的全过程打包成训练数据。

从命令行到数据集，六个阶段依次执行；灰字是负责这块的源码文件。

启动采集 cli.py · collect-no-edit
指定资产目录、run-id、用几张卡。一个 run-id 一个目录，永不覆盖。
锁死环境，冻结输入 verify_version · frozen_config.json
先核对 cuRobo 是不是 0.8.0 且每个文件哈希一致；同时把「源码 + 机器人 + 配置 + 场景清单」的摘要写成指纹。 之后想 断点续跑，指纹不一致会被直接拒绝 —— 防止跨版本跑出脏数据。
列场景，派 GPU collect_batch · gpu_selection.json
只接受 val_*.xml 原始场景；挑利用率 ≤50% 且空闲显存 ≥10 GB 的卡， 每张卡只跑一个场景，谁空就先给谁，忙的时候就等。
进场：冻结场景 + 找任务 run_scene · discover_tasks
加载原始房子并冻结一次，算出底盘外接圆半径（决定站位间距），然后扫描两类任务：
拿取 pick物体最小边 ≤ 0.10 m，而且是能自由移动的物件（不是钉死的家具）
打开 open有门 / 抽屉这类可动关节，当前没全开，也不是把手本身
逐任务采集：撒点 → 跑 5 次 → 画热图 collect_task
每个任务都走同样的四步，站位的 5 次尝试彼此独立、都是真物理，不复用现场。

任务判定 & 选点 construction_rate · select_starts

连续 rollout：一次仿真里先走过去、再动手 run_raw_attempt(path=…)
同一个仿真进程内，从 S0 用 A* 导航到 S1，到站后立刻用 cuRobo 规划操作。 失败就换次高点位、从 S0 重新来一段全新轨迹（不恢复现场）。够格的任务凑满 1 段即可，目标 3 段。
打包成数据集 rebuild_dataset_index · export_rollout
把成功的 rollout 证据复制进 datasets/，连同它起点 S0 的失败证据一起， 并写一份只引用成功段的索引文件。

?站位怎么筛：能站、站得稳、还看得见目标

撒出的每个点都要过三道关，过不了的点会被标注原因而不是悄悄丢掉。

  • ① 底盘摆到点上、朝向目标，头部相机对准目标
  • ② 下方有地面支撑，不和家具/自己穿模
  • ③ 真的渲染一次，目标像素数 ≥ 24（看得见才算数）
  • ✕ 站不稳 → geometry_filtered
  • ✕ 看不见 → visibility_filtered
  • ✕ 通过 → valid，参与后面的 5 次尝试
绿点 = 有效站位，灰点 = 被过滤（原因与数值都记录在案）

⤳S0 → S1：为什么这样选点

热图上每一格都是真实测出来的，不是猜的。

S0 起点成功率最低 + 空间分散 --A* 导航--> S1 终点有成功见证 + A* 可达 --操作--> 成功 rollout打包进数据集
概念怎么来的有什么用
S0 起点 从成功率最低的一档里选，同一档尽量选离其他点最远的 提供「在这里容易失败」的真实素材
S1 终点 只保留实测有过成功的站位，并要求 A* 能连通过去 保证「走过去之后真能做事」
S0 失败证据 来自独立的站位评测，不是从失败现场硬掰出来的 配套的失败样本，来源诚实

⚠几个必须记住的点

开始仿真后不能再摆位姿不能恢复快照、重启或传送；要重来就新建一个仿真和一条新记录。
规划无解 ≠ 做不到只是这一次有限步内没解，物理没执行，不算失败样本。
头部相机视野是硬约束目标不在头部相机视锥内就判无解，默认开启且没有开关，是当前「拿取」成功率的主要瓶颈。
5% 规则有前提只有该任务所有有效站位都跑满了，丢弃规则才生效。
视频一律保留成功失败都存四路 MP4，没有开关可以关掉。
热图 ≠ 可通行地图它显示的是实测成功率；导航栅格另有保守膨胀，可能漏掉狭窄通路。

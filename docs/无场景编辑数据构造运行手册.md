# 无场景编辑数据构造运行手册

本手册用于 `collect-no-edit`：在原始 **ProcTHOR-10k-val** 场景中，使用 **RBY1M、20D全向底盘协议**构建 pick/open 数据。不修改场景，不替代原场景编辑流水线。

**先核查试验数、真实动作步数和视频数，再判断运行是否有效。进程存活、退出码为0或场景处理完成，都不代表采到了成功轨迹。**

代码核对日期：2026-10-10；当前无编辑协议为mobile-pick-v2/mobile-open-v2，躯干误差仅记录。下列命令均从批准的 Worktree 根目录执行。已有运行信息只作查找入口，不代表当前仍存活。

本机复用已装好 MuJoCo/cuRobo/CUDA 的解释器；仅成功 import 不等于GPU规划或EGL渲染验收通过。换机器需显式替换解释器与资产路径，不能仅用系统 `python3` 假定依赖齐备。

## 2. 启动完整或子集构建

每次新构建用新的 `--run-id`，仅允许字母、数字、下划线和连字符。下面模板通过时间生成新ID；不要重复执行已有目录的启动命令。

### 2.1 完整 val_103：全部合格目标、全部采样点

```bash
export RUN_ID="no-edit-val103-full-$(date +%Y%m%d-%H%M%S)"
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id "$RUN_ID" \
  --houses 103 --workers 1 --gpu-ids 0 1 2 3 4 5 6 7
```

不要加 `--targets`、`--max-tasks`、`--max-trials`。原始 val_103 当前枚举得到24个任务（20 pick、4 open），以新运行 `task_index.json` 为准。场景内任务及站位试验依次执行；提高 workers 不会并行拆分一个场景。

当前新协议的独立运行ID是 `no-edit-val103-full-v2-20261010`。旧 `no-edit-val103-full-20261010` 已因协议切换中断、保留为历史数据。查看该运行用第4节命令；**不要用相同ID重新启动**。

### 2.2 仅 Cup_30，但对该目标完整采样

```bash
export RUN_ID="no-edit-val103-cup30-$(date +%Y%m%d-%H%M%S)"
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id "$RUN_ID" \
  --houses 103 --targets Cup_30 --workers 1 --gpu-ids 0 1 2 3 4 5 6 7
```

`--targets` 支持 asset ID、instance ID 或 task ID，不是自然语言类别筛选。Cup_30是资产ID。此命令是**目标子集完整评测**，不是全场景完整评测。

### 2.3 所有原始 val 场景

```bash
export RUN_ID="no-edit-val-full-$(date +%Y%m%d-%H%M%S)"
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id "$RUN_ID" \
  --workers 4 --gpu-ids 0 1 2 3 4 5 6 7
```

不传 `--houses`。当前本机导出1000个规范 `val_<id>.xml`，不重复统计 ceiling 变体。workers控制同时运行的场景进程数，不是每个点的重复次数。

### 2.4 少量试验检查执行链路，不作为完整构建

```bash
export RUN_ID="no-edit-val103-smoke-$(date +%Y%m%d-%H%M%S)"
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id "$RUN_ID" \
  --houses 103 --targets Cup_30 --max-trials 1 \
  --workers 1 --gpu-ids 0 1 2 3 4 5 6 7
```

`--max-trials` 是每任务本次新增尝试的调试预算，不是每点试验数。到达预算会留下 incomplete；退出码1不一定是程序崩溃。`--max-tasks` 是每场景任务子集限制。任何这些限制都不能描述为全场景完成。

只列输入场景可用 `--index-only`（也需独立ID）；不会生成动作或视频。正式采集不要传 `--no-video`。

## 3. 后台运行

先在第1节设置环境，再执行。示例仅启动完整 val_103：

```bash
export RUN_ID="no-edit-val103-full-$(date +%Y%m%d-%H%M%S)"
export LOG="outputs/${RUN_ID}-launch.log"
export PIDFILE="outputs/${RUN_ID}-launch.pid"
setsid -f bash -c '
  echo $$ > "$PIDFILE"
  exec bin/lastmile-dataflow collect-no-edit \
    --assets-dir "$ASSETS" --run-id "$RUN_ID" \
    --houses 103 --workers 1 --gpu-ids 0 1 2 3 4 5 6 7
' > "$LOG" 2>&1 </dev/null
sleep 3
cat "$PIDFILE"
ps -fp "$(cat "$PIDFILE")"
tail -n 20 "$LOG"
```

环境变量必须 export，子shell才能读取。`setsid -f` 立即返回，其返回值不是采集完成状态；看主进程、日志和运行 summary。每个场景详细日志在各自 `worker.log`，主日志只显示派发等信息。

## 4. 检查进度和实际产出

### 4.1 场景级状态和日志

```bash
export RUN_ID=no-edit-val103-full-v2-20261010
export RUN="outputs/no_edit/$RUN_ID"
bin/lastmile-dataflow no-edit-status "$RUN"
tail -n 30 "$RUN/scenes/val_103/worker.log"
cat "$RUN/timing.json"
find "$RUN/scenes/val_103/tasks" -name progress.json -print
find "$RUN" -name '*.mp4' -print
```

`no-edit-status` 只是读取 `summary.json`，不会启动仿真。summary约10秒更新，但 worker 死亡/运行结束后可能保留旧状态；结合实际 `ps` 查看，不能只信 `status=running`。

`completed_scenes=0` 时可能已做很多尝试；`retained_segments=0` 时也可能已有失败操作视频。具体看任务 `progress.json` 的 `terminal_trials/expected_trials` 和尝试 `result.json` 的 `executed_steps`。

### 4.2 一次读出尝试、动作、视频、失败原因

下面命令只读文件，适用于单场景和全量运行；不依赖GPU。并发写入时偶尔读不到某文件，跳过后下次再查。

```bash
"$DATAFLOW_PYTHON" - <<'PY'
import os, json
from pathlib import Path
from collections import Counter
root = Path(os.environ['RUN'])
def read(path):
    try:
        return json.loads(path.read_text())
    except (OSError, ValueError):
        return None
summary = read(root / 'summary.json') or {}
print('batch:', summary.get('status'), 'retained:', summary.get('retained_segments'))
for scene in sorted((root / 'scenes').glob('val_*')):
    attempts = []
    for path in (scene / 'attempts').glob('*/result.json'):
        row = read(path)
        if row is not None:
            attempts.append(row)
    reasons = Counter((r.get('status'), r.get('termination_reason')) for r in attempts)
    print(scene.name, 'finished_attempts=', len(attempts),
          'executed_steps=', sum(r.get('executed_steps', 0) for r in attempts),
          'mp4_files=', sum(1 for _ in (scene / 'attempts').glob('*/videos/*.mp4')))
    print('  outcomes:', dict(reasons))
    for path in sorted((scene / 'tasks').glob('*/progress.json')):
        row = read(path) or {}
        print('  task:', path.parent.name, row.get('terminal_trials'), '/', row.get('expected_trials'))
print('timing:', read(root / 'timing.json'))
PY
```

这里 finished_attempts只统计有结果文件的尝试，executed_steps只统计已完成尝试；正在执行的视频可能尚未封装完毕。MP4数量不能证明文件可解码或任务成功。

推荐每5–10分钟检查一次。**连续两次检查尝试数增长、实际步数仍为0时，先诊断规划/候选，不要等待“自动出视频”，也不要直接提高workers。** 这是人工检查建议，当前程序没有自动零产出告警。

### 4.3 整体生成时间

`timing.json`：

- `started_at_utc` / `ended_at_utc`：UTC起止时间，上海时间加8小时；运行中终止时间为 null。
- `elapsed_wall_s`：从首次开始到当前/结束的墙钟时间，包括准备、GPU等待、渲染编码和续跑之间的间隔。
- `elapsed_active_s`：各次主进程session的单调时钟耗时之和，不是所有并行worker用时之和。
- `sessions`：每次运行/恢复的记录；突发kill后无法确定的终止时间明确标未知。

单任务smoke用时不能当全场景或1000场景总生成时间。主进程被异常kill时最后计时心跳可能过期。

### 5.2 四路视频

前三路是原始 head、左右夹爪图像。第四路是 **1280×720 分析合成视频**，含第三人称主画面、同步活动夹爪近景、阶段/时间、实测抬升/接触及路线；总共四路，不是五路。机器人相机默认320×240；视频FPS以 `videos.json` 为准。

真实执行的站位尝试均保留视频，后续通过 `s0_failure_videos` 引用S0的失败尝试。连续 rollout 的四路覆盖实际导航、到站、操作及发生的重试。原始第三人称PNG只在连续rollout逐帧保存，MP4是分析版。

规划没有动作时，`video_status=not_executed`，不生成虚假失败操作视频。独立站位失败视频不是从同一失败现场无缝恢复；连续示教是独立Simulation从相同S0初始化后执行。

已出现MP4后核验解码（把 VIDEO 替换为实际路径）：

```bash
export VIDEO=/absolute/path/to/videos/third_person_camera.mp4
"$DATAFLOW_PYTHON" - <<'PY'
import os
import imageio.v2 as imageio
with imageio.get_reader(os.environ['VIDEO']) as reader:
    count = reader.count_frames()
    frame = reader.get_data(count // 2)
    print('frames=', count, 'shape=', frame.shape, 'fps=', reader.get_meta_data().get('fps'))
PY
```

再看实际画面。对同一attempt检查四路帧数一致、画面/阶段/时间同步；不能仅凭文件名验收。

### 5.3 成功率热图

`tasks/<task-id>/maps/success_heatmap.png` 或离线 `index.html` 可查看；NPZ保存栅格数值，`heatmap.json`声明平滑方法。

热图首次在站位初始化后生成，并在站位五次试验结束等节点更新。**出现热图不表示所有点已测完**；结合progress检查。Gaussian平滑成功数和有效终局数后相除；未知/未测试不是0%，平滑区域不是新增实测。S0/S1依据原始实测率，不依据插值值。

### 5.4 最终成功数据

只有 `tasks/<task-id>/result.json` 中 `dataset_eligible=true` 的任务进入 `dataset_index.jsonl`。每条是一段真实成功的 S0→S1移动＋S1操作，含语言、20D动作、视频、热图、S0失败证据和选点。

```bash
wc -l "$RUN/dataset_index.jsonl"
head -n 1 "$RUN/dataset_index.jsonl"
```

索引在任务result发布后由主进程刷新，约有一个轮询周期延迟；尚在收集额外段时，已成功的局部rollout不一定立即进入总索引。独立站位成功视频不等于最终成功连续段。

## 6. 停止和断点续跑

### 6.1 停止自己指定的运行

```bash
# 示例为已经启动的 val103 独立运行。
PIDFILE=outputs/no-edit-val103-full-v2-launch.pid
PID=$(cat "$PIDFILE")
ps -fp "$PID"
# 人工确认命令包含目标run-id，而不是其他进程，再执行：
kill -TERM "$PID"
```

向主进程发TERM会中断其worker并写 incomplete/计时；不是等待当前attempt完成，可能留下未完成视频。前台可Ctrl+C。不使用 `pkill python`、`killall`，也不默认kill -9；不删除输出或run.lock。

如果在沙箱/容器中看不到宿主进程，需要在可见宿主进程的终端或经批准的权限下检查；不要因 `ps` 看不到就重复启动。

### 6.2 原身份恢复

确认旧主进程已退出，重用相同 run-id、输入路径、配置、目标/预算限制与输出路径：

```bash
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id no-edit-val103-full-v2-20261010 \
  --houses 103 --workers 1 --gpu-ids 0 1 2 3 4 5 6 7 --resume
```

仅从**已保存的终局attempt边界**恢复。旧未完成尝试保留，新尝试创建新ID；不会在已begin的物理仿真里恢复快照或传送。已完成任务/场景跳过，未完成部分续测。

GPU列表和workers可按资源重新安排；配置、源码摘要、机器人、collection、输入清单以及 `targets/max_tasks/max_trials` 子集身份必须一致。**改源码、参数，或把smoke改成不限预算，必须新run-id，不能强行删除冻结配置后resume。** 恢复后台运行可在第3节模板中用旧ID并加 `--resume`，重新写该进程PID。

## 7. 调整参数

参数先按用途区分，避免把“试验次数”与“调试预算”混为一谈。

| 参数 | 当前默认 | 作用 |
|---|---:|---|
| `--houses` | 全部原始val | 场景子集；103表示独立该场景 |
| `--targets` | 全部合格目标 | asset/instance/task ID子集 |
| `--workers` | 2 | 并行场景数；全量常用4，单场景用1 |
| `--gpu-ids` | 0–7 | 允许派发的物理GPU集合 |
| `--spacing-m` | 实测底盘外接圆半径 | 正方格间距；本机约0.4435m |
| `--trials-per-station` | 5 | 每个合法点的独立操作次数 |
| `--max-tasks` / `--max-trials` | 无限制 | 明确调试/子集预算，正式完整运行不传 |
| `--config` | `configs/no_edit/val.json` | 其他构造与规划参数 |
| `--output-dir` | Worktree的outputs | 最终根目录追加 `no_edit/<run-id>` |

JSON配置关键项（部分默认来自 `NoEditConfig`，不一定显式列在val.json）：

| 配置键 | 默认 | 说明 |
|---|---:|---|
| `radius_m` | 2.0 | 目标周围工作空间半径，物理执行检查 |
| `operation_base_mode` | `holonomic_joint_planning` | base x/y/yaw＋单臂10D规划，20D下发；不支持锁底盘模式 |
| `torso_error_policy` | `record_only` | v2躯干误差只记录，不再超过0.002rad立即停止；限位/碰撞等仍保留 |
| `third_person_enabled` | true | 启用可复用第三人称；四路需求不能关 |
| `discard_below` | 0.05 | 全点评测完成后，严格低于5%丢弃 |
| `start_count` / `min_successful_rollouts` | 3 / 1 | 最好3段、最少1段实际成功 |
| `operation_retries` | 1 | 每个连续S1操作额外重试1次 |
| `max_s1_candidates` | 0 | 0表示尝试全部有成功见证且可连接的S1 |
| `attempt_timeout_s` / `scene_timeout_s` | 300 / 86400 | 单次attempt与单场景预算，超时不记真实任务失败 |
| `max_grasp_candidates` | 4 | 每次试验候选抓法数 |
| `max_operation_plans` / `max_open_plans` | 12 / 128 | pick/open规划预算 |
| `num_ik_seeds` / `num_trajopt_seeds` | 32 / 4 | 规划搜索种子数 |
| `min_free_disk_gb` | 50 | 低于阈值停止，不删除历史数据 |
| `smoothing_sigma_m` | 一个采样间距 | Gaussian热图核宽度 |

示例：只为**新的运行**增加间距或修改次数：

```bash
export RUN_ID="no-edit-val103-custom-$(date +%Y%m%d-%H%M%S)"
bin/lastmile-dataflow collect-no-edit \
  --assets-dir "$ASSETS" --run-id "$RUN_ID" --houses 103 \
  --spacing-m 0.5 --trials-per-station 5 \
  --workers 1 --gpu-ids 0 1 2 3 4 5 6 7
```

改JSON时复制为新配置文件，不要改正在运行的冻结身份再试图resume。更稀网格、更多候选或种子都会改变评测协议，须记录并重新验收。

## 8. 故障排查

| 现象 | 先查什么 | 处理原则 |
|---|---|---|
| 很久没有MP4，试验数在涨 | executed_steps、outcome归因、planning及dry_plans | 步数0通常是执行前候选失败，不是编码故障；不造失败视频 |
| 反复 `IK_FAIL` | `outcome.json.attribution.planning_diagnostic`，抓法/目标变换/FK/关节边界 | free_ik诊断无解只说明有限候选与种子，不证明全局不可达 |
| `robot_collision` 且步数0 | diagnostic.dry_collisions双方body、深度、位置 | 可能是候选躯干姿态碰撞，不等于采样初态漏检或已经实际撞击 |
| GPU低利用率但CPU忙 | 规划器/世界初始化、候选尝试及日志增长 | 当前候选间重建/预热规划器可能昂贵；不要把加workers当自动修复 |
| 没有worker、主进程还在 | gpu_selection.json、nvidia-smi、主日志 | 可能没有合格卡；不要强占已忙或显存不足卡 |
| worker异常/主队列停止新派发 | 场景worker.log traceback、场景summary | 设施错误不记0成功率；先修依赖/资产，再新ID或相同身份resume |
| `resume configuration/code mismatch` | frozen_config与当前代码/参数/路径 | 新run-id，不能篡改历史冻结身份 |
| 同ID启动失败/锁占用 | 该run对应主进程和完整命令 | 已在运行则只监控；锁文件存在不等于锁正被占用，不删除文件绕过锁 |
| 不可见/全部站位过滤 | stations、初始head、skipped_targets | 原始柜内遮挡等可能合理；不隐藏物体、编辑场景强行通过 |
| 索引空但有成功抓取 | task result、selection、navigation验收 | 独立站位成功不代表连续导航操作成功；等待完整评测/实际连续验收 |
| 场景completed但无保留数据 | retained_tasks、各task状态 | 可能所有任务低成功率/无站位/无成功rollout；completed仅表示处理结束 |

2026-10-10曾出现约49分钟内269次尝试全部零动作，故必须检查第4.2节实际产出计数。历史诊断见[无视频排查报告](../reports/no-edit/2026-10-10-no-video-diagnosis.md)，不作为新运行的当前结论。

## 9. 完成验收

逐项核查，而不是只看终端退出：

- `summary.status=completed` 且输入场景范围正确；缺metadata或incomplete不算完整处理。
- 确认 `frozen_config.subset` 没有非预期的目标/预算限制；所有合格任务完成或有明确跳过原因。
- 每任务合法点终局次数达到设定值，未知/incomplete/设施异常不混入零成功率。
- 热图PNG/SVG/NPZ与说明存在，未知区域没有伪装成0%。
- retained任务有1–3段实际连续成功，导航和操作都通过；只完成0段的任务不进最终数据。
- 最终索引引用的动作、四路视频、S0归因均可追溯；无动作S0明确not_executed。
- 四路视频实际解码/看图确认同步；第三人称保留原场景遮挡。
- timing有终止时间与实际总耗时；运行中/异常kill的时间不能当最终完成时间。

CLI正常处理完（包括无保留数据）可退出0；incomplete/设施错误退出1。后台启动的shell退出0只表示启动命令返回。

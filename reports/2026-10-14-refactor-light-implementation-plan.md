### 实施原则：科研代码，不做安全审计式开发

**禁止写哈希和 SHA256；禁止反复写基本不可能出现的 Case。我们不是写安全审计的代码，我们是写科研的代码。可以校验，但禁止过度防御。**

- 不新增哈希计算、校验和文件、源码指纹或以此为基础的身份/封存协议；现有相关实现按上述轻量化顺序移除。实验复现仍只保存实际配置、seed 和 Git commit，不自行计算源码或产物摘要。
- 校验针对会影响实验正确性的实际问题：必要输入可用、动作维度与数值合法、初始化有效、任务判定正确、数据可读取。相同条件在必要边界检查一次，不在每层重复验证。
- 不围绕假想攻击或极低概率组合编写成片分支、异常分类、兜底和测试；只有实际发生的问题或明确影响核心结果的情况才补处理。
- 优先清楚报错和修正输入，不自动修复、猜测兼容或堆叠 fallback。保留必要资源关闭，不将简单读写扩成审计框架。
- 优先最小、轻量、可读的实现；新增校验、抽象或测试必须能解释它解决了哪个具体科研问题。

**该原则同样约束现有代码，不只是禁止新增。实施时必须删除或重构所有相关违反原则的实现，并同步清理调用、配置、测试和运行说明；不能只删除公开命令、停用默认开关，或把旧实现搬到其他目录。** 以当前工作树代码为范围，不改其他工程或既有实验数据。

## 1. 制定方案时的调用关系（实施前）

复读了需求中的删除边界、协议和验收条件，并检查了 `bin/lastmile-dataflow`、安装入口以及源码、脚本、测试中的启动调用。

当前 Shell 包装负责设置源码路径、默认 EGL 和选择解释器；安装声明已经提供 `lastmile-dataflow = lastmile_dataflow.cli:main`。因此无需新增入口系统，直接保留安装入口即可。

删除包装时必须同时处理使用它的队列脚本和 `test_independence.py`。场景 worker 已通过 `sys.executable -m lastmile_dataflow.cli` 启动，MolmoBot 服务通过其配置解释器启动；这两类内部启动不是重复的用户入口，不按名字一并删除。

复查采集调用后确认：`lastmile_datasets.collect()` 为每个场景包建立子 run，再调用 `no_edit.collect_batch()`，最终通过 `collect_views()` 审计并整理数据。真实执行集中在 `no_edit.collect_task()` 及 runtime。这种父子关系可以消除，核心采集不需要再包一层发布 workflow。

## 2. 最终要跑通的最小链路

```text
场景与任务 + 采样点 + 障碍物增强
              ↓
scene-datasets
              ↓
cuRobo / MolmoBot 逐点 rollout → 成败记录与热图
              ↓
       ┌──────┴────────┐
       ↓               ↓
S0→S1→操作数据    困难 S0 最小评测
```

这张图说明目标，不表示现有闭环已验证。首轮真实复现用一个场景、一个 pick 目标、少量采样点、单卡串行；保留实际使用的 open 能力，但不在本次顺手扩展未实现范围。

### 2.1 采集 workflow 合并为 `collection.py`

下列调用关系已在步骤五实现；两个公开入口位于 `workflows/collection.py`。

```text
scene-datasets
      │
      ▼
workflows/collection.py
      ├─ evaluate_stations()  → 逐点 rollout、trials.jsonl、热图
      └─ collect_lastmile()   → 使用标定、选 S0/S1、连续采集、episodes.jsonl
                 │
                 ▼
      共用 runtime 执行器、任务判定与单套记录器

lastmilebench → 共用站位选择与 runtime，不需要调用连续采集
```

两个公开函数代表不同实验目的，不保留 `station_only / lastmile_selection / calibration_only` 等开关交织成的单一巨型函数。

- `evaluate_stations()` 可单独运行，支持 cuRobo / MolmoBot，完成整个采样区域的成败数据与热图。
- `collect_lastmile()` 首版用 A* + cuRobo，读取已有匹配标定；未提供标定时可在本次 run 内调用逐点评测函数一次，不另外创建子 run。
- 使用已有标定时只检查必要的场景、任务、后端、机器人/相机配置和有效次数是否匹配，不重新 rollout，不再审计封存证书。不完整标定不能用于正式 S0/S1 选择。
- 输入统一为最小 scene-datasets 记录；无增强场景也通过同一场景构建入口生成，不保留一套独立的 raw-val-only 采集协议。
- 一个采集 run 只写一份配置和相应主记录；场景、任务按引用组织，不建立“父 publication → no_edit 子 run → 派生发布”的目录关系。
- 必要共用步骤用少量内部函数表达；真实运动、成功判定、记录、选点和绘图仍归各自领域模块，不全部塞进 `collection.py`。

| 旧代码 | 合并时的处理 |
|---|---|
| `lastmile_datasets.input_units()` | 保留场景/任务遍历，删多层身份、源文件摘要和 val-only 绑定；读取归统一场景 loader |
| `lastmile_datasets.collect()` | 删除父子 run、重复配置与发布管理；必要循环纳入统一采集编排 |
| `lastmile_datasets.collect_views()` | 删除审计、重复索引和封存；episode 结果在执行完成时直接写入 |
| `no_edit.collect_batch() / run_scene()` | 简化为场景/任务迭代与共享准备，不再绕原始 val 文件重新找场景 |
| `no_edit.collect_task()` | 分离逐点评测与连续采集，共用场景准备和 runtime，不保留开关驱动的全部历史分支 |
| 执行记录与父级二次整理/索引 | 只保留一套权威记录，统计与选择直接消费 `trials.jsonl` / `episodes.jsonl`；模型格式按需转换 |

文件删除在新函数接管调用后完成，不保留两个旧 workflow 作为兼容壳。`no_edit` 名称也从保留的命令、配置和相关模块中按职责逐步去掉；不机械替换已有实验目录或结果里的历史字符串。

### 步骤三：在原目录里缩小数据协议

按下列顺序改，每次同时改生产者与消费者，避免“新输出 + 旧读取”长期共存。

| 顺序 | 修改对象 | 新的唯一主记录 |
|---|---|---|
| 3A | 场景写入、场景/初态加载、任务和站位读取 | `scenes.jsonl` |
| 3B | 单次 rollout、统一记录器、成功率汇总和热图 | `trials.jsonl` |
| 3C | S0/S1 选择、A* 导航、连续操作与数据读取 | `episodes.jsonl` |
| 3D | 困难 S0 定义、策略评测与结果汇总 | benchmark `episodes.jsonl` / eval `results.jsonl` |

**操作：**

- 每次运行只保存一份实际 `config.json`，其中包含 seed、后端/权重、机器人和相机配置；不再保存整树源码哈希。
- 逐级移除 manifest/seal/checksum 前置条件和内容哈希 ID；ID 改为简单、局部稳定的名称或编号。
- 合并 raw/canonical/replay 重复载荷为一套必要轨迹与观测；大数组用 NPZ，不嵌入 JSON。
- 去掉 all-attempts/train/lastmile 等重复索引，成功训练样本从同一个 episode 主记录过滤。
- 任务成功和执行终止原因分开；保留有效试验计数、异常分类和记录是否完整。
- 初始化、控制模式、相机配置匹配保留为直接检查，不再依靠递归哈希绑定。
- 去掉容量穷举认证与重放。放置不符合配方时报告未生成，不能悄悄少放后仍标成合格。
- 按 §2.1 的职责在原目录中解除父子采集依赖：先让逐点与连续记录直接写入一次，再去掉 `collect_views()` 的二次整理；此时不急于搬文件或新建抽象层。

**一个必要前置检查：** 场景改为 MJCF/可重建配置 + 状态载荷时，先用一个实际增强场景确认新增物体、初态和资产引用能重载，再删除唯一可用的旧快照载荷。没有完成该检查时，如实保留必要载荷，不宣称已经实现可搬动。

**完成条件：** 下游只靠主记录、配置和必要载荷就能加载数据；不要求 audit/checksum/seal。核心单测覆盖读取、计数、选择与连续轨迹关系，不延续旧发布协议测试。

### 步骤八：完成一次最小真实复现

**操作：**

1. 跑保留的核心单测，不再执行已删除历史功能的全套回归。
   采集合并只补必要的关系回归：逐点入口不执行连续采集；已有匹配标定不重复 rollout；配置不匹配或有效次数不足不进入正式选点；没有重复写结果或创建子发布目录。
2. 用一个真实场景和 pick 目标生成增强场景、少量有效采样点，并确认场景可重载。
3. 用 cuRobo 和 MolmoBot 分别执行小规模逐点 rollout，保存真实成功/失败/异常，生成带有效次数的热图。
4. 从完整有效标定中选择 S0/S1，运行 A* + cuRobo 连续采集。无合格配对时保存负结果；若另用有效配对测试连续代码，明确它不是自动筛出的困难样本。
5. 用一个真实标定的困难 S0 跑一次策略评测，保存结果、覆盖率和分母。不同机器人/相机 profile 不复用不兼容标定。
6. 将一个必要输入/输出移动到不同路径，修改 data_root/上游位置后确认可加载，不要求原服务器 symlink。

**完成条件：** 明确哪些链路已实际运行、哪些未运行及其原因。任务失败可以是有效结果；成功示教必须真的导航和操作成功，不能用单测、退出码或文件完整代替。

若采样子集没有困难 S0，bench 只完成启动 smoke，不宣称困难评测完成。下一步针对缺口补标定，而不是扩大成全量场景审计。

## 4. 实施中不增加这些工作

- 不创建新的总 registry、审计清单、来源追踪系统或平行派生索引。
- 不同时维护新旧协议，不建设通用历史数据迁移框架。
- 不为每一步生成封存报告；结果有变化时更新一份简短实施记录即可。
- 不新增 PI、短程导航、模型训练、多策略排行榜或多卡调度。
- 不以行数减少比例、文件数量或全视频验收作为完成标准。
- 不覆盖既有实验输出；首版默认新 run，不实现复杂 crash 恢复系统。

## 5. 需要提前处理的边界

- **工作树：** 修改和安装都针对 `refactor-light`。使用其他工作树的 `bin/` 会运行其他源码，不是统一入口带来的复现保证，之后会merge到main，同时也会应用在其它分支上。
- **仓库约定：** `AGENTS.md` 仍包含旧目录和审计要求，且按当前约定由所有者维护。需要修改。
- **场景载荷：** 保留可用载荷到新的实际增强场景重载检查完成；删除协议不等于删掉物理初态。
- **任务语义：** 成功判据、动作限位和连续执行不因“轻量化”降低。物理逻辑能合并，不能删除成只看执行状态。
- **复现限制：** 下载链接、资产授权、权重可用性和新环境兼容性尚需实际检查。本方案未承诺安装时间或 GPU 实验时长。

## 6. 最终交付

1. 一个只包含核心功能、目录清楚、无旧发布审计依赖的代码仓库。
   包括删除或重构现有违反科研代码原则的实现及配套内容，不仅保证新代码遵守原则。
2. 一个安装后的 CLI，以及可直接被 Python 实验调用的函数。
3. 少量可修改配置、独立环境安装与前置数据说明、一个简短数据格式说明。
4. 一份最小真实运行结果与限制记录；运行载荷留在 outputs，不提交大型数据或模型。

## 0. 口径与证据分级

- **证据分级**（全文统一）：简化 fixture 回归 = 只证明程序逻辑；单元/审计通过 = 证明记录与协议自洽；**真实 GPU/资产执行 = 唯一可支撑任务成败结论的证据**。
- **三层结论不合并**：场景是否有效 / case 是否成立 / 机器人是否完成任务，任一层为 `unknown` 不许升格。
- **数字绑定 run-id**：`outputs/` 被 git 忽略，跨 run 相加会重复计数；「规划无解」一律指**冻结预算内无解**。

## 1. 一页结论

- **一句话**：已能在单一真实场景上跑通「自动构造困难场景 → 站位采样 → cuRobo 规划 → 真实执行 → 成败留证」的闭环，
  并取得**可归因的成败对照**（同站位仅改接近深度，抬升 0.016 cm → 11.54 cm）；但 **case 成立性尚未被验证**，覆盖也不足以支撑任何成功率结论。
- **两项工作的主结论**：
  1. **Agent 参与的 case 构造**：机制可用（协议严格、可真实编辑并留证），但**产出率极低**——真实运行 case1 接受 1 个，case1.5 与 case3 均为 0，**无一处 `case_verified`**。
  2. **真实成败采集**：取得 **3 次严格成功 / 3 次真实执行失败 / 16 次预算内规划无解**，并通过单变量对照解释了同站位成败翻转的机制。
- **核心诊断**：瓶颈**不在模型能力**，而在**自然语言 case 描述缺少可计算、可验证的操作化定义**。

## 2. 研究问题

- **RQ1（构造）**：能否用「程序提供候选 + 外部视觉 Agent 决策」自动构造出符合 case 意图的操作困难场景？

- **RQ3（归因）**：场景构造失败与成败翻转时，原因能否定位到**任务定义**而非模型能力？

## 3. 实验平台（只讲与结论相关的前提）

- **三条能力**：① 场景编辑 + 真实静置检查；② 固定底盘站位采样 + 原生 GPU cuRobo 规划；③ 20 维动作桥的真实执行与逐 tick 物理留证。
- **构成结论前提的设计选择**：
  - 编辑后**必须真实静置**再判定，不允许固定物体、关闭碰撞、写回坐标伪造稳定。
  - 规划无解 / 真实执行失败 / 基础设施异常 / 未测试**四类分开**，不混淆、不生成虚假执行轨迹。

## 4. 研究一：Agent 参与的 case 构造

### 4.1 方法

- 四 Agent 分工：生成模板 → 选局部上下文 → 产出 DSL 编辑 → 编辑前后配对复查；
  程序负责候选生成、几何/物理检查与执行；Agent 只在候选内选择，无仿真写权限。

## 5. 研究二：站位图与真实成败采集

### 5.1 方法

- 分层站位采样（几何过滤 → 规划 → 只对价值点真实执行）；
  每次试验从**同一冻结初态**重载，只在开始前设置底盘站位；开始后不传送、不回滚、不固定目标。

## 6. 失败归因：自然语言 case 描述缺少可计算、可验证的操作化定义（重点）

- **一句话**：失败链条是 —— **语言歧义 → 隐含约束缺失 → Agent 自行猜测 → 构造结果不稳定 → 难以验证 case 是否真正成立**。

- **要点 1：语言歧义带来多义解释**
  「北面太窄」「南面够不到」「西面更适合抓」对人很好理解，对 Agent 却不唯一：
  「太窄」是多少米？「够不到」是 IK 无解还是规划碰撞？「更适合」是成功率更高，还是仅仅存在一条可行轨迹？
  于是 Agent 只能自行补全隐含条件，**同一句描述被转成完全不同的场景编辑**。

- **要点 2：任务定义不够可执行**
  Case Template 停在自然语言层，`requirements`、`parameters` 等关键约束**为空**（表 4-4 实测三例均为空），
  Agent3 只能自行猜测坐标、距离与采样范围。

- **要点 3：Agent 承担了过多本应程序化的判断**
  可达性、碰撞、站位空间都可由 `reach_ok`、`plan_ok` 与几何计算确定，不适合交给 LLM 猜测；
  由此导致**结果不稳定、成本高、难以规模化生成**。

- **真实图表**：图 6-1 因果链示意图（语言歧义 → 隐含约束缺失 → Agent 猜测 → 不稳定 → 难验证），
  每个环节旁挂一条本节已核对的真实证据：
  - 「语言歧义」→ 表 4-2（椅子 0.468 m 深 vs 所写 0.19 m 区间，9 候选全拒）
  - 「约束缺失」→ 表 4-4（三份真实 `template.json` 的 `requirements`/`parameters` 全为空）
  - 「Agent 猜测 → 结果不稳定」→ **图 4-1 散点图**（20 次真实运行里调用 0–15 次全部 0 接受，唯一接受者仅调用 4 次）
  - 「难以验证 case 成立」→ `case_verified_count` 累计为 0
- **保留的效度维度：构念效度** —— 全部样本只到「构造通过」，**无一处证明「不移动不行、移动后更好」**；
  case 描述还与原始定义漂移（case1 方向相反）。
- **说明**：本报告**不把偶发 SIGTERM、子进程原生崩溃等技术故障纳入归因**；它们是工程噪声，不构成科学结论。

## 7. 结论与下一步假设

- **已获证**：闭环可跑通；单变量对照可解释成败翻转；失败可按机制分类且留证完整。
- **未获证**：case 成立性、跨场景外推、双臂与多资产覆盖。
- **可检验假设**：把每类 case 写成**可计算的成立条件**——先区分「够不够得着」与「能否无碰撞抓到」两个判定量，
  由程序产出候选、Agent 只在候选内选择——预期同时提高接受率与可验证性。
- **真实图表**：图 7-1 `reach_ok × plan_ok` 四象限（正常 / 被障碍挡住 / 距离超出 / 预算内无解），
  象限语义依据 `reports/phase2/v-case-factory/case-definition-proposal.md` 第 67–75 行。
- **效度注意**：该假设尚未实施，本报告不作效果声明。

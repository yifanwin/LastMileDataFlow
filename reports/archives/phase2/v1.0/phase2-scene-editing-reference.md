日期：2026-10-02（Asia/Shanghai）  
范围：分析与设计建议；**未实现阶段二代码，未运行新的场景编辑、抓取或 cuRobo 实验。**

## 结论摘要

**建议把阶段二定位为“面向机器人任务的场景与初态构建”，而不是独立场景编辑器：任务/case 定义要求，检索和最小编辑产生候选，机器人执行提供反馈，最终按证据收录数据。** 内部借鉴 MUSE 的逐条需求满足与局部修复，以及 Edit-As-Act 的操作契约；不完整移植任何一套系统。

**原方案的编辑章节是可调整设计，不是必须照单实现的约束。** 能直接使用的场景不编辑；规则已能检查的样例不强制调用 Agent；只实现首批任务真正需要的操作。本报告给出替代设计建议，未修改原计划文件。

对 LastMileDataFlow，最重要的不是开放式编辑能力，而是：

1. **构建结果可用**：目标确实位于指定支撑区域，物理状态合理，机器人初态有效。
2. **不破坏数据含义**：场景有效、符合构建意图、机器人任务成功分别记录；困难程度留给第三阶段实证确认。
3. **构建过程可控**：少量修改、失败可回滚、超预算自动换场景，不追求把每个房屋都修成功。
4. **下游可复用且能反馈**：交付场景、机器人初态、任务定义、结果检查规则和证据引用；后续执行结果用于接受、重新归类或生成新候选，而不只是产出布局 JSON 或截图。

**首版保留：**结构化要求、有限编辑操作、几何候选、逐项验证、保护约束、静置检查、事务日志、预算退出。  
**首版不做：**通用自然语言规划、完整反向符号搜索、三个独立 LLM Agent、生成式 3D 资产、风格编辑、全屋优化和任意代码执行。

## 1. 我们需要的是“数据管线的场景构建器”

原计划已经区分了构建候选和第三阶段的操作实证。[P1] **这一证据边界值得保留，但不应变成“编辑做完再也不管执行”的单向交接。** 建议让阶段二与后续规划/执行通过明确的反馈接口形成闭环；必要的低预算探针可提前接入，但真实困难标签仍由实际试验产生。

| 比较项 | 通用室内场景编辑 | LastMileDataFlow 阶段二 |
|---|---|---|
| 输入 | 开放自然语言、任意布局要求 | 首批 case1、1.5、2、3 及结构化参数 |
| 修改范围 | 家具布局、外观、风格等 | 目标、少量障碍、局部通道及必要关节初态 |
| 合格标准 | 指令符合度、布局合理、非目标区域保持 | 正确落位、物理稳定、构建意图明确、可恢复 |
| 允许失败吗 | 通常希望尽量完成用户这一次编辑 | 可以记录原因后丢弃候选、换场景 |
| 主要输出 | 场景表示、渲染或资产 | 包含场景、初态、任务与证据的任务实例候选 |
| 如何认定“难” | 可能只作语义或几何判断 | 必须由后续指定策略、预算下的实际试验确认 |

尤其不能把“有障碍”都当坏事。case3 需要障碍影响机械臂路径；我们要禁止的是**初始穿模、错误支撑等无效状态**，而不是自动把所有妨碍机器人操作的物体清走。

同样，**有效场景中的真实机器人失败是有价值的数据**。不能只保留容易成功的构建，也不能把所有失败都解释成场景搭错了。

### 1.1 建议修改原方案的五个默认设定

| 原编辑流程容易形成的默认设定 | 建议替换成 |
|---|---|
| 找到场景后先让 Agent 提编辑方案 | 先检查任务条件；满足就零编辑通过构建检查 |
| 每个样例都经历固定的 Agent 选择和复查 | 规则优先；语义不确定、候选难选或修复停滞时才调用 |
| 六类编辑能力齐全后再接任务 | 按 case 需要逐步实现；关节编辑、家具组搬移等可延后 |
| 编辑模块产出一个 SceneVersion 就算结束 | 交付 TaskCandidate，并接收后续机器人试验反馈 |
| 尽量保留编辑前全部布局 | 默认少改；重点保护任务关键关系，允许在权限内调整无关局部内容 |

这里的最小修改是成本和可解释性偏好，不是必须求出数学意义上的最少动作。自动跳过没有把手证据、无法稳定落位或修复成本过高的候选，比建设更强的通用编辑器更符合首版目标。

## 2. Edit-As-Act：先明确目标，再倒推必要编辑

### 2.1 原论文的编辑流程

Edit-As-Act 将编辑视为目标驱动的动作规划，而非一次预测整间房的新坐标。其三步流程如下。[E1]

```text
自然语言要求 + 原始场景
        ↓
提取最终应满足的关系：存在、支撑、朝向、相对位置等
        ↓
从目标反推：哪个编辑动作能实现它？该动作缺什么前置条件？
        ↓
Planner 提议 → Validator 检查 → 拒绝并反馈 / 接受并继续反推
        ↓
得到反向计划，倒序后执行
        ↓
按论文设计，从更新后的几何重新检查关系
```

每个 EditLang 动作包含三部分：

- `pre`：执行前必须成立的条件。
- `add`：执行后应新成立的关系。
- `del`：执行后不再成立的关系。

例如“把灯放到桌上”，若桌面没有空位，就先形成“清出一块桌面”的子目标。原场景已经满足的前置条件不再重复构造。论文的 Validator 检查目标相关性、不破坏既有进展、上下文一致性和格式合法性，并结合几何约束过滤动作。[E1]

**对我们最有用的不是反向搜索本身，而是让每次编辑都说清楚：为什么要改、什么情况下能改、改后必须检查什么。**

### 2.2 可以直接借鉴的机制

**第一，声明编辑契约。** 比如移动杯子不能只是 `set_pose`，还应声明目标支撑面、允许变动对象、期望朝向和失败条件。

**第二，按依赖处理问题。** 删除桌子前查询桌上物体；移动支撑家具前处理依附物；旋转杯子后重新检查把手空间。首版用简单依赖关系与固定模板即可，不必上完整符号规划器。

**第三，使用执行后的事实更新状态。** 计划里写了 `on(cup, table)`，不意味着它真的成立；以静置后的接触、位置和支撑检查为准。

### 2.3 不建议照搬的部分

- **开放词汇目标提取与完整反向规划。** 我们的 case 已固定，模板可以直接生成要求；通用搜索会增加调试和调用成本。
- **风格化、缩放和生成资产。** 与首批采集目标无关，缩放还可能破坏碰撞、惯性和 grasp 的一致性。新增物体应来自已有合格资产池。
- **论文中的物理合理性分数。** 论文主评测的 IF、SC、PP 是视觉语言模型评分，且实验针对静态场景；不能据此认定 MuJoCo 动态落位或 RBY-1 抓取可靠。[E2]
- **固定数值容差。** 论文附录的包围盒碰撞、支撑面积规则可以启发预筛，但不是杯把手、柜层及机器人接触的通用验收标准。[E3]

### 2.4 本地代码与论文设计必须分开看

本地代码有实用参考价值，但**不能直接拿来当阶段二的物理执行器或验收器**。以下结论仅针对本次查看的代码版本，不外推为作者完整实验系统的行为。

| 本地代码事实 | 对我们意味着什么 |
|---|---|
| `GeomChecker._feasible_check` 对部分编辑及未知动作直接返回 `True`；部分缺失对象/支撑信息也放行 | 缺少检查不应等于可行；本工程应返回拒绝或 `unknown` |
| `PlanExecutor.apply_action` 先取得几何执行结果，再按声明的 `add/del` 更新符号集合；该函数未按几何结果重新推导全部关系 | 不能把符号效果当执行证据；错误结果必须阻止提交 |
| `PlanExecutor` 的未知动作可作为 no-op 返回成功；添加资产有占位条目 | 未支持操作、缺失真实资产必须明确失败 |
| README 使用的 `tools/apply_plan_to_scene.py` 也包含新增 MESH 的占位描述 | 生成布局文件不等于生成可仿真的实体 |
| 部分执行路径采用 Y-up 场景坐标，并提供 Blender 坐标转换 | 不复制坐标代码；沿用本工程 Z-up、m/rad、`xyz_wxyz` |

依据：[几何检查代码][C1]（约 258–355 行）、[计划执行代码][C2]（约 44–148 行）、[布局写出工具][C3]（新增资产分支）及[坐标工具][C4]。这些发现也说明：流程说明中的“每步重算关系”是论文应有机制，不能未经核对就当成本地所有执行路径已实现的保证。

## 3. MUSE：逐条满足要求，避免后续编辑破坏前面成果

### 3.1 原论文的编辑流程

MUSE 将指令拆为可跟踪的 requirement，也就是**能单独判断是否完成的一条要求**。Architect、Sculptor、Inspector 分别承担需求编译、局部编辑和验证职责。[M1]

1. **编译要求。** Architect 生成 `hard / edit / style / preserve / forbid` 等类型的要求，绑定对象、优先级及可检查谓词。
2. **把要求落到真实场景。** Sculptor 建立房间边界、支撑面、自由地面、墙面和保护区域，避免只对着一串对象名称推理。
3. **选择当前一条要求进行局部编辑。** 声明式工具先查询几何区域，再变成具体放置/移动操作；执行前检查保护约束。
4. **局部修正后逐条验证。** Inspector 对可计算条件使用规则，对剩余语义或视觉条件使用模型；规则结果优先。记录 `satisfied / unsatisfied / unknown`、对应对象、失败原因和修复建议。
5. **更新状态并继续。** 已通过内容进入保护范围，继续处理未完成要求；结束时做全局可行性检查。超出有效进展范围也可以结束，不保证每个输入都成功。[M1][M2]

保护分为两类：一种禁止删除/替换，另一种还禁止移动/旋转/缩放。关键在于**执行前阻断违规操作**，而不是只在生成后的图片上发现问题。

### 3.2 三层 memory 不必变成三个复杂子系统

| MUSE 的状态层 | 原论文用途 | 我们的轻量对应物 |
|---|---|---|
| Working Memory | 当前要求、完成/待办、对象绑定、保护集合、失败记录 | 一个构建会话的结构化状态和事务日志 |
| Scene Memory | 持久对象 ID、支撑关系、区域、场景结构 | 版本化实例表、区域表和关系缓存 |
| Skill Memory | 常见布局结构及分解提示；评测时冻结 | case1/1.5/2/3 的版本化模板和修复规则 |

因此，**不需要为了借鉴 MUSE 先建设向量记忆库、在线技能学习或多 Agent 对话平台**。JSON/SQLite、固定模板和清晰的状态机已经能承载核心思想。

还要注意：MUSE 的保护主要作用于一次编辑过程；后续新指令可以针对当前场景重新编译要求。它不是永远禁止修改任何已经成功过的对象。[M2]

### 3.3 特别适合阶段二的部分

- **逐条要求跟踪**：区分“物体稳定”“支撑正确”“把手朝向正确”“机器人初态有效”，不给一个笼统成功标记。
- **局部编辑与局部修复**：把手不对先转杯子；目标空间不足先换候选，不默认重排全屋。
- **保护已成立的关系**：构造障碍时，不应顺手移动已验证的目标或改变指定操作侧。
- **规则优先、模型补充**：视觉 Agent 可以指出把手辨认错误，但不能把已检测到的严重穿模判为通过。
- **最终独立检查**：MUSE 的论文评测不直接相信其内部 verifier，而在场景导出后另做检查；我们可借鉴为“从冻结包重新加载再验收”，不必复制整套 benchmark。[M3]

### 3.4 两个必须改写的地方

**不能接受改变任务含义的降级。** MUSE 附录 A.7 允许某些声明式放置失败退化为附近地面放置，并记录 `ToolDegradation`。这对编辑工具可能有用，但对我们的“必须放在桌面/指定柜层”是不合格结果。可以换同一合法区域内的候选，不能把错误支撑包装成完成。[M2]

**不能把保护集合当物理固定。** 禁止编辑器移动一个杯子，不意味着杯子在仿真里不会被撞走。保护约束必须同时有执行前检查和静置后的状态复查；不能焊住物体、关碰撞或每步写回坐标。

论文报告在固定 **240** 个编辑样例上，All-Goal 为 **49.6%**、保护率为 **99.9%**。这说明“保留背景”与“完成全部要求”是不同维度，不能只凭高保护率推断管线高产出率；这些也不是机器人任务成功率。本文不据该表对两种方法作脱离评测适配条件的通用排名。[M4]

## 4. 推荐组合：任务驱动外循环，两篇论文支撑构建内循环

以下为本项目设计建议，不是论文已在 LastMileDataFlow 上验证的结果。

| 机制 | 建议 | 落地方式 |
|---|---|---|
| 需求分解、逐项状态 | 首版采用 | case 模板直接生成要求；每项附检查器和证据 |
| 动作前置条件、预期效果 | 首版采用 | 严格 schema、编辑权限、支撑依赖、操作后检查 |
| 几何 grounding | 首版采用 | 稳定区域 ID、支撑面和候选位姿由程序生成 |
| 局部修改、保护与回滚 | 首版采用 | 小事务、保护字段、失败恢复、受影响要求重验 |
| 三层 memory | 简化采用 | 会话状态 + 场景事实 + 固定 case 模板 |
| 规则/视觉联合验证 | 按需采用 | 最多一个视觉 Agent；规则已充分时不调用，硬门槛不被覆盖 |
| 通用目标回归规划 | 暂缓 | 固定依赖顺序和少量修复规则足够时不用搜索 |
| 风格、缩放、生成网格 | 不纳入首版 | 只用合格资产及已知物理配置 |
| 完整编辑 benchmark | 不作为目标 | 测可加载、落位、恢复、退出及下游交接 |

### 4.1 先定义管线外循环，再实现构建内循环

任务契约就是预先说清：操作对象、机器人初态、允许动作、成功条件，以及这个 case 需要什么执行证据。它约束构建器，而不是让编辑器自行决定采集任务。

```text
任务/case 契约 + 机器人配置 + 采集目标
    ↓
检索 → 已满足则零编辑；否则最小编辑 → 冻结任务候选
    ↓
机器人低预算探针 / 阶段三站位规划与执行
    ↓
场景有效性、case 条件、任务结果分别判定
    ↓
符合收录目的 → 保存成功/失败/恢复数据
不符合构建意图 → 保留原证据，重新归类 / 新建候选 / 换场景
基础设施故障 → 修复或重试运行，不盲目改场景
```

低预算探针由 `planning/runtime/validation` 提供，构建器只消费结果；没有实现时记录 `not_tested`，不伪造成功。它用于筛掉明显不匹配的候选，不代替完整站位图，也不证明全空间可解或不可解。

构建内循环再借鉴 MUSE 与 Edit-As-Act：

```text
case 配置 + 机器人配置 + 冻结构建预算
    ↓
静态检索 → 候选房屋和资产
    ↓
加载候选 → 基础检查 → 场景事实、支撑区域、局部候选
    ↓
case 模板生成要求和保护范围
    ↓
已满足则跳过编辑；否则程序选方案，必要时咨询视觉 Agent
    ↓
检查权限、前置条件、候选版本 → 执行编辑事务
    ↓
真实静置 → 落位、穿透、稳定性及邻近资产检查
    ↓
失败：撤回试改，有限修复；重复失败或超预算则换候选
通过：更新事实和要求状态，保护已成立部分
    ↓
静置后按需视觉复查 + 最终全部硬要求检查
    ↓
冻结任务候选 → 独立加载复核 → 交给机器人试验外循环
```

流程图类别为“解释”，不是已运行结果。采用纯文本，避免依赖特定 Markdown 图形插件。

**“一次只改少量对象”不等于只能执行一个原子动作。** 若移动家具需要先安置其上物体，这些相互依赖的操作可以组成一个小事务，一起提交或一起回滚。首版遇到复杂支撑链时优先拒绝或换场景，而不是实现通用搬家规划。

### 4.2 要求分成三层，不提前制造困难标签

| 层次 | 例子 | 阶段二如何处理 |
|---|---|---|
| 场景有效性 | 目标正确支撑、无严重穿透、无异常掉落、机器人初态合法 | 必须验证；关键项未知也不能放行 |
| 构建意图 | 目标距离区间、把手局部方向、障碍区域、侧向净空差异 | 检查并记录；明确哪些是几何近似或视觉判断 |
| 实际操作性质 | 固定站位是否失败、移动后是否成功、指定把手抓取是否完成 | 由机器人试验检验；无实际证据时保持未知 |

建议新增 `build_requirements` 存储逐条构建证据，但不破坏现有三个独立结论：

```text
scene_validity = valid（注明本次检查范围）
build_requirements = 全部必需构建要求通过
case_condition = unknown（尚无机器人试验证据）
task_completion = unknown（尚未进行任务执行）
```

`unknown` 不是模糊的成功。若未知的是阶段二必须验证的支撑/穿透，应补充观察、换候选或退出；若未知的是阶段三的操作难度，才允许带着明确待验项交接。

### 4.3 有限操作接口应强调“意图”，而非任意坐标

Agent 或模板提议类似“将目标放到区域 T3 的候选 P4，使用朝向 O2”。程序解析实际位姿。下列六类接口可覆盖原计划，但**不是都必须先完成才允许形成任务闭环**：首批优先移动/旋转、按需增删及撤销，合法关节初态按 case 需要补齐。

| 操作 | 必需约束 |
|---|---|
| 移动 | 对象可编辑；候选属于当前版本；声明目标支撑/区域 |
| 旋转 | 合法姿态；明确物体轴、部件轴与参照系；旋转后重验 |
| 增加 | 真实资产存在；身份唯一；物理/碰撞资源完整 |
| 删除 | 不受保护；不存在未处理的支撑依赖或任务引用 |
| 设置关节初态 | 仅构建阶段；关节/单位/限位正确；检查新碰撞 |
| 撤销 | 恢复对应模型、状态、实例映射与要求状态；保留失败日志 |

每条要求至少记录：`id`、条件与参数、适用阶段、检查器版本、依赖对象/区域、状态、证据、失败原因。每条操作记录：请求版本、候选 ID、实际参数、前后状态引用、影响范围、检查结果和提交/撤销状态。

不让 Agent 修改质量阈值、物理参数、成功定义或保护规则。补视图与几何查询是可开放的工具；任意 Python 执行不是首版工具。

### 4.4 TaskCandidate 比单独 SceneVersion 更适合下游

建议将阶段二输出逻辑上升级为以下任务候选记录，复用已有文件引用，不复制模型和视频：

```text
TaskCandidate
  scene_ref / checkpoint_ref      场景和物体布局
  robot_init_spec                 机器人初态或合法初态采样范围
  target / operation              操作谁、做什么、普通抓取还是把手抓取
  build_requirements              构建硬要求及证据
  case_hypotheses                 期望的站位/操作差异，未试验前不当作事实
  execution_protocol             固定/移动底盘、允许自由度、策略与预算
  success_evaluator_ref           任务结果检查规则及版本
  provenance / build_ref          来源、编辑、Agent 与验证记录
```

可调整的不只有物体位置：目标实例、合法机器人起点、操作侧与障碍配置都可以是候选参数。变化必须记录；固定站位对照中的底盘移动不能偷偷作为“修复”继续记成原地成功，普通抓取也不能替代把手抓取。

### 4.5 机器人反馈必须先分类，再决定是否重建

| 后续证据 | 推荐处理 | 不应采取的做法 |
|---|---|---|
| 目标掉落、错误支撑、严重初态穿模 | 构建失败；修复或换候选 | 把它收录为正常机器人难例 |
| 实际任务成功，但没有预期站位差异 | 保留结果，归为普通样例，或按新参数另建候选 | 仍贴原来的困难 case 标签 |
| 指定原地试验失败，另一站位/移动后有成功见证 | 记录有条件的 case 证据，继续相应采集 | 声称所有原地配置都不可能成功 |
| 场景有效，但当前预算内所有试验失败 | 保存未解难例；按采集目的决定继续接管、换候选或补试 | 自动删除所有障碍直到成功，或宣称物理不可解 |
| 仅规划无解，未真正执行 | 保存规划失败和搜索范围 | 伪造执行失败轨迹/视频 |
| 渲染、资产加载、API 或规划服务异常 | 基础设施失败，单独重试/退出 | 根据基础设施异常调整任务难度 |

若某个 case 的定义需要“存在一个成功解”，相应成功见证是该 case 收录的必要条件；纯失败数据则进入声明为未解/当前预算失败的类别，不强行混为同一类。该反馈设计才是编辑模块服务数据管线的关键。

## 5. 比两篇论文更需要补强的，是仿真内的落位与恢复

### 5.1 先确定正确支撑，再谈稳定

检查顺序建议为：

1. **编辑前预筛**：区域尺寸、物体完整足迹、支撑高度、边缘余量、明显重叠及编辑权限。
2. **执行后真实静置**：保持机器人控制目标，使用真实 stepping；不持续重置物体。
3. **检查最终关系**：目标是否仍在指定支撑面/柜层/容器；不是仅看物体中心或家具整体包围盒。
4. **检查动态稳定性**：在末尾一段时间观察速度和位姿变化，并保留过程中弹飞、异常接触等信息。
5. **检查副作用**：目标附近物体、支撑依赖和保护对象是否掉落、偏移或失效。

支撑判定应综合已识别区域、接触对象、相对高度和足迹关系。metadata 中的 `parent` 可以用于检索和依赖提示，**不能替代编辑后的实际支撑证据**。

首版可沿用原方案提出的约 **0.5–2 秒**静置窗口作为试跑起点，并设最大延长时间。这个区间不是已经校准的保证；阈值必须按协议冻结，不能为某个成功样例临时放宽。[P1]

### 5.2 快速几何检查与最终物理检查分工

- AABB/OBB、区域边界、距离用于便宜的候选筛选；不要用整件桌子的包围盒替代真实桌面。
- 接触、实际碰撞几何和短时动力学用于验收；杯把手孔洞、柜内空腔尤其不能只靠大包围盒判断。
- 支撑所需的正常接触和轻微数值穿透可以按统一协议允许；严重穿透、错误落位及明显不稳定必须阻断。
- 保护对象允许协议范围内的数值漂移，但不能被当作“保持不变”而忽略实质移动。
- 源场景已有轻微告警应与新引入问题区分记录；已有严重无效状态不能因为“不是我们造成的”就放行。

第一阶段的穿透阈值已明确是**尚未逐类别校准的启发式**。阶段二应优先用代表性的目标、桌面和障碍校准，不直接继承为“完整落位验收器”。[P3]

### 5.3 局部检查节省成本，但提交前必须防止旧结论失效

可以只对本次编辑对象、支撑对象及接触邻居做即时精查，但要维护受影响范围：

- 对象/区域变化后，其关联的已通过要求标为待重验。
- 如果静置造成额外物体移动，把这些物体加入影响范围。
- 几何候选、把手世界方向、通道净空等缓存与场景 revision 绑定；旧版本候选不能直接执行。
- 最终扫描全场基础异常，并复查全部硬要求、保护关系和机器人初态。
- 最后一次修复后也要重新验收，不能“验收完再微调”。

这比追求“所有成功关系永远单调增加”更适合物理仿真：**允许试改失败，但不允许失败污染已提交状态。**

## 6. 首批四类 case 如何使用这些机制

| Case | 阶段二值得构造和检查的内容 | 应保护什么 | 阶段三再判断什么 |
|---|---|---|---|
| case1：距离困难 | 有效桌面目标、合法起点、声明的目标距离/高度区间、可接近区域 | 目标身份、正确支撑和操作语义 | 指定臂/躯干/grasp/预算下，原地是否失败，移动后是否成功 |
| case1.5：侧向差异 | 房间/家具局部坐标系下的侧向通道、净空与目标距离差异 | 造成差异的结构及拟保留接近方向 | 各侧导航、站位和操作的真实差异 |
| case2：把手朝向不匹配 | 合格 mug、可靠把手局部方向/区域、姿态候选、指定操作侧 | mug 身份、把手语义、支撑面及必要障碍 | 是否确为把手抓取；不同操作侧的规划和执行结果 |
| case3：抓取路径障碍 | 在候选接近走廊附近放置稳定障碍，同时不穿透目标 | 目标、必要难度障碍与不应修改的背景 | 是否影响真实规划/执行，是否存在其他可行路径 |

这里的“接近走廊”和“距离困难”只能是构建启发式。不要提前记录 `unreachable=true` 或 `all_paths_blocked=true`。几何代理可用于排序和预筛，但不证明机器人无解。

case1.5 的“北/南/西侧”还应明确参照系：世界、家具局部，还是机器人朝向；不能随相机视角改变含义。

### 一个具体例子：case2 的最小闭环

1. 索引检索含合适支撑面的房屋，从资产池选有把手标注的 mug。
2. 程序生成位置和朝向候选；把手方向来自资产局部标注变换，不能假设模型的 `+X` 天然就是把手朝向。
3. 模板依据可靠标注选择朝向与操作侧；需要语义判断时让 Agent 看带 ID 的局部图，看不清可请求补图。
4. 程序检查旋转后的几何与支撑，执行并静置。
5. 验证杯子仍在指定桌面、姿态稳定、把手方向符合构建要求；失败先换朝向/位置，不扩大修改范围。
6. 保存静置后的场景包。把手抓取成功与否仍为未知，留给第三阶段。

### 资产池不能用一个“可抓取”布尔值

建议分开记录 `loadable`、`placement_checked`、普通抓取证据、把手抓取证据及其机器人/协议/初态范围。grasp 文件存在或历史一次成功，只能说明有候选依据，不能证明当前场景可抓。

原计划要求首批资产分别验证普通与把手抓法，但阶段一没有原生 cuRobo 后端。这是需要显式处理的依赖：可以用少量标准化执行探针对资产资格做验证；若仍缺可执行抓取方案，则资产只能标为候选，**不能宣称这一项已完成**。不应为了填写资产表，把整套站位图与规划系统偷偷提前塞进阶段二。[P1][P2]

## 7. Agent、索引与记忆都保持轻量

### 7.1 视觉 Agent 按需调用，零调用也是合法路径

建议调整原方案“固定时机默认调用”的方式：保留构建选择、静置后复查和异常修复接口，但只在规则/模板不足时使用一个视觉 Agent。可靠资产标注和规则已经覆盖要求的样例，可以零调用；部件辨认、候选取舍或布局语义不确定时再升级处理。必需语义仍无法确认时，应换候选而不是跳过检查。

观察包建议包括：俯视图、目标局部图、机器人视角、必要侧视图，以及实例 ID、区域 ID、候选编号、几何事实和检查结果。**编辑前、编辑后未静置、静置后必须分清；最终判断只使用当前版本证据。**

诊断相机与剖视图独立标为 `diagnostic`，不能混进三相机机器人视频，后续更不能默认作为 VLA 可见输入。

没有外部 API 时，可用脚本决策或录制响应调试闭环，但日志应写明真实来源。规则证据充分的 case 可走正式程序路径；确实依赖视觉判断的 case 则限制范围或跳过，不能把脚本响应写成模型复查通过。

### 7.2 索引采用“静态粗筛、加载后确认”

对 10k 场景先解析 metadata/MJCF 和资产目录，记录类别、房间、父子关系、静态/动态类型、关节、资产与 grasp 引用。只对候选加载仿真，补充真实支撑面、放置区域和净空。

本次抽查 `train_0_metadata.json` 看到了 `room_id`、`is_static`、`parent/children`、`name_map` 等字段，也看到了空的 `mjcf_path`。因此不能假设 metadata 已经提供完整、可直接加载的资产路径或精确支撑区域。这只是单场景抽查，不代表已确认整个数据集的覆盖情况。[D1]

缓存随源文件/资产摘要失效；静态来源事实与动态验证事实分开保存。首版不需要先建完整全屋语义图或图数据库。

### 7.3 预算围绕“每个可用场景的成本”

建议冻结候选数量、编辑轮数、总静置时长、Agent 调用数和单场景超时。可从原计划的 **2–3 轮修复**起步，另设重复失败检测；预算耗尽记录原因后换候选。[P1]

外循环还应限制同一采集请求累计的候选与机器人探针次数，不能因为创建了新 build 就无限重置预算。

首次通过后即可冻结，不为画面更漂亮追加无关编辑。检索排序同时记录来源多样性，避免永远只挑一个容易编辑的房屋或一个 mug；不同版本保留源房屋 ID，供后续数据划分防止同源泄漏。

## 8. 对现有工程的具体补齐建议

### 8.1 沿用已有领域边界，不新建另一套 editor 工程

| 已有目录/模块 | 阶段二建议增加的能力 |
|---|---|
| `catalog/` | 静态索引、场景查询、资产资格与候选排序 |
| `scenes/` | 可编辑场景描述、稳定实例/区域映射、版本与状态标识 |
| `construction/` | TaskCandidate、case 模板、最小编辑、保护/依赖、事务与有限修复策略 |
| `runtime/` | 构建态编辑/静置的受控执行入口，模型重建与状态恢复 |
| `validation/` | 落位、稳定性、保护和构建要求检查器 |
| `agents/` | 观察包、严格决策协议、复查、预算与工作日志 |
| `recording/` | 编辑前后/静置后证据、失败事件和不可覆盖记录 |
| `workflows/` | 检索—构建—机器人试验—反馈的状态机与预算退出；按阶段接入实际后端 |

case 的差异放模板和检查器，不复制机器人、仿真及录制代码。底层步骤仍由 runtime 执行，不让 construction 或 Agent 绕过唯一执行入口。[P2]

### 8.2 第一阶段有基础，但不是“补几条 set_pose 就完成”

**缺口一：构建态静置需要独立生命周期。** 当前 `Simulation.step()` 要求先 `begin()`，但 `begin()` 后禁止恢复，`freeze()` 也只允许开始前使用。因此不能直接用连续 attempt 的 begin/step 做编辑静置，再解除 started 标志继续改。[L1]

建议新增明确的构建会话权限：允许编辑、静置、回滚；冻结后结束构建会话，下游使用独立新 Simulation/attempt。不能削弱现有“连续执行中不重置”的规则。

**缺口二：状态编辑与模型结构编辑不同。** 可动物体的自由关节位姿和关节初态是状态修改；增删资产、移动固定家具可能涉及模型描述重建。MuJoCo 提供 MjSpec 编辑、编译和重编译接口，但本项目对具体资产的兼容性仍待验证。[MuJoCo 3.5 模型编辑文档](https://mujoco.readthedocs.io/en/3.5.0/programming/modeledit.html)

首版可选可控的“编辑工作副本 → 编译 → 按稳定实例/关节名称迁移状态”。回滚跨拓扑编辑时，恢复前一份模型及其配套快照，不能把旧状态向量硬塞进新模型。重编译后应重建数字 body/joint ID、机器人适配器和渲染资源等绑定。

`integrations/legacy.py` 已有有限新增资产和 free-joint 位姿恢复代码，可抽取经过测试的底层思路，但不能把通用编辑器伪装成 legacy restoration，也不能据此宣布通用增删已经完成。[L2]

**缺口三：必须区分模型版本与动态初态。** 当前 `scene_version()` 的摘要含源场景、机器人、编译模型和 restoration，**没有纳入完整动态状态**。快照另有校验和保护，但只改动态物体 qpos 时，现有 version ID 不足以区分两种摆放。[L1][L3]

建议显式区分：

```text
model_id       → 编译模型、资产依赖与实例映射
checkpoint_id  → model_id + 静置后完整状态 + 恢复所需控制器状态
build_id       → case 要求、编辑记录、验证协议、Agent 证据及最终 checkpoint
```

冻结场景版本再引用上述内容。状态摘要针对规范化内容定义，不仅依赖带容器元数据的文件字节。第三阶段站位试验关联同一物体布局 checkpoint 和各自机器人初态，不能只写源房屋或模型 ID。

**缺口四：配置和数据格式需要正式扩展。** 当前 `TaskConfig` 显式拒绝非空 `allowed_edits`、成功条件和非短动作操作。应新增/扩展版本化构建配置及解析器，不绕过校验，也不改变历史 v1 的解释。[L4]

**缺口五：编辑观察包尚未等于三相机录制。** 当前运行相机服务于机器人执行；俯视、局部特写、分割标注与候选覆盖需要新增诊断视图能力。实例映射还要为新增对象保留真实资产身份，而不是长期停留在未知 asset ID。[L1][L3]

### 8.3 给阶段三的最小交付包

沿用架构已规划的 `outputs/builds/` 与 `outputs/scene_versions/`，不再引入平行存储树。[P2]

- **可恢复现场**：模型、依赖摘要、完整静置后快照、机器人配置和兼容版本。
- **稳定身份**：源房屋/房间、目标及新增实例 ID、资产 ID、MJCF 映射、删除记录。
- **明确任务**：case 配置、操作要求、机器人初态范围、执行协议和结果检查器引用，以及预期支撑区域、部件方向/抓法约束、必要保护对象。
- **构建证据**：编辑事务、请求和实际位姿、静置后结果、物理检查、按需视觉复查及告警；零编辑/零 Agent 调用也如实记录。
- **明确结论**：场景有效性、构建要求状态、待阶段三确认的 case 假设；不预填机器人成功。
- **有限复现信息**：种子、候选顺序、协议/模板/模型版本、Agent 决策和预算；不保存密钥或不可见内部推理。

新增资产清单和删除记录必须参与恢复。只保存 qpos 无法重建被修改的模型拓扑；只保存模型又无法重现已静置的动态物体摆放。

第三阶段若发现构建意图不成立，保留原 attempt，再提出新 build。不能修改已经采集过的冻结场景或覆盖其困难标签。

## 9. 建议的实施顺序与验收

这些是下一步建议，不是本次已经完成的工作。

### 2A：先定义任务候选，打通零编辑和最小编辑的恢复闭环

先明确一个 case 的目标、初态、执行协议、成功条件和待验假设，再用少量固定房屋和合格资产打通零编辑、移动/旋转及撤销。先解决静置—冻结—恢复，不等待所有编辑功能齐全。需要增删时再加入模型重编译与跨拓扑回滚，关节编辑按任务需要排期。

**验收重点：**源文件不变；未支持操作明确失败；事务失败不留下半编辑场景；冻结包可以在独立进程/会话中恢复；不同动态布局不会混成同一状态标识。

### 2B：完成支撑区域、落位检查和局部修复

先支持平面桌面及少量已知资产，柜层/容器保留接口但不要求首批四类 case 全面覆盖。可移动家具涉及复杂支撑链时明确限制，不默默丢掉依附物。

**验收重点：**能识别故意设置的掉落、错误支撑、严重穿模、持续运动及邻近资产被挤落；正常支撑接触不会全部被误拒绝。

### 2C：接入静态检索、资产池与四类 case 模板

再把经过小样例验证的执行与检查器接到场景检索，不先为 10k 场景做昂贵仿真预处理。资产池明确已有证据和待验资格。

**验收重点：**多个来源场景可构建；四类模板输出不同且可检查的构建意图；未知难度不被写成操作失败/成功。

### 2D：在确有语义缺口时接入一个视觉 Agent

复用同一套严格接口，增加选候选、静置后复查、请求补图与有限修复。先做结构化决策校验，再做实际工具调用；与程序模式使用相同物理门槛。若首批模板已能规则化覆盖，则先完成 2E，之后再按漏检/失败分布接入 Agent，不为论文架构强行增加依赖。

**验收重点：**实际完成视觉输入、结构化输出和日志；坏 JSON、未知 ID、过期候选、违规操作、API 超时都有明确结果；不需要逐例人工确认。

### 2E：打通预算退出、下游交接和反馈接口

超过预算自动换场景；冻结后独立重新加载，运行阶段一短动作/三相机记录回归，确保编辑包没有破坏既有底座。这个短动作回归只证明交接可运行，不证明抓取或 case 成立。

同时定义并测试第 4.5 节的反馈分类与新候选关联。真实 planning 后端尚未完成时，可用测试记录验证状态机，但必须标为测试，不算机器人证据；后端可用后优先跑通一个 case 的“构建—执行—判定—修正/收录”，再扩展批量站位采样。这比先把编辑功能全做齐更有价值。

**至少包含以下故障注入：**

1. 目标落到地上或相邻物体上，但最终静止。
2. 目标与桌面、柜壁或障碍严重穿透。
3. 删除带有依附物的支撑物，或局部编辑挤落邻近资产。
4. 修复破坏已通过朝向/保护要求，旧检查结果未刷新。
5. 新增资产资源缺失、ID 冲突、重编译后映射变化。
6. 跨拓扑撤销、损坏快照和模型/状态不匹配。
7. Agent 反复建议同一失败候选，或使用编辑前的候选版本。
8. 将构建期重置/诊断观测误用到连续机器人执行。

### 如何衡量阶段二“够用了”

采用管线指标，而非编辑美观分数：

- **构建产出率**：通过全部必需阶段二检查的场景数 / 尝试构建的场景数，按 case 与失败原因拆分。
- **单位有效场景成本**：总墙钟时间、仿真时间、编辑轮数和 Agent 调用数 / 有效场景数。
- **恢复与交接通过情况**：冻结后独立恢复是否保留身份、摆放、要求和可运行性。
- **错误放行情况**：已知故障是否被误判为有效；将漏检与误拒绝分开记录。
- **覆盖情况**：来源房屋、资产和 case 的覆盖，避免只报告易例总体成功率。

下游接通后再加两项最终指标：**符合采集目的的任务实例产出率**，以及**每个可收录成功/失败/恢复样本的端到端成本**。同时统计场景已有效但 case 不成立、任务无法初始化、结果检查不可执行等浪费。编辑通过率高但下游大量报废，不算管线成功。

暂不指定未经试跑支撑的统一产出率目标。先固定代表性回归集，确认必须阻断的故障不会被漏放，再根据真实失败分布确定预算与容差；不要一上来追求全部场景可编辑。

## 10. 最终取舍

**需要实现的是“在预算内构造可执行任务候选，并用真实执行证据闭合采集流程”，不是“复现两篇论文的完整编辑智能”。**

- 从 **Edit-As-Act** 取操作契约、依赖处理、执行后重新认定事实。
- 从 **MUSE** 取逐项要求、局部编辑、保护、结构化反馈与轻量记忆。
- 在 **LastMileDataFlow** 中补上真正决定数据质量的部分：任务契约、MuJoCo 静置落位、模型/状态共同回滚、版本身份、下游恢复及执行反馈分类。

**最先动手的应是 2A 的任务契约、构建生命周期与最小可恢复编辑，而不是通用 Planner。** 先用一个 case 打穿输入、构建、恢复和执行接口，再按任务需要扩展编辑能力；不把原计划的编辑步骤或论文的 Agent 分工变成新的包袱。

## 2. 目标与范围

**优化目标是减少实现现有功能所需的总代码，而不只是缩短某个文件。** 优先消除逻辑本身，其次改善表达，最后才考虑拆分组织。

- 以 `src/lastmile_dataflow/` 为主要范围，按实际阅读困难和冗余程度逐文件推进，不凭文件长度批量改写。
- 同步修改受影响的调用方、测试和必要说明；不恢复其他工作树，不覆盖用户已有修改。
- 保留五个命令：`build-scenes`、`evaluate-stations`、`collect-lastmile`、`build-bench`、`evaluate-bench`。
- 保留已有可用的实验选项、pick/open、控制 profile、记录方式和后端能力；非默认功能不等于冗余。
- 默认保持公开命令、配置和数据格式；内部接口可以简化，仓库内调用同步更新，不增加旧接口兼容壳。
- 模型算子和必要规划修正不因代码长就删除；先确认真实用途，再判断是否存在等价的更短实现。

## 3. 逐文件重点精简什么

| 对象 | 精简要求 |
|---|---|
| 重复逻辑 | 同一计算、转换、读取、写入或数据准备只保留必要的一次；先确认输入与语义确实相同 |
| 无用内容 | 删除无调用函数、无消费者的字段、无效参数、恒定分支和只服务已删除逻辑的代码 |
| 冗余校验 | 外部输入在合适边界检查必要条件；内部依赖明确约定，不层层重验、补缺或猜测类型 |
| 无效中转 | 删除纯转发包装、多余临时字典、重复对象转换和不增加含义的返回值拆装 |
| 过长流程 | 先删重复，再按清楚的步骤整理；独立职责确有必要时提取函数，不把长函数机械切段 |
| 过深嵌套 | 用提前返回、提前报错、`continue` 或小函数减少缩进，让正常路径顺着读下来 |
| 异常处理 | 在能作出实际处理的边界捕获；不重复包装、重复归因，不用默认结果掩盖程序错误 |
| 注释与命名 | 删除失效说明，改清楚变量含义；必要处补中文注释，不逐行翻译代码 |

不按关键词机械删除 `if`、`try`、`.get()`、数组复制或数值检查。是否冗余取决于实际调用、数据来源和实验用途。

### 3.1 减少代码，但不玩压行技巧

- 同等功能和清晰程度下，选择代码更少、状态更少、调用更直接的写法。
- 能直接计算就不引入通用策略、注册机制、管理类或额外数据层。
- 不用分号、超长表达式、多层三元表达式、复杂推导式或动态反射压缩行数。
- 保留合理空行和必要中文注释，不靠删除排版制造精简数字。
- 不预设必须删除的比例，但对每处改动都追问：能否用更少代码清楚完成同样的事？

### 3.2 函数和文件按职责拆，不增加阅读负担

- 只在独立步骤值得命名、逻辑确实复用或主流程明显更清楚时提取函数。
- 单次使用的函数也可以保留，但必须有清楚的职责，不能只是把几行代码藏起来。
- 文件混合多个独立职责时才拆文件，沿用现有领域目录，不为每个概念另建包。
- 不把单文件减掉的代码复制到其他位置，不增加纯转发文件或层层调用。
- 函数参数明确表达实际依赖；不为了减少参数数量塞进无边界的大字典或万能上下文。
- 拆分不是精简成果；应结合整个改动范围，判断总代码和阅读跳转是否真正减少。

### 3.3 中文注释解释“为什么”

- 重点说明单位、坐标系、动作含义、物理约束、必要算法修正和不直观的选择理由。
- 函数名已经说明的动作不再重复注释；简单函数不强制写长文档字符串。
- 参数和返回值只有在语义不明显时补充说明，不堆模板。
- 修改代码时同步修正附近过时注释，不全库机械翻译第三方模型说明。

## 4. 哪些内容不能为了少代码而删除

**我们写的是科研快速实验代码，不是安全审计或通用工程软件；必要检查服务实验正确性，不发展成重复验证体系。** 不新增文件指纹、封存协议、派生索引或通用校验框架，不反复处理基本不会出现的假想组合。

以下内容保留原有含义，可以精简表达，不能降低标准：

- 动作维度、单位、增量/绝对量、控制时序、关节限位及 position/native 的真实差异。
- 初始化和连续执行的边界；开始执行后不重置、传送或恢复状态。
- 场景编辑事务、静置、碰撞、支撑、初始化有效性与失败回滚。
- 抓取、开合、导航的真实判定，外部标定匹配与完整性，成功率分母和覆盖率。
- 一套实际执行轨迹及必要观测的对齐、部分执行记录、资源关闭和真实故障隔离。
- 任务失败、规划无解、超时、基础设施异常与未知结果的区分；共享服务故障的停批行为。
- 原始资产和既有结果只读，新试验不覆盖旧结果，不补造轨迹或成功证据。

没有样本、无路径、无合格配对、部分执行等是实际实验状态，不属于可以一并删掉的罕见情况。必要检查保留一处即可；不为了少一个判断而隐藏真实负结果。

## 5. 后续实施方式

1. **先读再改。** 检查工作树已有修改，阅读目标文件、直接调用方和相关测试，明确保留功能。
2. **先做减法。** 删除无用逻辑和数据准备，合并语义一致的重复处理，减少无效中转。
3. **再理顺表达。** 减少嵌套，明确变量与资源责任，必要时拆函数或文件，补关键中文注释。
4. **同步直接依赖。** 更新受影响的调用、测试和必要说明，不保留旧内部接口包装。
5. **做对应验证。** 先运行相关测试；累计修改后运行完整离线回归。涉及真实控制、规划、模型或记录行为时，按改动安排有界真实检查。
6. **简短记录后继续。** 说明删了什么、保留什么、验证到哪里；没有明确收益的候选停止改写。

每次处理一个文件或一组紧密相关文件，不同时铺开全库重构。已有测试优先复用，只补实际语义缺口，不穷举低价值异常组合。真实实验需要 GPU 时先看 0–7 卡的利用率和显存，显式选卡；文档整理不占卡。

## 6. 验收与交付

- **功能保持：** 原有有效功能和选项仍在，实验判定、数据含义和执行约束不变。
- **实现更少：** 无用逻辑确实删除，重复实现确实合并，不以移动、禁用或压缩排版代替精简。
- **总代码更少：** 统计包含提取后的文件及新增辅助实现，不能把拆出代码算作删除；源码和测试的变化分开说明。
- **阅读更直接：** 主流程清楚，嵌套更少，名称准确，中文注释解释关键约束，没有新增无效抽象。
- **验证真实：** 相关回归通过；已有问题、新问题、跳过项与未验证项分别说明。不用删核心断言换取通过。
- **报告精简：** 后续实施只维护一份简短结果报告，列出主要修改、代码量变化、实际验证和剩余限制，不为每个函数另建附件。

对算法和必要语义已经直接的文件，不为多删几行继续制造抽象。局部整理若增加代码，需有明确的可读性或正确性收益，不能以此回避整体减量目标。

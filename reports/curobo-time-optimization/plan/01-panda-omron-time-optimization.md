**先完成流程加速实现和软件回归，再统一全量实验。** 主结果是 PandaOmron 各初始点的 cuRobo 实际执行成功率，每点固定 3 次。允许重新组织准备、规划、执行调度与记录，不要求保留旧流程顺序。CUDA Graph 不纳入本轮。

本轮实现包固定为：局部任务构建与检查去重、每站位公共准备、静态资源常驻、同站位三次闭爪前 batch、**动态使用 1 个或多个常驻 GPU 规划进程＋最多 60 个 CPU trial 执行进程**，以及支持离线视频的数值记录。同站位三次 batch 规划完成后，三条可执行轨迹分别进入 CPU 池并行推进；闭爪后通过原 trial 的实测状态继续请求规划。GPU 物理后端迁移、CUDA Graph、异步视觉系统不在本轮。

本文统一规定实现顺序、资源池与运行链路的耦合；[并行专项](02-parallel-execution.md)保留机器资源采样、方案比较和依据。其中 6 张空闲卡是当时的配置示例，实际 GPU 进程数不固定为 6，也不要求所有可用卡都参加运行。

| 阶段 | 范围 | 运行要求 |
|---|---|---|

| 最终全量 | 固定的 100 个 val 来源场景，Case1、Case2、Case3，默认每任务/Case 1 个变体 | 提前提交时长预估；覆盖实际合格目标和 accepted 派生场景的全部最终点，每点 3 次；缺项/rejected 保留原因 |

100 个来源场景可能生成多个派生场景，实际数量由 Case、合格 pick/open 目标与构建结果决定；不是固定 100 条标定任务。最终输入清单和每房目标数在配方中预先明确，不能把 `Cup_30` 限制复制到其他房屋。全部实现须同时处理 Case1/Case2 pick 与 Case3 open 的阶段规划、动态碰撞世界和数值记录；首阶段的任务范围不缩减实现范围。

## 1. 目标流程与共享边界

```text
build-scenes
  来源任务元数据一次解析 → 每任务固定局部模型
  → 候选物理检查与增强事务，复用未变化模型的已有检查
  → 全部候选完成最终物理资格 → 覆盖保留最多 20 点
  → 最终点可见性记录 → 冻结新场景

evaluate-stations
  父进程确定任务/seed/rollout → 根据所选 GPU 启动 G≥1 个常驻规划进程
  → 动态领取站位，初始化与真实静置一次 → 保存操作初态
  → 同站位 3 个独立 seed 组成闭爪前 batch → 发给空闲 GPU 规划进程
  → 按 trial 拆分计划 → 3 条可执行轨迹分别进入 CPU 执行池（总上限 60）
  → 各自真实接近/闭爪 → 携各自实测状态请求 GPU 后续规划
  → 原 CPU 实例继续抬起/保持和判定 → 各自保存规划/实测轨迹
  → 父进程唯一写 trials.jsonl → 各点成功率与回放资料完整性
```

| 可以共用 | 必须独立 |
|---|---|
| 固定场景文件、来源元数据、站位准备初态、候选几何；进程内只读 MuJoCo model、静态网格和兼容规划资源 | 进程内的模型对象、每 trial 的 MjData/控制状态/随机流、规划输出、实际轨迹、任务 monitor、结果与日志归属 |

不同 spawn 进程各自加载并缓存模型，不直接共享或传递 Python Simulation/MjModel；同一执行进程内可复用只读 model，但每条独立 trial 新建 Simulation/MjData。GPU 进程拥有 cuRobo 与 CUDA，CPU 执行进程拥有真实仿真、控制、判定和 recorder，父进程拥有任务身份与主结果。

复用公共输入，不复用任务成败。三个 seed 分别真实求解，有可执行轨迹的 trial 各自推进物理；规划无解保留对应结果，不补造执行步。不能将一个成功计划或一次 no-solution 复制成三行结果。

完整三次结果按固定分组输出：低率为 0/3、1/3，高率仅 3/3，2/3 为中间组。Panda 有效配置显式保存 `lastmile_low=0.3333333333333333`、`lastmile_high=1.0`，沿用含等号比较；不完整标定不进入正式配对。同步匹配的 Panda 标定、采集和困难配对配置，不全局覆盖 RBY 或历史运行的阈值。

## 2. build-scenes：合并数据流，减少重复构建

### 2.1 单次解析与局部任务模型

房屋元数据、目标候选和支撑关系解析一次，发现记录直接传给资格检查，避免在相同模型上再次 discover。按既有空间覆盖规则选择目标与补选，不改变任务选择规则来增加容易场景比例。

每任务生成一个固定局部模型，覆盖站位圆盘、局部底盘运动、机器人全身/手臂扫及范围及余量。保留目标、完整支撑、相关地板/墙/门、附近障碍和必要视觉遮挡；按完整对象或结构子树保留，不按不同站位分别删障碍。原 XML/资产只读，派生模型走现有 `scenes/loading/` 和构建流程，不另建构建器。

在局部模型上完成增强、真实静置、源场景影响和最终站位校验。新模型会改变任务输入，统一保存新模型与有效配置并重新标定；不把旧整屋结果当作新标签，也不声称裁剪前后逐条结果必然一致。

### 2.2 合并候选检查，推迟非必要渲染

- 同一模型、任务和采样配置下，发现预筛已检查的候选结果直接用于后续资格扫描；继续检查剩余候选，最终仍覆盖全部候选，不为取得 20 点而提前截断。
- 支撑查询、地面/几何索引和不变的机器人分类在任务/模型范围准备一次。模型或几何改变后重算受影响检查，不机械沿用增强前结果。
- 可见性不决定资格，因此候选物理筛选不渲染；覆盖选出最终站位后统一记录这些点的可见性。全部候选仍保存物理合法性与排除原因。
- 构建会话已有按有序资产组合缓存最多 4 个编译模型；直接复用，减少同组合重复资产解析和编译。每次候选位姿、静置和源场景影响仍走真实事务。
- 放置搜索先做廉价几何排除，再进入编译/物理验证；无法完成必需数量或耗尽既定预算就记 rejected，不通过省略支撑/碰撞检查接受场景。Panda 当前为 2 次物理验证、180 s 变体预算。
- 修复秒级临时目录冲突；按房屋/任务分配独立构建工作单元，worker 常驻可复用资源，统一写当前主记录。优先沿用既有分层和事务，不增加另一套分片索引。

## 3. 每站位公共准备一次

当前 Panda 每 trial 先静置 1 s，随后 `sim.started=True` 导致完整 planner 缓存不命中。把这一重复准备移到站位层：

1. 从场景基线新建 preparation 实例，初始化该站位，真实静置既定时长并做必要健康/初态检查；此阶段不做三次重复操作，也不生成三份视觉记录。
2. 取得准备后的完整积分状态、控制状态、物理时钟余数和实际站位/目标姿态，作为该点统一的操作初态。公共准备失败单独记录，不伪造三次操作失败。
3. 三个 trial 各自新建 Simulation/MjData，初始化阶段复制该初态，随后各自规划与执行；不再次按原始站位摆位而覆盖准备后状态，不再次静置。
4. 准备实例只提供只读状态；开始执行的 trial 不恢复、不重置、不传送。当前 `freeze()` 禁止在 begin 后保存场景，不通过改回 `started=False` 绕过；在准备/克隆职责内传递完整状态，创建新的未开始实例。

记录请求站位和准备后实际底盘位姿。准备后若该点已不满足初态条件，记录无效原因；成功率对应明确记录的准备后操作初态，而不是未经记录的状态替换。相同初态的三个规划 seed 用来测执行系统随机性，不声称测到了三种独立物理扰动。

## 4. 静态资源常驻与同站位三次 batch

### 4.1 先分离公共资源与 trial 绑定

CPU 执行进程缓存所属场景的模型；GPU 规划进程缓存兼容的机器人解析、固定碰撞几何、目标局部坐标球拟合及 solver 资源。同站位候选在公共准备后计算一次，三个相同初态复用这些候选，每次 trial 仍以自己的随机流独立求解。

在现有 `planning/curobo_v2.py` 内拆清静态资源、站位规划状态与 trial 回调/日志，复用 solver 分配和预热资源。初态、目标/障碍位姿、锁定关节、接触许可、附着、seed 和 sim 引用按实际试验绑定。站位结束释放不再使用的资源，不缓存所有站位的重型对象。

CUDA Graph 保持关闭；资源复用不依赖其捕获。闭爪后三个实测状态通常不同，继续按各自状态构造/更新规划模型，先保留当前可靠的独立闭爪后路径。

### 4.2 batch 限定为同站位闭爪前

三个 trial 共用相同操作初态、参考底盘坐标、锁定配置、目标与碰撞世界，先把这三次闭爪前规划组织为一个小 batch。使用共享世界模式 `multi_env=False`，保留可用 PRM 搜索；不先做跨站位多世界或闭爪后多状态的通用批量系统。

批量规划输出按 trial 拆回原 attempt，三条可执行轨迹分别进入 CPU 池，继续调用现有 runtime 跟踪与任务判定。有空闲 slot 就立即执行，不等待其他站位凑满；CPU 容量不足时进入待执行队列。某个 batch slot 规划失败只属于该 trial，不占物理 slot，其他 trial 正常分发；没有实际执行就不生成物理轨迹行。

闭爪后三次实测状态可能不同，分别向 GPU 池请求后续规划。CPU worker 在等待响应时保留当前 Simulation 和模拟时间，响应返回后由同一个实例继续；其他 CPU worker 正常推进。单 GPU 时这些查询排队，多 GPU 时交给空闲规划进程，物理执行并发不绑定 GPU 数量。该拆分已实现，真实验收与限制见交付报告。

本地参考为主工作区 `reference_repos/curobo`，项目固定 v0.8.0。从本 worktree 查看固定版本：

```bash
git -C ../../reference_repos/curobo show v0.8.0:curobo/_src/motion/motion_planner_batch.py
git -C ../../reference_repos/curobo show v0.8.0:curobo/_src/motion/motion_planner_cfg.py
```

| 本地 v0.8.0 源码事实 | 本轮适配职责 |
|---|---|
| `BatchMotionPlanner` 支持共享世界，`max_batch_size` 指定容量 | 固定同站位三个问题；slot 与 trial 显式对应 |
| batch `plan_pose` 有重试循环，默认 1；单问题默认 5 | 显式传递原有预算；不采用文件顶部已过时的“no retries”描述 |
| batch `plan_grasp` 未暴露 `max_attempts`，内部调用各阶段 `plan_pose` | 在项目规划适配中传递各阶段预算、接触状态和诊断，不能只改构造开关 |
| v0.8.0 默认 IK/TrajOpt seeds 为 32/4 | 项目继续显式配置；不采用参考 HEAD 中较新的 batch 默认 16/2 |
| 原生 `reset_seed()` 不接受新 seed，单个 planner 配置不是逐 slot seed API | 项目生成/绑定每 trial 的随机流和 seed 张量，再组合进入批量求解；不能只重复同一随机问题 |
| 原生失败 slot 可使用占位目标维持批量计算 | 占位轨迹不进入执行、轨迹记录或任务成功判定 |

参考 HEAD 比 v0.8.0 更新，本轮不升级依赖。批量随机流不要求与旧串行版逐轨迹一致，但必须与 trial seed 稳定绑定，三个 trial 有各自随机样本；排队和 slot 排列不能变成未记录的随机变量。必要的 seed/状态/阶段适配是本轮实现工作，不声称原生接口已经直接支持所有项目语义。

## 5. 成功率专用轻量记录与站位并行

### 5.1 在线保存轨迹，离线生成视频

`evaluate-stations` 的成功率模式关闭逐帧 RGB、深度和视频，不创建无消费者的 renderer/编码器。复用现有 recorder，保存原始 `trials.jsonl`、规划轨迹、实际执行状态、seed、操作初态、任务证据及离线视频依赖；不另起记录链路或复制一套 trial。轻量化对象是在线渲染和编码，数值记录必须足以还原视频。

| 保存内容 | 最小实现与职责 |
|---|---|
| 规划轨迹 | 复用 `grasp_result.json` 中已有分段轨迹，补齐闭爪后 pose 规划输出；保存关节名、参考底盘变换、控制时间间隔、阶段与 trial。batch 结果拆分后分别保存 |
| 实际执行轨迹 | 扩展现有 `trajectory.npz`：初始状态加每个实际控制步后的整场景积分状态、`state_spec`、时间戳、实际/请求动作与阶段，包含控制恢复所需信息。沿用一次执行回调记录，不另录重复轨迹 |
| 场景与资产 | 每场景保留固定模型、版本、可读取的 mesh/texture 引用；站位保存公共准备初态，trial 指向既有模型和准备状态，不依赖会被清理的临时目录 |
| 相机与时序 | 保存所属 profile 的相机名称、内外参/位姿、图像尺寸与控制频率；存在运行时相机变化时同步保存相应参数。播放采用实测时间戳，不用 planner dt 替代实际执行时间 |

实施前 recorder 已保存整场景 `qpos/qvel/ctrl/time`，但尚未完整保存每帧积分状态和离线视频依赖；实施前规划输出也未完整覆盖所有闭爪后单段查询。本轮已补齐这些实际缺项，不将现有 NPZ 直接宣称为已保证回放。全部有执行步的成功/失败/超时 trial 均保留资料，帧数对应初始帧及实际执行步；无执行只保留真实初态和规划事实。

离线渲染入口放在现有 `data/rendering/`，作为按 run/rollout 选择的后处理，不新增第六个顶层命令。加载保存的模型，使用独立 MjData 逐帧设置实测状态并 `mj_forward`，按所选相机渲染和编码；不调用 planner、不做 `mj_step`，不恢复已经开始的执行仿真。视频注明来源为实测状态回放，原成功率和任务证据保持不变。

规划动画与执行回放分别标明来源。只有计划关节序列无法描述抓取滑移、掉落及其他物体运动，所以实际执行视频以完整实测状态为准。E01 的像素末位差异保留为已知边界；本轮验收帧时序、机器人/目标/其他物体状态及相机正确，不直接升级为训练像素一致性结论。

任务 monitor 与物理健康检查仍按所属 profile 的实际子步运行。保留现有遥测精简；完整 physics 文本 trace 按显式调试需求开启，关闭时不构造无用文本行。每步采样不变，但逐步落盘和 JSON 重写可以在内存积累后按 trial 写入。

回放资料完整性纳入录制检查，缺少状态或模型依赖就明确标记记录不完整。纯数值标定成功不等于视觉示教完整；按需生成视频或训练观测后，再检查对应用途的模态完整性。离线视频不提供新任务成败，也不能自动使原轨迹成为完整视觉训练样本。

### 5.2 动态 GPU 规划池与独立 CPU 执行池

“动态使用 1 个或多个”按每次运行显式选择的 GPU 列表建立规划池：`G=len(gpu_ids)≥1`，一张所选卡启动一个常驻进程，不固定卡号、进程数或六卡配置。运行中任务动态分配，进程常驻至本次 run 收尾；本轮不增加后台 GPU 探测或自动抢占其他作业的资源管理器。

| 资源 | 组织方式 | 与其他阶段的耦合 |
|---|---|---|
| GPU 规划池 | 所选 GPU 各 1 个进程，每进程同一时刻 1 个 native 查询 | 服务多个站位与 trial，跨场景保持常驻；一次 batch 对应同站位三个 seed |
| CPU 执行池 | 可配置上限 C，`1≤C≤60`，按剩余 CPU/内存和任务数实际使用 | 一进程一条活动试验；C 不要求等于 G 或 G×3，单卡也可供给多个 CPU worker |
| 站位准备 | 独立的有界准备任务，当前机器最多 12 个作为初始配置 | 准备初态只做一次；待规划/待执行任务达到调度容量后暂停领取新站位，避免提前准备整个数据集 |
| 父进程 | 全局站位与 trial 队列、唯一 ID 分配、主结果写入 | 跨已构建场景填补空闲 slot；按站位齐全情况汇总，不设置逐场景完成屏障 |

单场景最多 20 点共 60 个 trial，多场景共用最多 60 个活动执行 slot；不因场景数增加无限扩展池。一个 trial 完成就发下一条，不等待同站位其他 trial。正式任务少于进程上限时按实际任务量使用，60 是容量而不是必须同时启动/推进的试验数。

GPU 调度在空闲进程中优先复用相同模型/配置，空闲资源不足则排队；已有执行正在等待的闭爪后查询优先于新站位 batch，同优先级按入队顺序。GPU 进程返回计划后立即领取新查询，不等待对应物理轨迹完成。单 GPU 沿用同样协议，减少 GPU 数量只改变排队与吞吐，不改变三次试验数、搜索预算或统计规则。

使用 spawn，GPU 子进程设置可见设备后才初始化 CUDA；CPU 执行进程不初始化 CUDA。限制每进程数值库内部线程，优先按物理核分配 CPU，结合实际 GPU/CPU NUMA 拓扑安排模型加载和内存；内存充足时使用进程私有模型，先不增加复杂共享内存结构。具体采样和核预算见[并行专项](02-parallel-execution.md)。

### 5.3 规划与执行之间传什么

| 边界 | 必要内容与职责 |
|---|---|
| 公共准备→首次 batch | 固定模型/配置引用、准备后完整初态、参考底盘坐标、候选、三个 trial 的 seed/身份与预算 |
| GPU→CPU | 按 trial 拆分的阶段计划、关节名、参考变换、时间间隔、有效点数、规划状态及耗时；失败 slot 不产生执行任务 |
| CPU→GPU 后续查询 | 同一 rollout 的实测场景状态、当前阶段、实测锁定关节/附着信息、剩余规划与活跃时间预算 |
| CPU→父进程 | 原任务判定、终止原因、录制完整性、规划/执行耗时与轨迹引用；不通过主结果队列搬运整条轨迹 |

GPU 进程在非执行的规划视图中使用请求状态，不能对 CPU 活动仿真恢复快照或设置位姿。跨进程传数值状态和固定输入引用，不传 runtime context、recorder、Python 回调或 CUDA tensor；GPU 阶段日志按 trial/查询号返回，由原 attempt 接续保存。

trial 逻辑身份和预算在第一次规划请求前建立，即使 CPU 执行器尚未接手也保留首次规划耗时。进入物理阶段后由原执行上下文接续累计，闭爪后查询继续使用剩余预算；不能在每次 GPU/CPU 转交时重置计时或规划次数。排队时间单列，原生 batch 的完整计算耗时计入每个参与 trial。

各 CPU worker 通过原执行回调记录一次实测轨迹，写自己的 attempt 目录；父进程唯一写 `trials.jsonl`。GPU 资源故障继续按共享故障停批处理，不自动把故障查询换卡后补成任务失败；已执行结果保留。任务无解、执行失败和记录错误沿用原分类。

### 5.4 构建、标定和视频使用同一资源约定

先完成场景库构建，再对 accepted 场景统一标定，不读取未完成场景库。构建按房屋/任务/变体独立并行，保留变体内事务顺序；全候选物理结果汇集后才覆盖选点，父进程唯一写 `scenes.jsonl`。

标定主循环不渲染，GPU 池专注规划；回放源数据写完才算标定记录就绪。标定结束后按需用实际选择的渲染 GPU 建立 1 个或多个 renderer 进程，EGL 编号显式匹配，一条视频只有一个写入者，渲染与编码耗时单列。渲染 GPU 数不固定等于 G，CPU 执行进程无需创建 EGL renderer。

## 6. 实现、软件检查与统一全量实验

具体工作包、前置依赖、修改位置、交付和当前执行状态见[执行计划表 P00–P14](03-execution-schedule.md)。下表保留阶段目标与统一验收口径。

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| 实现 1 | Panda 每点 3 次、低阈值 1/3 / 高阈值 1.0、规划/实测轨迹保存、离线视频入口、公共状态与协议定义 | 低率含 0/3、1/3，高率仅 3/3；回放依赖齐全，旧通用/RBY 配置保留 |
| 实现 2 | 局部模型、合并发现/资格数据流、几何缓存、渲染后移、构建任务调度 | 全候选物理资格及增强约束保留；同模型不重复做相同工作 |
| 实现 3 | 同站位公共准备、规划静态资源拆分、三次闭爪前 batch | 逐 trial 初态/seed/计划/日志映射明确；闭爪后按各自实测状态查询 |
| 实现 4 | G≥1 个常驻 GPU 进程、最多 60 个 CPU 执行进程、跨场景队列和预算接续 | 同站位三条可执行轨迹分别推进；单卡和多卡使用同一链路，身份/预算/结果不随调度重置 |
| 软件检查 | 相关测试后跑全套回归；用现有简化模型/fixture 检查 G=1/多进程调度、batch 映射、状态与预算传递、轨迹离线渲染及结果统计 | 无串 trial、重复执行或漏记首次规划；回放状态/时间戳/相机对应，不冒充真实 GPU 验收 |
| 初步正式全量 | 全部实现完成后，构建并完整标定 val103 / Cup_30 / Case2；按需回放该轮实际执行 | 单任务原始结果、覆盖、成功率、回放资料和各阶段实测墙钟齐全 |
| 最终全量提前估时 | 用初步阶段实测分项与固定 100 个来源的任务清单估计最终批次 | 运行前给出正常/保守情景、资源配置和未测 Case 的假设，不增加抽点试验 |
| 最终全量 | 对 100 个 val 来源执行全部 Case 的构建、accepted 场景标定和按需回放 | 各 Case 来源/构建/站位覆盖、原始结果、总墙钟及预计/实际差异明确 |

实现过程中不跑 Panda 基线、少量点位预实验或每项优化的性能 A/B。软件检查不要求先产生真实成功示教；实际 CUDA/cuRobo 求解、物理执行、资源争用和最终性能在统一全量实验中验收，发生实际错误再针对修复。全量指选定输入集合和所有 accepted 场景的最终点集，不把调试用 `max-trials` 子集当最终结果。

正式计时包含加载、公共准备、调度和收尾；分项用现有 diagnostics 补充，避免把嵌套计时重复相加。新协议将 `attempt_timeout_s=300` 定义为每 trial 的活跃操作软预算，计入其规划调用和真实物理执行，公共准备、排队和结果写入单列。批量规划的整次调用耗时计入每个参与 trial，不除以 batch 大小；原始墙钟同时保留。这是明确的预算口径更新，不声称与旧版含记录等待的超时标签一致。

单场景满 20×3 的成功率结果及可回放资料就绪 ≤30 min 目标已由首阶段单任务实测达成，数值轨迹和模型引用的保存耗时计入；取消“成功训练图像全部就绪”前提。按需离线生成视频的时间单列，另报 build 时间和同批构建→标定总时间。没有同配置旧基线时只报告新流程实测耗时、完整性和结果，不从历史跨配置数据计算加速倍数。

## 7. 最终 100 个来源场景的提前估时

首阶段正式运行结束后、最终批次启动前，利用该轮原始结果与分项耗时完成估算，不额外运行少量站位或性能 A/B。

1. 固定 100 个 val 来源清单、目标选择规则/数量、Case1–3 和每任务变体数，统计各 Case 的计划构建单元；原来源缺少合格任务时保留缺项。按现有实现，Case1/Case2 为 pick 目标×变体数，Case3 为 open 目标数。
2. 使用首阶段实测的准备、batch/闭爪后规划、实际物理执行和保存成本，结合最终场景模型/候选规模构造正常及保守情景。Case1 增强与 Case3 open 的未测成本单列假设和预算，不当作已测，也不置零。
3. 按计划 G、CPU 上限 C 和准备/构建并发做调度估算；规划与执行可重叠，不能将首阶段墙钟简单乘 100，也不能在已经并行的耗时上再除一次 GPU 数。
4. 分别报告构建、标定、数值资料写入/收尾和按需视频时间；首阶段轨迹用于估算的分项已含记录时，避免重复相加。给出假设、输入规模、正常/保守预计时间，不将其写成保证完成时间。
5. 最终场景库构建完成后，在标定开始前按真实 accepted 派生场景和最终站位数更新剩余标定预计时间：`N_trial=3×Σ N_station(scene)`。最终结果报告预计与实际的差异及原因。

例如，仅在每个来源恰好选出 1 个 pick 和 1 个 open 目标、每 Case 1 个变体且全部构建通过时，100 个来源才对应 300 个派生场景、最多 18,000 个 trial。这是条件数量示例，不是已确定产出或耗时结论；正式估算按实际配方和任务清单计算。

## 依赖与推进安排

主要执行链为 **P00 → P02 → P05 → P06 → P07 → P08 → P10 → P11 → P12 → P13 → P14**。P01 环境准备、P03→P04 构建支线、P09 回放支线可在各自依赖满足后推进，统一在 P10 汇合。三类 Case 的加速实现都在 P11 前完成，不把 Case1/Case3 的实现推迟到最终运行前。软件检查随对应实现完成，完整软件回归在 P11 集中执行。

P00 先明确状态/身份/预算和资源字段，P02 落地其最小结构，后续模块按此对接；不增加通用消息框架或第二套记录协议。P07/P08 是现有 planning、runtime、workflows 职责的拆分，公共准备、GPU 视图、CPU 活动仿真与 recorder 的归属必须能直接对应主方案。

以下列出会影响汇合的具体条件：

- P03 产出的模型及资产引用必须长期可读，P09 离线渲染不能依赖构建临时目录。
- P05 的操作初态由 P06/P07 首次规划和 P08 实际执行共同使用，不能三处分别摆位/静置。
- P07 返回的每个 batch slot 必须有原 trial 身份；P08 从首次规划开始接续预算，不能新建上下文后漏计规划时间。
- P02/P09 的回放资料完整性参与 P08/P10 的记录状态；数值标定成功不自动代表视觉示教模态完整。

## P12 首阶段正式全量的执行顺序

1. **确定本次资源与输出。** 根据当时占用显式选 1 张或多张 GPU，设置 CPU 执行上限和准备并发，创建新 run；使用 position-v1、val103/Cup_30/Case2、1 个变体。
2. **完整构建场景库。** 保存全部构建结果与 rejected 原因，等待 `scenes.jsonl` 和 accepted 场景文件写完。
3. **统一标定 accepted 集合。** 所有最终站位各 3 次，GPU batch 规划后分别进入 CPU 池，闭爪后按原实例继续；原始 trial 是成功率唯一来源。
4. **完成数值结果与回放资料收尾。** 核对计划覆盖、有效分母、录制完整性与可读模型引用，报告每点成功数/有效数和未完成原因。低率为 0/3、1/3，高率仅 3/3，2/3 为中间组。
5. **按需生成该轮视频并交付。** 有成功执行时检查成功轨迹，有失败/超时时检查相应轨迹；缺少某类真实结果就如实注明。回放不改变标签，不用重跑制造所缺类别。

统一实验不是单独增加前置 smoke。正式运行中出现依赖、初始化、GPU、规划/仿真或记录错误时针对实际错误修复；已有结果只读，新尝试使用新 run/attempt，未执行部分保留真实原因，不改写成任务失败。

## P13–P14 最终全量的估时与执行顺序

1. **最终运行前完成预估。** 使用 P12 的实际准备、规划、执行和写入成本，加上固定 100 个来源场景的目标清单/Case 数量，按计划 G/C、构建并发模拟调度；给出正常与保守情景。Case1 增强和 Case3 open 成本仍属外推，明确所用规模/预算假设，不将其冒充已测时间。
2. **分别说明各阶段时间。** 构建、标定与数值资料完成、事后按需视频分列；区分活跃计算与排队，避免把首阶段已并行的墙钟简单乘 100 或再次除以 GPU 数。该估算不包含额外 Panda 抽点试验。
3. **完整构建 100 来源三类 Case。** 按正式配方发现 pick/open，不沿用其他房屋的 Cup_30 目标限定；保留无合格任务、rejected 和错误。100 来源不保证 300 个 accepted 场景。
4. **标定前更新剩余预计时间。** 按实际 accepted 派生场景和最终站位数量，确定 `N_trial=3×Σ N_station`；结合 P12 的阶段耗时及各 Case 假设更新剩余标定时间，再启动全部最终点各 3 次的标定。
5. **结果与预计差异一同交付。** 按 Case 报覆盖、原始有效率、实际资源/墙钟和缺失原因；用该轮实测轨迹按需回放视频，说明估时误差来自哪里。

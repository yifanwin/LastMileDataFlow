# 2026-10-12：程序化障碍物 Case1 / Case2 对抓取难度的影响（cuRobo vs MolmoBot VLA）

分析对象：同一任务 `val_103` / `Cup_30`（`pick-bf2b057e9916`，实例
`cup_ff2c6ab62ccb690220c97cdcfeb658c5_1_0_2`）下，**放置障碍物前**的密集站位基线与
**加入程序化障碍物后**的 Case1 / Case2 运行，以及一次 S0009→S0023 的导航后抓取实验。

**结论一句话**：在本目标上，障碍物增强目前不是通过“让抓取本身更难”起作用的，
而是通过**把半数以上格点站位判为初始碰撞、把可用站位集合整体换掉**来起作用；
两个后端都表现为“站位被吃掉”，cuRobo 死在规划、VLA 死在策略步数预算。

## 2. 不是“抓取更难”，而是“站位集合被换掉”

![图 5 站位集合与距离](figures/fig5-station-set-and-distance.png)

把基线的 13 个有效坐标逐个映射回 Case：

- **Case2**：13/13 坐标仍然有效且可测，平均成功率 **63.1%**，与基线的 64.6% 几乎相同；
  13 个坐标里只有 S0032/S0033 掉到 0/5、S0034 掉到 3/5，其余基本保持。
  → Case2 的 60.3% ≈ 基线的 64.6%，**成功率的差主要来自新加入的 45 个坐标（60.3% 的整体里，
  这 45 个点贡献了 225 次试验）**，而不是原站位被削弱。
- **Case1**：只有 **5/13** 坐标还活着，其余 8 个被判为与新增椅子碰撞（碰撞对是
  `procedural_obstacle_0 ↔ robot_0/base`）。这 8 个恰好是**离目标 0.44–0.70 m 的最近一圈**（S0003、S0008、
  S0009、S0015、S0016、S0022、S0023、S0029），也就是基线里表现最好的那一档。
  剩下 5 个可测坐标的成功率是 40.0%，看似下滑，但这 5 个已全是较远的点，样本只有 25 次。

![图 2 空间成功率热力图](figures/fig2-success-heatmaps.png)

图 2 把 10 个 run 的 `success_heatmap.npz` 用统一色标重绘（未使用各 run 自带的 PNG）：
Case1 行能看到左侧最近的一整片区域被红虚线框（新增椅子包围盒）覆盖后变成空白/深灰，
有效站位被推到外围；Case2 行的色场与基线形态相近，只是多了一圈近距离格点。

![图 3 失败模式构成](figures/fig3-failure-decomposition.png)

**图 3** 说明两个后端的失败机制完全分离：

- cuRobo：失败几乎全是规划阶段。Case1+终选 220 次终结试验中 142 次 `planning_no_solution`（65%）
  + 19 次执行期物理失败；Case2+终选 390 次里 109 次无解 + 47 次执行失败。
  具体到状态量：Case1 的 83 次 `PlanningFailure` 里，全部 258 次 solver 调用都带着
  `constraints/head_fov_endpoint` 且该约束项代价 > 0（基线 76/76 亦然）——**head FOV 硬约束是规划失败
  的常驻卖方**，本次没有做关闭 FOV 的消融，因此不能把它单独归因为障碍物的责任，只能说明
  “站位被推到更差视角后，规划器要同时满足 FOV + 新障碍物回避，更容易无解”。
- VLA：失败 100% 是 `policy_step_budget_exhausted`（跑满 400 步 ≈ 40 s 仿真、约 240 s 墙钟，
  从未达到物理抬升判据），没有一次是规划问题。Case1+终选 220 次里 197 次预算耗尽、23 次成功。

## 3. E02：S0009 → S0023 导航后抓取

![图 4 E02 导航后抓取](figures/fig4-e02-transfer.png)

同一仿真实例内从 S0009 真实导航约 **0.444 m** 到 S0023 后再调用 MolmoBot（不重置、不传送、不恢复快照）：

| 设置 | 抓取成功 | 成功率 |
|---|---:|---:|
| S0009 原地操作（基线 5 次） | 0/5 | 0% |
| **S0009 导航 → S0023 后操作（E02）** | **3/5** | **60%** |
| S0023 原地操作（基线 5 次） | 4/5 | 80% |

- 导航 5/5 到达（位置误差约 0.153 mm、偏航误差 1.6e-8 rad，50 个控制周期 = 5.0 s，约 0.444 m）。
- 3 次成功在 11–14 s 内把杯子抬升 11.6–13.9 cm；2 次失败跑满 400 步、抬升停在 0.6 / 9.0 cm，
  且未形成持握（成功判据 = 物理抬升 + 手指接触 + 持握）。
- **边界**：保持 S0009 的头部等初态、到达后不重设为 S0023 原地初态，因此这不是“只改底盘位置”的严格因果对照；
  另外 A\* 网格因 0.4435 m 包围圆与桌子支撑包络膨胀把两端点都标为 blocked，实际走的是
  101 点静态碰撞检查过的直线连接器（静态采样 ≠ 连续扫掠证明）。n=5 也不足以断言导航后
  优于/劣于原地——只能说“导航链路在这个点位对上闭合了，剩余不确定性在到达后的策略稳定性”。

## 4. 对 Case 设计的直接含义

1. **“更密集的站位”这一改动在 Case1 上是自我抵消的。** 间距减半把候选点 ×4.4，
   但新增椅子一次性把最近一圈（也是基线成功率最高的一圈）全部判为初始碰撞；
   净余 24 个点里 19 个是新坐标。要测“障碍物是否让抓取更难”，Case1 当前布局**无法回答**——
   它比的是两批不同的站位。
2. **Case2 是更干净的“同场景加料”。** 13 个原坐标全部保持且成功率不变，整体 60.3% 是对
   58 个坐标的平均，能反映“在更拥挤的桌面上、从更多角度抓取”的难度画像。
   这也是为什么 Case2 更像“密集站位增强”，Case1 更像“局部可达区域消失”。
3. **两后端都不能互相做消融对照。** cuRobo 与 VLA 在基线上就差 64.6% vs 18.5%，
   差异来自算法而非障碍物；Case 之间的差才是本次要读的量。
4. **下一次要回答的问题**：若目标仍是“障碍物是否提高抓取难度”，需要
   (a) 关闭 `head_fov_enabled` 或做开关消融，把 FOV 与新障碍物的贡献分开；
   (b) 让 VLA 的两组 Case2 真正跑完 20 点 ×5（本次中断在 3 个站位）；
   (c) 在 Case1 上补一份“椅子放在远处、不覆盖最近一圈”的变体，作为位置对照。

## 5. 未做与不可结论

- **不做**跨 run 的总体成功率推断：Case1/2 各只有 1 个变体（v000 / v001）真的跑了任务，
  构造阶段的 5 个随机变体没有对应任务结果；跑完的 run 也只有 5 种子级别的重复，不做误差棒或显著性。
- **不能**把 `planning_no_solution` 读成“物理不可达”（诊断自带 `finite_budget_not_impossibility: true`）；
  也不能把 head FOV 的普遍违规读成“FOV 是本次差异的唯一原因”（无消融）。
- VLA 两个 Case2 run 的 11–14 次试验**不参与**任何成功率比较，只作为中断证据记录。
- 本报告只读既有 `outputs/`，未重跑仿真、未修改任何 run、未改动源码；图由 `scripts/` 下脚本从原始数组重绘。

## 一、先明确阶段二交付什么

阶段二的输出不应只是修改后的 MJCF 或截图，而应是一个 **任务候选包 `TaskCandidate`**：

> 在指定场景中，对哪个目标、从什么机器人初态、执行什么操作；场景满足哪些构建要求；还需要阶段三验证哪些操作性质。

交付分为三层：

| 层次 | 阶段二需要完成的内容 | 不能提前宣称的内容 |
|---|---|---|
| 场景有效 | 正确支撑、稳定、无严重穿模、机器人初态有效 | 几何正常就一定可抓取 |
| 构建要求 | 距离、操作侧、把手方向、障碍位置等符合配置 | 已经形成真实操作困难 |
| 下游交接 | 模型与初态可恢复，任务和验证协议明确 | 原地失败、换站位成功、把手抓取成功 |

沿用现有三个独立结论，另加逐项构建要求：

- `scene_validity`：通过本阶段规定范围的检查。
- `build_requirements`：所有必需构建要求通过。
- `case_condition`：没有机器人试验证据时为 `unknown`。
- `task_completion`：没有真实任务执行时为 `unknown`。

**必需的支撑或把手语义未知，不能放行；尚待阶段三验证的操作难度未知，可以交接。**

这一边界与[阶段二参考文档](phase2-scene-editing-reference.md)一致。

## 二、范围取舍：首版必须做与暂时不做

### 首版必须做

1. 场景静态索引与候选检索。
2. 少量资产的加载、摆放与部件标注资格记录。
3. 移动、旋转、增加、删除，以及事务撤销。
4. 桌面等明确平面区域的候选生成和落位检查。
5. case1、1.5、2、3 的构建模板。
6. 自动修复、重复失败检测和预算退出。
7. 观察包、严格决策接口、决策来源和工作日志。
8. 冻结包独立恢复，并接入阶段一短动作与三相机记录回归。

### 首版明确限制

- 新增资产只来自已验证可加载的资产池，不支持任意模型导入。
- 删除支撑家具前必须处理依附物；复杂支撑链优先拒绝或换候选。
- 固定家具移动属于模型编辑，不冒充普通位姿修改。
- 关节初态编辑可后置，先限定为已声明、有限位的关节；未支持时明确报错。
- 柜层、容器保留区域类型接口，不要求首批全面覆盖。

### 暂时不做

通用自然语言规划、全屋重排、生成式资产、资产缩放、任意代码执行、多 Agent 协商，以及完整 cuRobo 站位采集。

**建议把“构建核心完成”和“真实视觉 Agent 联调完成”分开验收。**没有外部 API 时可以完成规则覆盖的正式构建，但不能把脚本决策描述为模型复查。

## 三、总体流程：零编辑优先，失败允许退出

下面是建议流程，不代表已经实现。

```text
任务配置 + 机器人配置 + 构建预算
                 ↓
静态检索：房屋、目标、支撑物和资产候选
                 ↓
加载少量候选，提取真实几何与初始状态
                 ↓
case 模板生成要求、保护对象和候选操作
                 ↓
当前已满足？──是──→ 跳过编辑，仍执行必要验证
       │
       否
       ↓
规则选择最小编辑；语义不确定时请求视觉 Agent
                 ↓
检查权限与候选版本 → 执行事务 → 真实静置
                 ↓
支撑、稳定性、穿模、邻近资产与构建要求检查
       │
       ├─ 失败 → 回滚 → 有限修复 / 换候选
       └─ 通过 → 更新事实，失效相关旧检查
                 ↓
最终复查 → 冻结任务候选 → 独立恢复验证
                 ↓
阶段三机器人试验
                 ↓
收录 / 重新归类 / 新建构建候选
```

这里有两个关键原则：

- **不是每个场景都需要编辑，也不是每次构建都需要 Agent。**
- **真实机器人失败不一定是构建失败。**不能为了提高成功率，把任务需要的障碍全部删除。

## 四、沿用现有目录，只补齐职责

不另建一套 editor 工程，也不把 `runtime/runner.py` 扩展成全流程巨型入口。

| 模块 | 阶段二新增职责 |
|---|---|
| `catalog/` | 静态索引、资产资格、检索与候选排序 |
| `scenes/` | 可编辑模型描述、稳定实例与区域映射、模型和状态身份 |
| `construction/` | 要求、case 模板、候选生成、编辑事务、保护与修复策略 |
| `runtime/` | 构建会话、受控静置、模型重建、状态恢复 |
| `validation/` | 落位、稳定性、编辑副作用和逐项构建要求检查 |
| `agents/` | 观察包、严格决策协议、补图请求和调用日志 |
| `recording/` | 编辑前后、静置后证据及失败记录 |
| `workflows/` | 串联检索、构建、预算退出、冻结与下游反馈 |

**模板和 Agent 都只提出操作；真正修改模型、写入状态和推进仿真，仍由 `runtime` 执行。**保持[现有架构](LastMileDataFlow/docs/architecture.md)的执行权限边界。

## 五、优先解决四个工程问题

### 5.1 新增构建会话，不放松连续执行规则

现有 `Simulation.step()` 要求先 `begin()`，而开始后禁止恢复，也不能再冻结初态。因此，不能直接把现有 attempt 当编辑沙盒，更不能通过重置 `started` 绕过限制。

建议增加独立的 **构建会话 `BuildSession`**：

- 允许初始化、编辑、静置、回滚。
- 静置时保持机器人控制目标，不逐帧写回机器人或物体位姿。
- 冻结后关闭构建会话。
- 下游创建全新的 `Simulation` 和 attempt，加载冻结结果。

底层模型加载、机器人适配和快照能力继续复用，不复制另一套机器人执行代码。

### 5.2 区分状态编辑与模型结构编辑

| 编辑类别 | 典型操作 | 处理方式 |
|---|---|---|
| 状态编辑 | 自由物体移动/旋转、合法关节初态 | 修改状态，更新几何，静置验证 |
| 模型结构编辑 | 增删资产、移动固定家具 | 编辑模型工作副本，重新编译并重建绑定 |

首版建议采用**工作副本重编译**，不优先追求复杂的在线热修改。

重编译后必须：

- 按稳定实例/关节名称迁移仍然存在的对象状态。
- 为新增对象显式初始化。
- 重建数字 body/joint ID、机器人适配器和渲染资源。
- 重新验证目标引用与实例映射。

**跨结构回滚恢复“上一份模型＋对应完整状态”，不能把旧状态向量直接写入新模型。**

### 5.3 把模型身份和动态摆放身份分开

现有 `scene_version()` 未纳入完整动态状态。因此，同一模型中只移动一个杯子，现有版本 ID 不足以表达摆放变化。

建议分开记录：

| 标识 | 表示什么 |
|---|---|
| `model_id` | 模型、资产依赖、实例映射及兼容信息 |
| `checkpoint_id` | 对应模型下的完整动态状态与恢复所需控制状态 |
| `build_id` | 一次构建的配置、操作、检查、决策与结果记录 |
| `scene_version_id` | 已冻结模型、检查点和映射等内容的组合引用 |

候选位置和观察包还应绑定当前 `revision`，防止执行编辑前生成的过期候选。

状态摘要基于规范化内容定义，而不是只依赖压缩快照文件的字节。

### 5.4 正式扩展配置，不绕过 v1 校验

现有 `TaskConfig` 明确拒绝非空编辑权限和任务成功条件，这是阶段一的正确限制。

建议增加版本化构建配置，至少包括：

- case 类型、目标和操作语义。
- 可编辑对象、允许操作和保护对象。
- 必需构建要求与待验证假设。
- 静置、碰撞、支撑等检查协议。
- 候选、编辑、修复、Agent 和超时预算。

**保持旧 v1 配置与 attempt 的解释不变。**新版通过明确版本解析，不让历史字段悄悄改变含义。

上述缺口依据现有[仿真生命周期](LastMileDataFlow/src/lastmile_dataflow/runtime/simulation.py)、[版本实现](LastMileDataFlow/src/lastmile_dataflow/scenes/source.py)和[配置实现](LastMileDataFlow/src/lastmile_dataflow/config.py)的静态检查。

## 六、构建器内部怎么工作

### 6.1 检索采用“静态粗筛，加载后确认”

首版建议使用 SQLite 保存可查询索引，JSON 保存版本化记录。

静态索引提取：

- 房屋、房间、类别和实例。
- 父子关系、静态/动态属性和关节。
- 模型、资产与 grasp 引用及可解析状态。
- 源文件和依赖摘要。

只对候选房屋加载仿真，补充：

- 实际支撑区域。
- 目标尺寸、碰撞几何与可放置空间。
- 局部地面净空和机器人初始化候选。

metadata 的父子关系只作为线索，不能直接当作已验证支撑关系。索引也应区分“已发现文件”“可解析”“可加载”“已验证”，不能把缺失字段补成猜测值。

### 6.2 先可靠支持少量桌面，不追求通用支撑面识别

首版针对少量代表性桌面：

1. 从实际几何提取候选平面。
2. 建立带边界、高度和局部坐标系的区域。
3. 按物体足迹、朝向、边缘余量和占用情况生成位置候选。
4. 对区域可信度不足的资产跳过，不用家具整体包围盒代替桌面。

每个区域、位置和朝向都有稳定引用。模板或 Agent 选择的是“区域＋候选”，精确位姿由程序计算。

### 6.3 每次编辑都是可撤销的小事务

一笔事务包含：

- 为什么修改、当前版本、涉及对象。
- 操作权限、保护约束和支撑依赖。
- 请求位姿、实际执行参数和预期落位关系。
- 编辑前检查点、编辑后检查结果。
- 提交或回滚结论。

流程为：

**预检查 → 保存检查点 → 应用操作 → 静置 → 检查 → 提交或回滚。**

相互依赖的少量操作可以组成一个事务。例如先移走桌上物体，再删除桌子；不要求每个原子操作单独形成有效场景。

回滚恢复现场，但不删除失败证据。

### 6.4 落位检查不能只看最终速度

建议分五组检查：

| 检查组 | 主要判断 |
|---|---|
| 支撑正确性 | 是否仍在指定桌面，而非地板或相邻物体 |
| 区域关系 | 足迹、高度、边缘距离是否符合要求 |
| 动态稳定性 | 末尾窗口内速度与姿态变化是否稳定，过程中是否弹飞 |
| 碰撞有效性 | 是否存在严重穿透或异常卡住 |
| 编辑副作用 | 邻近资产、保护对象和机器人初态是否受损 |

静置窗口可从原计划的 **0.5–2 秒**开始试跑，并设最大延长预算；这不是已经校准的保证。

阶段一的穿透启发式不能直接当完整落位验收器。应先用代表性目标、桌面和障碍校准协议，随后固定参数，不能为单个样例临时放宽。

每次编辑后，相关旧结论都要失效；最终冻结前复查全部硬要求，并扫描全场基础异常。

### 6.5 修复规则保持简单

- 支撑错误：重新定位支撑面或换候选。
- 靠边滑落：向区域内部移动。
- 碰撞重叠：小幅平移、换朝向或换资产。
- 把手方向错误：优先只旋转目标。
- 邻近物体被挤落：回滚，减少修改范围。
- 连续同类失败：换候选，不反复尝试同一方案。

建议先采用原计划的 **最多 2–3 轮修复**作为试跑配置。另设单场景预算和整个采集请求的累计预算，不能通过创建新 build 无限重置计数。

## 七、四类 case 的具体构建方式

**建议实现顺序：case1 → case2 → case3 → case1.5。**这是工程顺序：先验证摆放与恢复，再验证方向、增删，最后处理更复杂的侧向空间关系。

| Case | 构建内容 | 阶段二验证 | 留给阶段三 |
|---|---|---|---|
| **1：距离困难** | 桌面目标、合法机器人起点、距离/高度区间 | 目标稳定、起点合法、构建参数满足 | 当前站位是否失败，其他站位是否成功 |
| **2：把手朝向不匹配** | 有可靠把手标注的 mug、指定操作侧和方向候选 | 标注来源可信、世界方向正确、旋转后稳定 | 是否真正完成把手抓取 |
| **3：抓取路径障碍** | 在候选接近区域布置稳定障碍 | 障碍落位正确、不与目标严重穿透、保护关系成立 | 是否影响实际规划，是否可绕行 |
| **1.5：侧向差异** | 在家具局部坐标系中设置不同侧的净空和距离差异 | 各侧几何关系与参照系明确 | 各侧真实通行、站位和操作差异 |

特别注意：

- case2 不能默认资产 `+X` 就是把手方向。
- case3 的必要障碍应加入保护要求，修复不能自动把它清掉。
- case1.5 的“北、南、西”必须绑定明确坐标系，不能随相机视角改变。
- 资产池分别记录加载、摆放、普通抓取和把手抓取证据。**存在 grasp 文件，不等于当前场景可抓。**

原计划中的普通抓法和把手抓法资格验证依赖可执行抓取能力。若该后端仍未完成，应明确列为待验资格，而不是提前宣布完成，也不因此把整套阶段三塞进阶段二。

## 八、视觉 Agent：按需使用，但接口先规范

默认路径是规则和模板。只有以下情况升级到视觉 Agent：

- 部件语义或遮挡不能可靠判断。
- 多个几何候选需要语义取舍。
- 修复停滞，需要选择其他局部策略。

### 输入

- 俯视图、目标局部图、必要侧视图和机器人视角。
- 实例 ID、区域 ID、候选 ID。
- 当前要求、保护约束与程序检查结果。
- 明确区分编辑前、编辑后未静置、静置后的图像。

### 输出

只允许：

- 选择候选操作。
- 请求补图或几何查询。
- 提议局部修复。
- 放弃当前候选。

不允许修改碰撞参数、质量阈值、成功定义或执行任意代码。硬检查失败不能被视觉判断覆盖。

所有观察和决策绑定版本；坏 JSON、未知 ID、过期候选、越权操作和调用超时都有明确退出结果。

诊断俯视、剖视等图像独立标记，**不混入机器人三相机观测，也不默认成为后续 VLA 输入。**

## 九、实施顺序与验收门槛

沿用参考文档的 2A—2E 划分，但明确各步必须拿到的结果。

| 里程碑 | 主要工作 | 验收门槛 |
|---|---|---|
| **2A：最小恢复闭环** | 新配置与任务契约；构建会话；固定小样例上的零编辑、移动、旋转、撤销 | 源文件不变；失败无残留；不同布局有不同检查点；独立恢复一致 |
| **2B：可靠编辑与物理检查** | 支撑区域、落位检查、保护失效机制；受限增删与跨结构回滚 | 掉落、错支撑、严重穿模可阻断；增删后身份正确；回滚恢复模型与状态 |
| **2C：检索与四类模板** | 静态索引、资产池、检索排序、四类构建要求与修复规则 | 不依赖单一房屋/资产；四类要求可检查；难度不提前标成功或失败 |
| **2D：按需视觉协作** | 观察包、结构化协议、补图、日志和预算；真实后端按条件接入 | 规则与 Agent 共用物理门槛；非法决策被拒绝；决策来源如实记录 |
| **2E：交接与反馈** | 冻结包独立重载；阶段一回归；预算换场景；下游反馈分类 | 编辑场景可运行、可记录；超预算退出；冻结产物不被后续反馈覆盖 |

规则已覆盖时，可以先完成 2E，再补真实 Agent 联调，但交付报告必须分别说明完成状态。

### 必测故障

至少覆盖：

1. 物体掉到地上或错误支撑物上，最终却静止。
2. 目标与桌面、障碍严重穿透。
3. 删除带依附物的家具。
4. 修复破坏先前已通过的朝向或保护要求。
5. 新增资产缺资源、ID 冲突、重编译后映射改变。
6. 跨结构撤销、损坏快照、模型状态不匹配。
7. Agent 重复失败建议或使用过期候选。
8. 连续机器人执行错误调用构建期编辑接口。

验收先看这些错误是否被正确阻断，再衡量构建产出率和速度，不先设缺乏试跑依据的统一成功率目标。

## 十、最终交付与阶段三反馈

沿用现有存储布局：

- `outputs/indexes/`：场景与资产索引。
- `outputs/builds/<build-id>/`：任务候选、事务、观察、决策、检查和成本记录。
- `outputs/scene_versions/<version-id>/`：冻结模型、完整状态、实例映射和依赖清单。
- `outputs/attempts/<attempt-id>/`：独立恢复回归及后续真实执行证据。

模型结构变化与动态状态必须一起保存；只保存 qpos 或只保存 MJCF 都不够。

阶段三反馈分开处理：

- **场景无效**：修复或换候选。
- **任务成功但没有预期难度**：保留结果，重新归类或另建候选。
- **有效场景中预算内全部失败**：保留未解难例，不自动删障碍。
- **基础设施失败**：重试服务或退出，不改变场景难度。

任何反馈都不得修改已经冻结并采集过的版本。

**第一项具体工作应是：选择一个桌面 case1 小样例，完成“任务契约 → 构建会话 → 移动/旋转 → 静置检查 → 冻结 → 独立恢复 → 阶段一短动作回归”。这个闭环通过后，再铺开索引、增删和四类模板。**

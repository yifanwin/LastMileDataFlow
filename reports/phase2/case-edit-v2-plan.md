# 新 Pipeline 完整方案

## 方案总结

本方案采用 **4 个主 Agent + 程序化构造与验证模块**：

- **Agent1：生成 Case Template。**
- **Agent2：选择局部上下文和初步编辑方向。**
- **Agent3：面向具体场景生成 DSL 编辑提议。**
- **Agent4：检查编辑前后可见变化是否符合构造意图。**

单场景输入跳过房屋检索；数据集输入以后增加独立的场景检索模块。

**构造验收与机器人任务验收分开：Agent 不负责证明底盘可达、抓取成功或“必须移动”。这些结论来自程序检查与真实仿真。**

以下都是设计方案和提示词草案，不表示当前工程已经实现；本轮不修改代码。

# 一、整体流程

```text
用户输入
  ├─ case 抽象描述
  ├─ 单场景 / 数据集
  ├─ 任务类型与验收目标
  └─ 数量、种子、预算
          │
          ▼
M0 输入解析与来源路由
  ├─ 单场景：直接定位指定场景
  └─ 数据集：场景检索与筛选【后续实现】
          │
          ▼
M1 Agent1：生成 Case Template
          │
          ▼
M2 场景加载、准备期检查、完整 Scene Graph
          │
          ▼
M3 程序生成局部上下文候选
          │
          ▼
M4 Agent2：选择上下文 + 初步编辑方向
          │
          ▼
M5 采样合法、head 可见目标的机器人初态
          │
          ▼
M6 拍摄编辑前观察，固定基准
          │
          ├──────────────┐
          ▼              │
M7 按需检索与筛选资产      │ 可请求调整方向、
          │              │ 扩展上下文或重建基准
          ▼              │
M8 Agent3：生成具体 DSL ───┘
          │
          ▼
M9 DSL 校验、参数采样、生成可执行操作
          │
          ▼
M10 事务编辑、静置、物理与端点检查
          │
          ▼
M11 同初态、同相机拍摄编辑后观察
          │
          ▼
M12 Agent4：编辑语义检查
          │
          ├─ 未通过：反馈与重试
          │
          ▼
构造候选通过 construction_accepted
          │
          ├─ construction_only：保存并结束该候选
          │
          ▼
M13 真实移动操作验收
          │
          ▼
M14 汇总结果、去重、计数与预算调度
```

**每个候选从未编辑的基准独立构造，不默认在上一个候选上累计编辑。**

# 二、输入与核心数据对象

## 2.1 用户输入

建议明确以下字段：

| 字段 | 含义 |
|---|---|
| `scene_input` | 单场景或数据集，以及实际数据位置 |
| `case_description` | 只描述期望现象，不要求指定物体实例或编辑操作 |
| `task_type` | `pick`、`place`、`pick_then_place` |
| `objective_mode` | 移动后更好，或要求验证需要换工作位置 |
| `verification_mode` | 仅构造，或包含真实任务验收 |
| `target_variant_count` | 从输入来源生成多少个不同构造 |
| `seed` | 随机种子 |
| `budgets` | Agent 调用、上下文、参数采样、仿真时间等预算 |

单场景示意：

```json
{
  "scene_input": {
    "kind": "single",
    "dataset_dir": "molmospaces_data/assets/scenes/procthor-10k-val",
    "scene_id": "val-103"
  },
  "case_description": "目标周围的几何布局使部分接近方向不适合操作，而换到另一个方向后更有利于抓取；不能仅靠增大目标距离制造困难。",
  "task_type": "pick",
  "objective_mode": "beneficial_reposition",
  "verification_mode": "construction_only",
  "target_variant_count": 10,
  "seed": 42
}
```

这是**新方案的输入契约草案**，不是当前已有命令的配置格式。

### 两种目标必须区分

- `beneficial_reposition`：调整底盘位置后，任务效果更好。
- `required_reposition`：要求额外验证，成功操作需要离开原工作区域。

未明确选择时，可以将前者作为**显式记录的系统默认**，但不能自动给出“必须移动”的标签。

## 2.2 模块之间传递的主要对象

| 对象 | 主要内容 |
|---|---|
| `CaseTemplate` | 抽象机制、任务角色、构造要求、端点 invariant、待验证任务假设 |
| `SceneSnapshot` | 指定原始场景、完整模型、准备期状态和来源 |
| `GlobalSceneGraph` | 全场景物体、几何、支撑、区域和关系 |
| `LocalContext` | 目标、支撑面、局部物体、附近地面与障碍、上下文边界 |
| `ConstructionPlan` | 选定上下文、编辑方向、布局对比假设、资产需求 |
| `ObservationBaseline` | 机器人初态、相机状态、编辑前 RGB、可见性结果 |
| `AssetCandidates` | 实际可加载资产、尺寸、来源、编辑能力与预览 |
| `SymbolicProposal` | 物体绑定、DSL 操作、参数范围、附加要求 |
| `ExecutableEdit` | 采样后的实际资产和具体位姿 |
| `EditEvidence` | 前后图、RGB、物理检查、语义检查 |
| `TaskEvidence` | 实际底盘移动与操作轨迹、结果、对比指标 |
| `CandidateResult` | 构造、case 成立、任务完成的独立结论 |

程序为这些对象生成身份标识，避免把不同基准、不同候选的图像和结果混用。这里只保留必要的复现信息，不增加人工审批或额外权限流程。

# 三、各模块的输入、操作、输出

## M0：输入解析与来源路由——程序

### 输入

用户请求、机器人配置、数据位置、预算和验收协议。

### 操作

1. 检查请求字段和数据路径。
2. 将 `val-103` 等别名解析为明确的场景身份。
3. 检查场景编号与数据集 split 是否一致。
4. 根据输入类型分支：
   - 单场景：直接定位该场景，**不调用场景检索**。
   - 数据集：进入检索模块。
5. 区分“输入来源数量”和“期望构造数量”。
6. 建立共享预算和种子。

### 输出

`ResolvedRequest`：

- 确定的输入类型；
- 原始场景来源；
- 任务与验收模式；
- 构造数量；
- 预算与配置摘要。

**单场景定位失败应报错，不允许模糊搜索另一栋房屋替代。**

---

## M1：Case Template 规范化——Agent1

### 输入

- 原始 case 描述；
- 任务类型；
- 验收目标；
- 用户明确给出的数值要求；
- 可选难度配置。

不输入具体物体实例和全场景图。

### 操作

将描述拆分为：

1. 用户希望出现的现象；
2. 可能导致该现象的机制；
3. 需要的抽象角色；
4. 可由构造程序检查的要求；
5. 编辑前后都需要成立的 invariant；
6. 可以通过前后图像检查的语义；
7. 必须真实执行才能判断的任务假设。

例如 case1.5 应保留：

- 部分方向站立空间受限；
- 部分合法站位对操作不利；
- 另一个方向更有利于操作；

而不是降级为“目标离机器人更远”。

### 输出

`CaseTemplate`，建议包含：

```text
case_type
intent
task_type
objective_mode
roles
parameters
requirements
invariants
semantic_checks
task_hypotheses
assumptions
```

**每次重新规范化，不检索历史模板。**

---

## M2：加载指定场景并建立完整图——程序

### 输入

- 明确的场景来源；
- 机器人模型；
- 准备期物理检查与静置配置；
- 可选的同源、未编辑缓存。

### 操作

1. 加载完整场景和机器人。
2. 在准备期完成合法性检查和静置。
3. 建立完整 Scene Graph，包括：
   - 实例身份与资产来源；
   - 实测位姿、碰撞几何；
   - 房间归属；
   - 支撑面、放置区域；
   - 实际支撑关系；
   - 固定、自由、关节化根节点；
   - 程序支持的编辑能力。
4. 对缺失信息标记 `unknown`。

这里用于准备场景的机器人位置，**不是正式任务初态**；正式初态在 M5 确定。

### 输出

- `SceneSnapshot`；
- `GlobalSceneGraph`；
- 场景准备结果。

缓存只用于加速同一原始场景加载，不继承旧人工绑定、成功标签或旧 case 判断。

---

## M3：生成局部上下文候选——程序

### 输入

- Case Template；
- 完整 Scene Graph；
- 上下文数量、空间范围和信息量预算。

### 操作

以目标候选及支撑面为锚点，生成局部区域，包含：

- 目标和支撑家具；
- 同一支撑面上的关联物体；
- 附近地面、墙、椅子、凳子；
- 可能影响底盘站位的障碍；
- 任务相关的接近空间；
- place 任务的目的区域及必要连接部分。

同时生成粗粒度的候选工作区域。它们只是几何候选，**不是已证明可站立、可抓取的站位**。

通过种子控制随机采样，避免长期只选择同一个桌面或物体。

### 输出

`LocalContextCandidates`：

- 上下文 ID；
- 目标和支撑候选；
- 局部图与简要摘要；
- 工作区域候选；
- 上下文边界及被截断的关系；
- 已知缺失信息。

局部范围采用**程序提出候选、Agent 选择并动态请求扩展**的方式。:codex-annotation{index="1"}

**上下文裁剪只减少 Agent 的输入，不删除完整仿真中的其他物体。**

---

## M4：选择上下文和初步编辑方向——Agent2

### 输入

- Case Template；
- 局部候选摘要；
- 当前可用编辑操作；
- 可检索的资产类别；
- 历史失败反馈；
- 可选、身份明确的局部预览。

### 操作

1. 选择适合构造的目标和局部区域。
2. 必要时请求扩大上下文。
3. 提出布局对比假设，例如：
   - 区域 A：站立空间可能受限；
   - 区域 B：可以接近，但操作方向可能不利；
   - 区域 C：预计存在较好的操作空间。
4. 选择初步编辑方向。
5. 提出新增资产需求。

此时不输出最终物体位姿，也不输出机器人控制动作。

### 输出

`ConstructionPlan`：

- 选中的上下文；
- 初步编辑方向；
- 预期布局变化；
- 工作区域对比假设；
- 资产检索需求；
- 未验证的任务假设。

操作方向不与 case 编号硬绑定。例如，case1.5 既可能通过移动家具构造，也可能通过新增凳子改变接近空间。

---

## M5：采样合法且可观察的机器人初态——程序

### 输入

- 选中的局部上下文；
- 目标；
- 完整场景模型；
- 机器人几何与关节限位；
- 初态采样预算。

### 操作

1. 在任务相关地面区域采样底盘位置和朝向。
2. 在合法范围内选择头部、躯干等初始配置。
3. 检查：
   - 实际地面支撑；
   - 机器人与环境严重碰撞；
   - 关节与控制范围；
   - head 相机实际目标可见性。
4. 用真实渲染或分割检查遮挡，不能只检查目标投影是否落在画面内。
5. 选定正式初态 `S0`。

### 输出

`InitialStateCandidate`：

- 底盘、头部、躯干、双臂和夹爪初态；
- 合法性检查；
- 目标可见性；
- 未选中初态的失败原因。

**无法合法站立的 A 区域不能被强行设为初态。**A/B/C 是工作区域假设，S0 是实际合法初态，两者不能混为一谈。

---

## M6：建立观察与编辑基准——程序

### 输入

选定初态、完整场景、局部上下文和构造计划。

### 操作

1. 完成初态静置并再次检查。
2. 更新正式基准图中的机器人站位。
3. 拍摄编辑前 head RGB。
4. 检查关键构造区域是否也被覆盖。
5. 必要时增加辅助观察相机。
6. 冻结本轮未编辑基准。

### 输出

`ObservationBaseline`：

- 基准场景；
- 正式机器人初态；
- 相机内外参；
- 编辑前 RGB；
- 目标与关键对象可见性；
- 对应图和基准身份。

这张编辑前 RGB：

- 用于 Agent3 构造；
- 用于 Agent4 前后检查；
- 不重复拍摄不同初态的“编辑前图”。

**目标可见只是必要条件。**如果关键变化位于 head 视野之外，应增加固定配对辅助视角，或重新建立初态和基准。

---

## M7：检索与筛选新增资产——程序

### 输入

- Construction Plan 中的资产需求；
- 实际资产库；
- 尺寸、放置位置和编辑能力要求；
- 检索数量与编译预算。

### 操作

建议首先接入现有只读资产来源：

- `molmospaces_data/assets/objects/thor/`
- `molmospaces_data/assets/objects/objaverse/`
- 对应的可读取元数据。

检索顺序：

1. 类别、关键词或描述召回；
2. 按尺寸与用途筛选；
3. 实际加载、编译候选；
4. 测量碰撞尺寸、根节点类型及支持的操作；
5. 必要时生成预览；
6. 返回少量可用于构造的候选。

坐标轴、尺度等转换必须由明确的资产适配程序完成，不能假设所有资产使用相同约定。

### 输出

`AssetCandidates`：

- 真实资产 ID；
- 来源；
- 测得尺寸；
- 根节点与编辑能力；
- 可选预览；
- 不支持或加载失败原因。

不依赖人工填写的“已验证资产白名单”。

**添加障碍物不要求它具有机器人抓取标注；如果它是任务目标，才需要进一步检查操作所需信息。**

---

## M8：生成具体 DSL 编辑提议——Agent3

### 输入

- Case Template；
- Construction Plan；
- 当前局部 Scene Graph；
- 编辑前 RGB；
- 实际资产候选；
- DSL 语法和程序能力；
- 上轮失败反馈。

### 操作

1. 将抽象角色绑定到实际实例。
2. 生成多种有意义的具体编辑提议。
3. 给出位置和相对旋转的采样范围。
4. 明确新增、移除与关联移动。
5. 保留所有原始要求与 invariant。
6. 信息不足时请求更多上下文或观察，不猜测不可见事实。

### 输出

多个 `SymbolicProposal`：

- `proposal_id`；
- `description`；
- `bindings`；
- `operations`；
- `goals`；
- `invariants`；
- `sampling`。

**无最小编辑目标，不限制为只移动目标物体。**

---

## M9：校验 DSL 并采样具体操作——程序

### 输入

Symbolic Proposal、完整基准、局部图、资产候选和随机种子。

### 操作

1. 校验语法、引用、操作能力和要求冲突。
2. 绑定实际资产。
3. 对范围数值采样。
4. 根据实际几何计算放置高度和支撑区域。
5. 按操作顺序更新中间布局。
6. 将关联搬移展开为具体操作。
7. 生成候选 ID 和可复现采样记录。

### 输出

`ExecutableEdit`：

- 实际对象和资产；
- 具体世界位姿；
- 操作顺序；
- 采样参数；
- 对应模板、计划、基准身份。

统一采用：

- 长度：米；
- 角度：弧度；
- 世界坐标：右手系、Z 向上；
- 四元数：`[w,x,y,z]`；
- DSL 旋转：明确 world/object 坐标系的**相对旋转**。

---

## M10：事务编辑与规则检查——程序

### 输入

Executable Edit、未编辑基准、物理检查配置。

### 操作

1. 从基准建立独立构建分支。
2. 检查编辑前的 invariant。
3. 执行整个操作组。
4. 静置。
5. 更新完整图和局部图。
6. 检查：
   - 非有限状态和求解器异常；
   - 严重穿模、碰撞；
   - 稳定性；
   - 动态物体支撑；
   - 编辑后的 requirements 和 invariant；
   - 新增、移除后的拓扑关系。
7. 失败则回滚分支，保留失败原因。

### 输出

`RuleCheckResult`：

- `pass / fail / unknown`；
- 各项检查；
- 静置指标；
- 实际编辑后图；
- 待视觉检查的候选，或回滚结果。

**支撑等 invariant 在静置后的编辑前、编辑后检查，不要求操作组的每个中间步骤都成立。**

完整场景仍参与物理检查，不能因为对象未进入 Agent 上下文就忽略碰撞。

---

## M11：生成固定配对的编辑后观察——程序

### 输入

未编辑基准、规则通过的编辑分支、Observation Baseline。

### 操作

1. 检查机器人各组初态是否发生超出容差的漂移。
2. 检查 head 相机状态是否一致。
3. 从同一相机拍摄编辑后 RGB。
4. 检查目标和关键变化的可见性。
5. 复用原编辑前图片组成配对证据。

辅助相机也必须保持前后配对，不能前后独立重新取景。

### 输出

`PairedObservation`：

- 编辑前后 head RGB；
- 可选辅助配对视图；
- 初态一致性检查；
- 可见性结果；
- 前后图与候选身份。

如果编辑后目标出画或被完全遮挡，不允许通过转动编辑后 head 相机补救。应调整编辑，或重建初态和基准后重新构造。

---

## M12：编辑语义检查——Agent4

### 输入

- 原始描述；
- Case Template；
- Construction Plan；
- Symbolic Proposal 和实际执行操作；
- 前后局部图；
- 程序规则结果；
- 实际配对 RGB。

### 操作

逐项检查：

- 是否真的出现了预期可见变化；
- 是否与原始 case 构造意图一致；
- 是否只是改变了距离而没有形成要求的几何布局；
- 关键变化是否因遮挡而无法判断；
- 是否存在遗漏或相反效果。

### 输出

`SemanticReview`：

- `pass / fail / uncertain`；
- 每项语义检查及视图依据；
- 未验证的任务假设；
- 建议下一步动作。

通过只表示**可见构造符合意图**，不表示 A 抓不到、C 抓得到。

## M13：真实移动操作验收——程序与任务执行器

这是完整 case 验收所必需的下游模块，不能由 Agent4 替代。

### 输入

- 构造通过的冻结场景；
- 合法初态 S0；
- 任务；
- 待验证的工作区域假设；
- 固定的搜索、控制、任务成功和比较协议。

### 操作

建议按成本分层：

1. **几何检查**
   - 底盘占地；
   - 空间与障碍；
   - 工作区域是否合法。

2. **规划诊断**
   - 底盘路径；
   - 操作配置；
   - 接近、抓取、抬升、持物搬运、放置路径。
   
   规划结果是诊断证据，不等于真实执行成功。

3. **连续仿真执行**
   - 允许底盘平移和旋转；
   - 记录实际运动；
   - 执行抓取或放置；
   - 检查任务完成条件。

4. **按目标模式汇总结论**
   - 调整位置后是否成功；
   - 是否比对照策略更好；
   - 是否满足协议限定的必要性证据。

### 输出

`TaskEvidence`：

- 实际底盘路径及工作位置；
- 实际操作轨迹；
- 任务结果；
- 失败阶段；
- 对比指标；
- 验证覆盖范围和剩余未知。

### 不能混淆的三种结论

- **观察到移动后成功**：证明这条执行成功，不自动证明移动带来改善。
- **移动后更好**：需要公平对照，双方都允许底盘平移和旋转。
- **必须换工作位置**：需要额外定义工作区域和搜索协议；有限搜索无解不能证明全局不可能。

“指定搜索协议”就是预先固定：

- 搜索哪些区域、位姿和操作配置；
- 使用什么规划器或控制器；
- 每类尝试的次数、时间和种子；
- 成功与失败如何判断。

协议由配置决定，Agent 不能看到结果后修改它。

对于 place / pick_then_place，应通过真实抓取建立持物状态，或使用具有来源证据的合法持物初态，不能仅设置 `holding=true` 就当作已抓取。

**现有固定底盘站位测试只能作为诊断，不能直接充当本模块的移动任务验收。**

## M14：反馈、去重、计数和停止——程序

### 输入

所有阶段结果、失败反馈、剩余预算和目标数量。

### 操作

根据失败位置决定重试层级：

| 失败类型 | 优先处理 |
|---|---|
| DSL 格式或引用错误 | 返回 Agent3 修正 |
| 个别采样碰撞、越界 | 重新采样参数 |
| 多次同类物理失败 | 修改提议或编辑方向 |
| 目标不可见 | 调整提议，或重建初态与基准 |
| 关键变化无法观察 | 增加固定配对辅助视图 |
| 局部信息不完整 | 扩展上下文 |
| 当前区域无法表达机制 | 返回 Agent2 换区域 |
| 资产无可用候选 | 改资产需求或构造方向 |
| 真实任务不符合预期 | 将真实证据反馈给 Agent2/3 |
| 服务或渲染异常 | 作为基础设施问题处理，不当作 case 失败 |

去重依据最终布局，而不是提议文字、随机 ID 或操作数量。

### 输出

- 接受的构造候选；
- 已验证的 case；
- 失败候选及原因；
- 预算使用情况；
- 停止原因。

单场景模式下，所有重试都留在指定场景内；达到预算后输出“预算内未找到”，不擅自换场景。

# 九、数据集模式预留：场景检索 Agent

**单场景阶段不调用这个 Agent。**

后续数据集模式采用：

```text
Case Template
    ↓
程序从场景索引召回候选
    ↓
场景选择 Agent 排序
    ↓
程序加载少量候选并检查实际适用性
    ↓
进入同一套 M3—M14 流程
```

索引中的类别匹配只用于召回，不等于场景适合构造。

## 输入、操作、输出

- **输入**：Case Template、场景候选摘要、已测几何信息、真实预览、预算、历史失败。
- **操作**：排序值得进一步加载的场景，解释与 case 机制的关联。
- **输出**：有序场景 ID、理由、未知项、需要补充的检查。
- **最终筛选**：由程序实际加载、采样上下文和检查，不由 Agent 一句话判定。

## 中文提示词

```text
你是数据集模式的场景候选选择Agent。

你的任务是从程序召回的场景中，
选择值得进一步加载并尝试构造的候选。
你不直接编辑场景，不决定最终case是否成立。

请考虑：
- 是否包含任务所需的目标、支撑面或目的区域；
- 是否存在构造不同接近方向和工作位置的空间；
- 是否可能通过当前支持的操作形成目标机制；
- 是否缺少重要信息，需要实际加载后检查。

只返回输入提供的scene_id。
不要依赖人工成功标签或历史“已验证场景”白名单。
不要把类别匹配、预览图片或metadata直接当作物理适用性证明。

优先给出与用户机制相关的理由，
不要只因为物体多、房间大或看起来复杂就排在前面。

不能通过摘要判断的信息必须列为未知。
候选不足时请求扩大召回，不得宣称整个数据集不存在合适场景。

输出：
{
  "decision": "rank / expand_retrieval / no_candidate",
  "ranked_scene_ids": [],
  "reasons": [
    {
      "scene_id": "实际候选ID",
      "known_supporting_facts": [],
      "uncertainties": [],
      "required_program_checks": []
    }
  ],
  "retrieval_request": null
}
```

# 十、共享运行模块与结果契约

## 10.1 Agent 网关

所有角色共用一个程序网关：

- 输入：角色、提示词、结构化输入、图片和剩余预算。
- 操作：选择 provider、请求模型、解析和校验 JSON、有限重试。
- 输出：合法结构化结果，或明确的服务／格式错误。

沿用已讨论的 provider 语义：

- 显式指定 provider：只访问指定服务。
- `auto`：每次逻辑调用先尝试第一个，服务失败后访问第二个。
- 重试与切换都计入共享预算。
- 密钥只从本地配置读取，不进入 Agent 输入或交付结果。

## 10.2 独立结果字段

每个候选至少保留：

```text
scene_validity
construction_satisfaction
visual_semantic_alignment
case_condition
task_completion
verification_scope
```

例如，仅构造通过时：

```json
{
  "scene_validity": "valid",
  "construction_satisfaction": "pass",
  "visual_semantic_alignment": "pass",
  "case_condition": "unknown",
  "task_completion": "unknown",
  "verification_scope": "construction_only"
}
```

停止状态也应区分：

- 达到目标数量；
- 预算耗尽；
- 当前上下文无候选；
- 规划无解；
- 实际执行失败；
- 基础设施异常；
- 用户中断。

这些状态不能统一写成“case 失败”。

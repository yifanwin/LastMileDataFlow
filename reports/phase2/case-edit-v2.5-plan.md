# Case 构造 Pipeline 完整修正计划

## 执行摘要

已核对当前工作流、机器人初始化、图像检查及 CuRobo 封装。本轮**只给计划，不修改代码、配置或文件**。

按最新补充，方案确定为：

- **加载实体机器人，采样几个初始点并实际放置。**
- **初版重点验收编辑前后的场景变化，不执行底盘移动和抓取。**
- Agent 可以分析“移动到哪个方向可能更好”，但不据此宣布 case 成立。
- CuRobo 留作后续程序化验证接口，本轮不作为构造前置条件。
- 优先解决统一输出契约和补图闭环；偶发 SIGTERM 暂不专项处理。

---

## 一、本轮目标和边界

### 本轮交付

从指定单场景 `val-103`，自动生成 case1、case1.5、case3 的**构造候选**，完成：

1. 原始描述规范化。
2. 局部区域和编辑方向选择。
3. 机器人初始点采样、加载及观察。
4. 资产检索、DSL 提议和实际编辑。
5. 物理规则检查。
6. 固定相机的编辑前后配对检查。
7. 缺少视图时自动补图，回到原步骤继续。
8. 保存场景、RGB、检查结果和未验证假设。

### 本轮不做

- 数据集级场景检索、历史 Case Template 检索。
- 真实底盘移动、机械臂操作和抓取成功率测试。
- 用 Agent 判断替代可达性、碰撞路径或移动收益验证。
- 偶发 SIGTERM 的专项定位。
- 最小编辑、最少物体或最小位移优化。

原始场景稳定检查继续采用已授权的宽松策略，不重新收紧，也不继续靠放宽物理阈值解决 Agent 问题。

### 三类 case 的构造验收范围

| case | 本轮应构造出的变化 | 暂不宣称 |
|---|---|---|
| case1 | 目标与家具、支撑面或障碍的关系发生变化，形成不同操作侧的几何差异；不能只是移远 | 必须移动、移动后一定成功 |
| case1.5 | A 侧空间受限、B 侧布局对目标操作不利、C 侧保留更合适的操作空间 | A 实际不可达、B 机械臂不可达、C 成功率高 |
| case3 | 在目标接近、抬升或撤离相关区域形成具体障碍布局，可组合移动、旋转和新增资产 | 真实抓取路径必然碰撞、换位置后必然避开 |

原始任务要求仍完整保留，只是标为**待验证假设**，不是删掉后降低验收目标。

## 二、修正后的完整流程

局部范围采用“**程序生成候选，Agent2 选择或请求扩展**”：可以基于房间、桌面及附近地面进行采样，不把整栋房屋直接交给 Agent。:codex-annotation{index="1"}

| 模块 | 输入 | 操作 | 输出 |
|---|---|---|---|
| 输入解析 | 场景、case 描述、数量、种子、预算 | 精确定位单场景，不检索其他房屋 | 明确的构造请求 |
| Agent1：规范化 | 抽象描述、输出契约 | 每次重新生成模板，拆分构造要求与任务假设 | Case Template |
| 场景准备 | 原始场景、宽松配置 | 加载完整物理场景，建立全局图 | 未编辑基准、Scene Graph |
| 局部候选生成 | 全局图、模板 | 提取目标、支撑面、墙体、家具和附近地面 | 局部上下文候选 |
| Agent2：方向选择 | 候选上下文、模板、可检索资产类别 | 选择局部区域，提出编辑方向及 A/B/C 等区域假设 | Construction Plan |
| 初始点采样 | 局部目标、机器人模型 | 实际放置机器人，检查地面、碰撞、关节限位和 head 可见性 | 初态候选及选中初态 |
| 观察与资产准备 | 计划、选中初态、资产需求 | 拍 head 和必要辅助图；检索、加载、筛选资产 | 编辑前观察包、真实资产候选 |
| Agent3：具体提议 | 模板、局部图、观察包、资产 | 输出 DSL；信息不足则提出结构化请求 | 提议或信息请求 |
| 信息请求执行 | 请求、当前阶段和基准 | 补图、扩展上下文或补充资产，然后返回原阶段 | 更新后的输入 |
| 编辑执行 | DSL、采样种子、未编辑基准 | 采样数值，事务编辑、静置、规则检查 | 编辑后场景与检查结果 |
| 配对观察 | 前后场景、固定相机组 | 渲染同初态、同相机的前后图 | 配对证据包 |
| Agent4：变化检查 | 配对图、前后局部图、规则结果 | 检查可见变化；另给移动收益辅助意见 | 分项检查、辅助判断 |
| 程序汇总 | 所有检查、预算 | 决定构造接受、补信息、修改提议或结束 | 构造结果与交付目录 |

**各编辑候选从未编辑基准独立生成，不在上一个候选上累计修改。**

## 三、统一输出契约

### 1. 一份定义管理全部接口

建立统一的契约定义，供以下部分共同使用：

- Agent 中文提示词中的字段说明。
- 合法输出示例。
- 服务支持时使用的 JSON Schema。
- 本地解析器。
- 模块间输入输出校验。
- 单元测试和错误反馈。

不能再分别维护“提示词认为的结构”和“解析器要求的结构”。

结构合法后，程序仍需检查引用的物体、区域、资产和视图是否真实存在，不能仅验证 JSON 能解析。

### 2. 四个 Agent 的职责同步修正

| Agent | 必须遵守的提示词要求 |
|---|---|
| Agent1 | 把物理条件、可见变化、任务假设分别输出；不把底盘运动收益放进前后静态图检查 |
| Agent2 | 只选择提供的上下文和区域；输出编辑方向、资产需求及观察覆盖需求，不编造可达事实 |
| Agent3 | 只引用真实物体和资产；缺信息时输出结构化请求；不能假装已经看到侧后方布局 |
| Agent4 | 逐项检查可见变化并引用证据；信息不足返回 unknown 或请求补图；移动收益意见单独输出 |

### 3. 简化 Reviewer 输出

程序负责身份、版本、必检项和总体状态。Agent 重点返回：

- 检查 ID。
- `pass / fail / unknown`。
- 判断理由。
- 证据引用。
- 可选的信息请求。
- 独立的移动收益辅助意见。

原始 case 意图作为背景保留，**不再把包含“成功率高、必须移动”等内容的整段描述，当成必须通过的视觉检查项**。

### 4. 格式修复不触发重新编辑

格式失败后：

1. 保留当前场景、提议和图片。
2. 返回上一份错误响应、具体错误位置及预期结构。
3. 在同一候选上进行有限修复，建议默认最多一次。
4. 仍不合规则记录 `agent_protocol_error`，不当作物理失败。

服务失败、响应截断、结构错误、无效 ID 和真实检查失败分别处理。**不能自动补出缺失的 pass，也不能为了格式问题重新移动物体。**

## 四、实体机器人初始点采样

### 采样方式

在选中目标附近，结合房间地面和工作区域，采样：

- 底盘 XY 和朝向。
- 合法的 head 观察姿态。
- 固定的手臂、躯干初始配置。

建议先尝试保留 **3 个合法初态**；找到至少一个即可继续，不因未凑满三个而过滤场景。尝试次数沿用有界配置。

每个候选需要**实际加载和放置机器人**，检查：

- 关节限位。
- 地面支撑。
- 与场景的严重碰撞或穿透。
- 实际 head 渲染中的目标可见性。

这只证明该位置可以作为初始化放置和观察点，**不证明机器人能从其他位置导航到这里**。

### 初态与 A/B/C 的关系

- 初态候选与 A/B/C 工作区域假设分别管理。
- A 如果狭窄到无法合法放置机器人，不强行将机器人放进去。
- 可以选择 B、C 或其他合法位置作为观察初态。
- 不在同一场景同时放置多台机器人；每个初态在独立初始化分支验证。

### 前后配对原则

选定一个主初态 `S0` 后：

- 编辑前后使用同一个机器人初态。
- head 配置保持一致。
- 不为拍摄编辑后图片单独转头或移动底盘。
- 若必须更换初态，重新建立该初态下完整的前后配对，不能只重拍后图。

本轮所有放置都发生在构建初始化阶段，不是任务执行中的传送。

## 五、真正执行补图请求

### 1. 统一观察包

观察包包含：

- 实际 head 图。
- 辅助相机图。
- 各视图的位置、参数、覆盖对象和状态身份。
- 哪些区域仍不可见。

辅助图是仿真实际渲染，不是机器人传感器输入，也不替代 head 图。

建议默认 **head＋两个辅助视角**，按需增加；辅助视角上限和采样预算可配置。

### 2. 根据机制动态选相机

| case | 重点覆盖 |
|---|---|
| case1 | 目标、支撑面、相关家具和操作侧的整体关系 |
| case1.5 | A/B/C 地面范围、柜体边缘、凳子等障碍占地 |
| case3 | 目标周边桌面、障碍分布及高度关系 |

程序生成候选相机后，应通过实际渲染、射线或分割结果筛选：

- 相机不在墙体或其他实体内部。
- 不被外墙遮挡。
- 所需区域实际进入画面。
- 不只是“目标可见”，而是关键变化也可见。

### 3. 结构化信息请求

请求至少包含：

- 请求类型：补图、扩展上下文、补充资产或更换目标。
- 需要覆盖的对象、区域。
- 希望判断的问题。
- 请求前图、后图还是配对图。

执行关系为：

**Agent3/4 请求 → 程序执行 → 返回同一个 Agent 阶段继续。**

补图不默认消耗一轮新的上下文选择，也不默认重新编辑。

建议每候选最多两轮补图；耗尽后记录 `information_insufficient`，不能把“看不清”判断为“物理失败”。

### 4. 前后共用相机

构造前观察与编辑检查共用同一组相机：

- 编辑前图直接复用。
- 编辑后使用相同相机参数。
- 若编辑后才请求新视角，必须在保存的前后状态分别渲染该视角。
- Reviewer 接口从“只能两张 head 图”改为接收实际视图清单，并验证配对关系。

## 六、检查与接受规则

### 硬验收

构造接受需要：

1. 物理规则通过。
2. 编辑前后支撑等 invariant 通过。
3. 编辑产生实质布局变化，不是重复候选。
4. 必需的可见构造检查通过。
5. 证据来自正确的场景、初态和相机配对。

新增物体的支撑属于编辑后条件，不要求它在编辑前已经存在。

### Agent 辅助意见

Agent 可以输出：

- 哪个区域可能更有利。
- 推测的原因。
- 仍缺少哪些证据。
- 建议后续验证哪些站位。

这些意见**不直接决定移动收益，也不因缺少任务执行证据而否决已经满足的构造条件**。但“只是移远、没有要求的几何变化”等构造不匹配仍应拒绝。

### CuRobo 后续接口

当前 [CuRobo 封装](LastMileDataFlow/src/lastmile_dataflow/planning/curobo.py)是指定底盘位姿下的单臂规划，不能直接当成底盘移动优化器。

后续需要：

1. 外层采样底盘 XY、朝向。
2. 检查候选站位及底盘移动路径。
3. 在各候选位姿下调用 CuRobo。
4. 使用相同抓取候选和规划预算比较结果。
5. 将规划证据与实际执行结果分别保存。

单次规划无解不能证明绝对不可达；规划通过也不直接等于抓取成功率高。**该模块本轮只预留接口，不阻塞构造。**

## 七、按顺序实施的任务

以下均是**待执行的修正任务**，不是已完成声明。

| 阶段 | 主要任务 | 完成标准 |
|---|---|---|
| P0：冻结边界 | 明确构造验收、辅助意见、任务验证三类结果 | 未执行的移动和抓取始终保持 unknown |
| P1：统一契约 | 统一四 Agent 接口、提示词、Schema、解析器和错误分类 | 既有格式失败样例有明确检测与修复测试 |
| P2：初态候选 | 将当前首个合法初态扩展为少量候选，实际加载并选择主初态 | 有初态、碰撞检查和实际 head 观察证据 |
| P3：动态视图 | 实现局部覆盖驱动的相机采样、筛选及固定配对 | 能覆盖桌面和 A/B/C 地面，不接受外墙遮挡图 |
| P4：信息闭环 | 执行 Agent3/4 的补图请求，返回原阶段 | 补图期间不重新编辑、不无故更换上下文 |
| P5：验收拆分 | 分离物理、可见构造、辅助收益意见；同候选格式修复 | 缺任务证据不会误伤构造验收，Agent 不能宣布任务成功 |
| P6：模型对照 | 用同一输入比较 gpt-5.6-sol 与 glm-5.3 | 分别报告格式、补图、职责遵守及耗时 |
| P7：真实交付 | 重新执行 val-103 的三类 case | 每类至少一个真实构造接受样本，证据完整 |

SIGTERM 保留现有隔离、超时和异常记录。偶发退出可独立重跑；若重复复现，再单列定位任务，不在本轮提前扩展工作范围。

## 八、模型、交付物与最终验收

### 模型策略

- 主模型仍使用 `agent_api.json` 中的 `gpt-5.6-sol`。
- 保持 auto 优先第一个 provider、服务失败后访问第二个。
- `glm-5.3` 作为显式对照，不与 provider 故障切换混在一起。
- 先检查服务是否提供该模型及图片、结构化输出能力；若不支持图片，不承担视觉检查任务。
- 不以“通过样本更多”单独判断模型更好，还需检查是否误判、漏检或越权宣布成功。

### 交付物位置

继续使用现有目录，不新增带版本后缀的平行实现：

`LastMileDataFlow/outputs/case_construction/<run_id>/`

主要交付：

- `template.json`：规范化模板。
- `contexts/.../`：局部图、编辑方向、资产、初态候选和编辑前观察。
- `samples/.../executable_edit.json`：实际编辑操作。
- `samples/.../rule_checks.json`：规则结果。
- `samples/.../rgb/`：编辑前后 head 和辅助 RGB。
- `samples/.../rgb/pair.json`：相机及配对信息。
- `samples/.../semantic_review.json`：可见变化检查和独立辅助意见。
- `samples/.../scene/`：接受的构造场景。
- `samples/.../task_validation/status.json`：明确标记尚未验证。
- `result.json`：构造接受数、失败分类和未验证事项。

计划确认后可直接覆盖原 [实施计划](LastMileDataFlow/docs/case-to-edit-pipeline-plan.md)，同步原设计和运行说明，不新增重复版本文件。

**本轮完成标准是三类场景的自动构造、检查和证据交付；不是已经证明底盘移动更好。**

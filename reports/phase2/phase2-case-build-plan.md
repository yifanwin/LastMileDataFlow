# 阶段二各 case 场景编辑构建方案

## 本次执行摘要

- 对照 `数据采集管线方案与计划.md`、[阶段二场景构建方案](phase2--plan-scene-editing-ruled-based.md) 与工作区中的阶段三代码，梳理四类 case（case1、case1.5、case2、case3）在**场景编辑构建**一侧的具体做法。
- 本次**只给设计方案，不改代码、不跑仿真**。文中对现有实现的所有描述均来自静态阅读，未做运行验证；涉及未提交文件的引用以工作区实际内容为准。
- 聚焦点是构建（阶段二）而非执行（阶段三）。阶段三只作为构建结论的下游消费者出现。

**建议结论：四类 case 不应继续共用"同一套候选生成 + 换惩罚项"的结构。应把 case 特化部分收拢到逐 case 的构造器，并为每条构建要求标注它是物理证据还是几何代理。**

## 一、现状与问题定位

当前 `src/lastmile_dataflow/construction/` 用四个文件承载全部四类 case：

| 文件 | 现状职责 |
|---|---|
| `config.py` | 参数白名单、必需参数、case2 把手标注校验 |
| `templates.py` | `requirements()` 统一做几何检查；`pending_hypotheses()` 给出待验假设 |
| `candidates.py` | 支撑区域网格 × yaw 候选，逐 case 附加惩罚项；case3 追加障碍操作 |
| `README.md` | 目录说明 |

四类 case 的差异只体现在三处：`templates.py` 的 `requirements()` 分支、`candidates.py` 里的 `penalty` 累加、`config.py` 的参数白名单。**这是"同一个模板换惩罚项"的结构。**

它能表达 case1 的几何意图，但不足以支撑另外三个 case，因为四者的困难来源不同：

| case | 困难来源 | 构建期可观测 | 构建期不可观测 |
|---|---|---|---|
| 1 | 目标离机器人初态远 | 目标位姿、支撑面、距离带宽 | 真机是否真的够不到 |
| 1.5 | 家具各侧通行/操作空间不对称 | 家具局部距离差、几何净空 | 是否真的通得过、差异是否真实 |
| 2 | 把手朝向与操作侧不匹配 | 把手几何、世界方向角 | 抓取是否真的落在把手上 |
| 3 | 抓取接近路径被挡 | 障碍位置、接近走廊几何 | 是否真的堵住规划、能否绕开 |

两个具体后果：

1. **候选的构造性被放到了排序阶段。** case1 的候选是整张桌面的均匀网格，再由 `distance_range_m` 惩罚筛出窄带。对 10k 场景这是纯浪费；对 case2，`direction_tolerance_rad` 很小时网格 yaw 根本采不到可行点。
2. **跨量纲线性加权。** `candidates.py` 把米（距离误差）与弧度（方向误差）按同一系数 `*100` 累加。量纲或量级一变，就会出现某一项压倒另一项，而排序结果表面上看仍然"合理"。

另有一处结构性隐患：`templates.py` 的 case1.5 净空用的是 `geom_rbound` 保守圆，代码注释已写明 "conservative_collision_bounding_circle_not_navigation"。**这个自我说明是对的，但它只是注释。** 一旦该代理过松，阶段三只会给出"case 不成立"的结论，而查不出是构建期的代理选错了。构建期与执行期之间缺少结构化的强度标注。

## 二、需要先补的共用层

建议在 `construction/` 下显式分层，而不是继续在 `templates.py` / `candidates.py` 里加 `if` 分支。

### 2.1 逐 case 构造器

每个 case 一个模块，暴露三个纯函数：

- **`preflight(config, world) -> ok | reject(reason)`**
  在加载重资产之前拒掉不成立的配置。例如 case2 没有可靠把手证据、case3 的障碍既不在可编辑列表也无法从资产池新增、case1.5 的 `frame_body` 不是家具或两侧向量不指向家具外侧。这类失败目前要等到 `requirements()` 抛错才发现，代价过高。

- **`generate(session) -> [candidate]`**
  只生成该 case 有意义的候选，不再共用一套全区域网格。构造性应体现在生成阶段，而非靠排序惩罚补偿。

- **`local_check(session, candidate) -> [requirement]`**
  每条 requirement 带 `strength` 字段：`physical`（真实静置/接触/穿透证据）与 `proxy`（仅由几何算出）。当前 case1.5 的注释应提升为结构化字段并进入交付报告，让"代理通过 ≠ case 成立"在数据里可见。

### 2.2 坐标系语义固定

四类 case 目前混用三种参照系：世界系（case1 距离、case2 `desired_direction_world`、case3 `approach_offset_m`）、家具局部旋转系（case1.5 的 `side_a` / `side_b`）、支撑区域局部系（`candidates.py` 中 `placement_pose` 的 region 局部 xy）。

**建议统一规则：凡是"相对某个家具或区域"的量，一律用该对象的局部系表达；只有"面向机器人的朝向"才用世界系。** 世界坐标作为 evidence 落盘，但不作为配置的输入语义。这条规则直接决定第五节 case3 的改法。

### 2.3 资产池补证据维度

`catalog/assets.py` 当前只有 `load` 与 `placement` 两个资格维度，而 `construction/config.py` 的 case2 要求 `handle` 带 `source` 且 `verified: true`。两者接不上：**把手标注目前只能手写进场景配置，无法支撑 10k 场景。**

建议把把手证据做成资产池的第三个维度（`handle`），场景配置只引用 `asset_id` 与摘要，不重复手写几何。同时**保持 `catalog/index.py` 已有的克制**——该文件明确区分 `discovered` / `parsed` / `missing_resources`，并注明 "metadata parent is not support proof"。把手证据也应遵循同一原则：`grasp_reference` 存在不等于把手可用。

## 三、case1：距离困难

已基本成立，建议只做两处收紧。

**构建内容**：桌面上的目标 + 合法机器人初态 + 目标到初态的水平距离落在 `distance_range_m` 内；支撑面、边缘余量、静置稳定性全部通过。

**第一处——距离语义来源要冻结。** `templates.py` 当前取 `sim.robot.group('base')`。这个值来自 build 配置的 `robot_base` 与构建会话的初始化。**必须冻结这次实际使用的 base，并把"距离是相对哪个 base 量的"写进 requirement evidence。** 否则阶段三换站位之后（`stations/sampling.py` 的 `place_base` 会覆盖 base），这条距离要求失去可追溯性，`validation/stations.py` 中 `case1_verdict` 用 `source_base` 判定 origin 的那一步也就没有对应的构建期基准。

**第二处——要求分两层，不再混在一起：**

- 层 A（case 无关的场景有效性）：目标在支撑面上、边缘余量、静置稳定、无严重穿透。由 `validation/placement.py` 与 `runtime/build_session.py` 承担，保持不动。
- 层 B（case1 构建意图）：距离带宽、高度带宽。

拆开后 `pending_hypotheses` 的归属更干净。`current_station_failure` / `alternative_station_success` 永远是假设；`case1_verdict` 已经实现了 origin 失败 + 其他站位物理成功 + `fail` 分支处理"初态本来就成功"，**不需要改动**。

**修复策略**：只允许移动目标（保持同一支撑面）或更换桌面候选；不允许改机器人初态来凑距离——那会让 `distance` 与 `robot_base` 互相定义。预算耗尽换场景。

**显式不做**：不在构建期断言"当前站位不可达"。保持 `unknown`。

## 四、case1.5：侧向差异

四个 case 里最容易"构建期通过、阶段三被否"，优先级应排在 case2、case3 之后。

**构建内容**：以某件家具（或跨越家具的一条通道）为 `frame_body`，在其局部系给出两个侧向参照点 `side_a` / `side_b`，要求两侧到目标的距离差 ≥ `min_distance_difference_m`，且一侧净空明显小于另一侧。

**三个具体问题：**

1. **侧向量语义不完整。** `config.py` 只校验了向量非零，未校验这两个点是否真的落在家具**外侧**、是否处于同一高度、是否指向自由空间。一个指向家具内部的向量同样能通过校验，并生成看起来"有距离差"的候选。建议 `preflight` 增加：侧点相对家具自身足印的外向性、两侧点高度与目标高度的一致性、家具本身位于房间可达区域。

2. **净空是 bounding circle 代理，偏松。** 用 `geom_rbound` 做保守圆时，椅子腿可能在圆内而实际通道仍能通过，也可能在圆外而实际被堵死。建议加一层**仍然廉价但更接近真实**的检查：在侧点上按少量离散 yaw 做 base 位姿的地面与碰撞查询（复用 `stations/sampling.py` 中 `floor_support` + `inside_triangles` 的思路，但在构建会话里只做几何查询、不执行），得到"该侧是否存在任一可站立的 base 位姿"。这依然是 proxy，但比圆更接近"能不能站"。

3. **两侧距离差的参照不一致。** 当前 `distances` 是侧点到目标中心的水平距离，`clearances` 是侧点到最近 geom 的距离，两者不是同一件事。同时要求 `min_distance_difference_m` 与 `min_clearance_difference_m` 时，排序惩罚可能把"距离差达标但净空差不达标"的候选推到前面，随后被 requirement 判 fail，白烧编辑预算。

**修复策略**：只允许移动目标（沿家具局部系的一个轴向外/向内平移），不允许同时改家具与机器人初态。多轮仍无法同时满足距离差与净空差则更换家具候选。

**假设要写全**：当前 `pending_hypotheses` 只有一条 `real_side_navigation_and_manipulation_difference`。建议拆成三条独立可验证的：北侧通行证据、南侧操作证据、西侧成功证据。这与总方案"case1.5：分别记录北侧通行、南侧操作、西侧成功证据"一致，也便于阶段三给出分侧结论而非一个总体 unknown。

**坐标系硬约束**：`frame_body` 与 `side_a` / `side_b` 必须在报告中落成"家具局部向量 + 解析出的世界坐标"两份。当前 evidence 只有世界坐标，可读但无法在场景重新加载后复核。

## 五、case2：把手朝向与操作侧不匹配

真正瓶颈不在几何，而在"可靠把手标注从哪来"。必须先解决，否则构建跑不起来。

**构建内容**：选一个把手几何清楚的 mug，旋转它使把手世界朝向落在 `desired_direction_world` 容差内，且旋转后仍稳定落在原支撑面上。**不做平移**——case2 的意图是"物体位置合理，只有朝向不对"。

**三件事：**

1. **把手标注的获取路径。** `config.py` 当前强制 `handle.source` 非空且 `verified: true`，本质是要求人手写。建议改成两条独立证据交叉确认，写进资产池而非场景配置：
   - 路径 A（结构）：从资产 XML 的 body 树找出把手子构件（`templates.py` 已在查 `descendants`），取其局部轴。
   - 路径 B（行为）：从该资产的 grasp 文件观察抓取分布——若存在一簇抓取点沿某轴明显偏离杯体中心，则指向把手。

   两条路径方向一致才允许标 `verified`，两边证据都存档。**只有单侧证据一律降级为未验证，不允许当作把手抓取。** 这与总方案"存在 grasp 文件，不等于当前场景可抓"一致。

2. **方向候选改为解析求解。** 当前是在 yaw 候选上附加朝向误差惩罚。建议由 `handle.axis_local` 与 `desired_direction_world` 直接解出所需 yaw，再加容差邻域内的少量扰动候选。既省候选预算，也避免容差很小时采不到可行点。

3. **旋转后的落位检查要单独看。** 杯子旋转后可能出现：把手伸出桌沿、把手插进邻近物体、杯体因摩擦变化而滑移。三条都不能用通用落位检查覆盖。建议 case2 的 `local_check` 增加两条针对性检查：把手构件在旋转后位于支撑面之上且不越出支撑面边界；把手与邻近资产的间距不小于由 asset 参数化的容差。**不使用全局绝对穿透阈值**——总方案已明确不建议所有资产共用绝对阈值，且 `config.py` 的 `BuildProtocol` 当前把 `penetration_m` 等做成全局常量，case2 需要的是资产级参数。

**修复策略**：优先小幅 yaw 增量重解，不换资产（换资产会改变 instance ID，使 `scene_version` 与阶段三的 grasp 绑定失效）。朝向可行但落位不稳时回滚到上一个稳定朝向，把该资产标为"朝向代价高"并更换 mug 候选。

**阶段三假设**：保留 `real_handle_grasp_success`，但建议在构建包里同时冻结"把手区域的 body 名与几何"，供阶段三在 `validation/pick.py` 中核对抓取接触点确实落在把手构件上。否则阶段三只能记录"抓取成功"，无法区分杯身抓与把手抓。

## 六、case3：抓取路径障碍

与现有代码复用度最高的一个（支撑区域、资产池、`add` 操作均已具备），建议排在 case1 之后优先做。

**构建内容**：目标不动（`candidates.py` 已有 `no_target_edit` 分支），在其接近侧放置或移动一个障碍，使正面直取走廊被挡，而侧向/绕行仍留有理论空间。

**四个问题：**

1. **接近走廊用世界系偏移表达。** `approach_offset_m` 是世界系向量，而目标可被旋转移动、支撑面随房屋变化。世界系偏移跨场景复用会失效。建议改为**支撑区域局部系的相对方向 + 距离带**（`obstacle_distance_range_m` 保留），世界坐标只在 evidence 中落盘。与 2.2 的坐标系规则一致。

2. **新增障碍的高度计算是启发式。** 当前用 `region.height - (body_points 最低点 - root xpos)` 再 `+.003`。建议障碍放置同样走**区域局部系**：先按区域局部 xy 求候选，高度由区域高度确定，用与目标相同的 `placement_pose` 逻辑生成位姿，再由真实静置验证。新增资产的失败模式（脚陷进桌面、悬空掉落后静止）正是 `runtime/build_session.py` 静置检查要覆盖的，不应在生成阶段用启发式替代。

3. **"可绕行"缺少构建期证据。** 当前只检查障碍与目标的距离带，意味着一个把目标彻底围死的障碍也能通过构建。建议增加一条廉价的构造性约束：在支撑区域内沿目标周向，至少存在 N 个"无遮挡接近候选"（从该方位出发的接近线段与障碍不相交）。这条约束不需要规划器，纯几何即可，但它是构建期唯一能拿到的"可绕行"凭证，仍标为 `proxy`。

4. **必须保护障碍不被修复清掉。** `config.py` 已有的 `editable` 与 `protected` 互斥校验，但 case3 的障碍是**构建过程中新增**的，新增时是否进入 `protected` 需要显式决定。若不处理，修复轮次的"删除资产"操作可能直接删掉障碍，于是构建通过、case 意图消失——这恰好对应参考文档列出的必测故障"修复破坏先前已通过的朝向或保护要求"。**建议障碍一经提交即自动加入保护，任何触及障碍的修复都记为一次显式编辑并进入 evidence。**

**阶段三假设**：`real_planning_path_obstructed` / `possible_bypass` 保留，但建议增加**分站位归因**要求：原地失败、近站位失败、绕行站位成功三者分开记录。总方案"case3：区分原地绕障可解、需要换站位、尚未找到解"就是这个意思；只写两条假设会让阶段三无法区分"障碍有效但换站位可解"与"障碍根本没起作用"。

## 七、跨 case 的构建流程与证据链

### 7.1 流程

```text
preflight（逐 case 轻量校验，拒掉不成立的配置）
      ↓
零编辑检查（当前场景已满足 case 要求？满足则跳过编辑，仍做完整验证）
      ↓
逐 case generate()（生成该 case 有意义的、小范围的候选）
      ↓
逐 case 排序（同类量纲比较，不做跨量纲线性加权）
      ↓
事务执行 → 真实静置 → local_check（标注 physical / proxy）
      ↓
修复（最多 2–3 轮，逐 case 的修复方向白名单）
      ↓
冻结 → 独立恢复 → 交接阶段三
```

**零编辑检查要显式化。** 总方案与阶段二方案都写明"不是每个场景都需要编辑"。当前 `candidates.py` 里只有 case3 的 `no_target_edit` 特例，case1、case2、case1.5 没有统一入口。建议把"零编辑即满足"做成每次构建的第一个分支，并在构建记录里明确 `edited: false`——这既是省预算的手段，也产生一批合法的 case1/case2 样本。

### 7.2 逐 case 追加冻结的证据

| case | 追加证据 |
|---|---|
| 1 | 冻结的 base、目标位姿、支撑区域 id 与边界、实测距离及其测量来源 |
| 1.5 | `frame_body` 的局部向量与世界坐标、两侧距离与净空、净空所用代理方法名 |
| 2 | 把手标注的两条来源证据、把手构件 body 名、旋转前后世界方向角、旋转增量 |
| 3 | 障碍 body 名与新增来源、走廊在区域局部系的表达、周向无遮挡候选数、障碍进入保护的记录 |

### 7.3 要求带 `strength` 字段

`physical` / `proxy` 分组，并让 `exporting/station_report.py` 按该字段展示。这样"未测范围"与"仅代理通过"在交付报告中成为两张明确清单。该文件的现有结尾已经写明"未测试/预算耗尽保留 unknown。当前只支持 case1 普通抓取"，当前是散文描述；结构化之后不必靠读者推断。

## 八、实施顺序与验收门槛

| 优先级 | 内容 | 理由 |
|---|---|---|
| 1 | 冻结共用接口：逐 case 构造器 + `strength` 字段 + 坐标系规则 | 四个 case 都要用，且不改变 case1 的现有外部行为 |
| 2 | case1 的两处收紧（base 冻结、要求分层） | 现成闭环，改动小，能立刻验证接口是否合适 |
| 3 | case3 | 与现有支撑区域、资产池、`add` 复用度最高，能立刻触发新增资产的静置与保护检查 |
| 4 | case2 的资产池把手证据与标注交叉验证 | 最长的一条依赖，越早开始越好；先做证据链，再接候选生成 |
| 5 | case2 的 yaw 解析求解与旋转后落位检查 | 依赖第 4 步 |
| 6 | case1.5 | 最容易"构建通过、阶段三被否"，放最后，等前三个 case 的 proxy/physical 分层跑顺 |

### 必测故障（在参考文档 8 条之外，为四个 case 各加一条）

| case | 故障 | 期望行为 |
|---|---|---|
| 1 | 冻结 base 被绕过，距离改用当前 base 计算 | 拒绝或把测量来源标为不一致 |
| 1.5 | `side_a` / `side_b` 指向家具内部 | preflight 拒绝，不生成候选 |
| 2 | 把手标注只有单侧证据 | 拒绝标 `verified`，不得作为把手抓取依据 |
| 3 | 修复流程删除障碍 | 删除被保护拦截，或记为显式编辑并留证 |

这四条都属于"能通过现有校验但构建意图不成立"，是当前结构下最可能漏掉的一类。

### 验收门槛

沿用阶段二方案 2C 的口径，不新设缺乏试跑依据的统一成功率目标。构建产出率与速度在错误被正确阻断之后再衡量。

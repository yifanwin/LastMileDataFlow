# 数据管线重构提议：围绕“底盘移动后是否更好”的 Case 工厂

更新：2026-10-07（第三版）。第二版起以“底盘移动后是否更好”为统一目标，任务构造分为“不编辑场景”和“编辑场景”两个分支。第三版的变化：只使用纯场景，不使用 benchmark；正式运行用 train 集，初步调试用 val-103；`same_edge` 单独保存为一类；新增第十节，评估程序化能力和 Agent 的作用。第四版：新增 RBY-1 抓取候选生成模块（D），新增 10.5 节“合理性复核的判定方法”，并记录 Agent 插件优先级等确认事项。**本文是提议，没有修改代码、配置或已有结果。**

评估对象是 [v2 方案](case-edit-v2-plan.md)、[v2.5 修正计划](case-edit-v2.5-plan.md) 所描述的 case 构造管线，以及它与阶段三、四的衔接。四类 case 的具体定义见 [Case 描述具体化提议](case-definition-proposal.md)（下称“定义提议”）。

## 摘要

1. **统一目标：每个任务都要回答“底盘移动后是否更好”。** 判定方法是同一目标、同一预算下的**配对比较**：起点 S0 不移动底盘（对照）和移动到另一站位 S1（实验）。case1、1.5、2、3 是对“起点为什么不好、需要怎样移动”的四种归因，不是四套互不相干的流程。
2. **任务构造分为两个分支，共用同一套验证：**
   - **分支 N：不编辑场景。** 只使用纯场景，不依赖 benchmark 的任务或起点。场景保持原样，只选择目标和起点 S0。做法是先画出原始场景的站位图，再从“成功站位”反推出合理的“失败起点”。成本低，场景天然，优先使用。
   - **分支 E：编辑场景。** 当原始场景找不到满足条件的组合，或者某类 case 自然出现得太少（预计 case1.5 最明显）时，按配方编辑场景，再走同样的验证。
3. **机制验证放在流程中心。** 现在的硬验收是“物理合法 + 前后图有变化”，与“移动后是否更好”无关；阶段三已有的站位采样、cuRobo、严格物理执行，正是做配对比较所需要的工具，应当接进构造流程。
4. **由程序生成候选，Agent 只少量参与。** 去掉 Agent1，合并 Agent2 和 Agent3；Agent 只做可选的布局合理性复核。默认在数据集上批量运行，单场景只用于调试。

## 一、现状诊断

### 1.1 结果

| 指标 | 实际 |
|---|---|
| 三类 case 的真实运行 | case1 构造接受 1 个，case1.5 和 case3 都是 0 个 |
| 每轮成本 | 900 s 硬期限，4–8 次 Agent 调用，单次调用约 60 s 以上 |
| `case_verified_count` | 全部为 0：没有一个样本验证过“移动后更好” |
| 已接受的 case1 样本 | 把盐罐挪到锅铲后侧；既没有说明起点为什么不好，也没有说明移动后为什么更好 |
| 只改起点的路线 | 现管线没有这条路线；旧管线 `case1-cup-001` 走的正是这条路（原样筛选 → 只移动机器人起点 P131），并取得 3 次试验 3 次成功 |

### 1.2 结构性原因

| 原因 | 表现 |
|---|---|
| **目标函数错位** | 硬验收只看物理合法和前后图变化，没有任何一项比较“不移动”和“移动后” |
| **默认必须编辑** | 流程从一开始就要求产生编辑；场景本身已经满足条件时，没有直接采用的路径 |
| **机制验证被推迟** | M13 被列为后续，`construction_only` 成了唯一的运行模式 |
| **抽象描述直接交给 Agent** | Agent1 输出的 `requirements` 和 `parameters` 为空，Agent3 自己编世界坐标范围 |
| **为 Agent 补信息的机制过于复杂** | 动态补图、扩展上下文、格式修复占了大部分开发量和调用预算 |
| **单场景硬约束** | val-103 可能根本没有合适的几何条件，所有重试却只能在这个场景里打转 |

## 二、统一目标：“底盘移动后是否更好”的配对比较

### 2.1 三组条件

对同一个冻结场景、同一个目标、同一组抓取候选和同一份预算，分别求：

| 条件 | 底盘 | 其他自由度 | 作用 |
|---|---|---|---|
| **C0 不移动** | 固定在 S0 | 左右臂都可用，躯干在允许范围内，所有抓取候选都可用 | 对照：证明“在原地怎么调都不行” |
| **C-yaw 原地转向** | 位置固定在 S0，只改朝向 | 同 C0 | 对照：排除“原地转个身就能解决”的情况 |
| **C1 平移后** | 移动到 S1 | 同 C0 | 实验：证明“移动后可行或更好” |

C0 必须给出公平的对照：不能锁死某只手臂、限制躯干，或者用更少的抓取候选，人为制造困难。

### 2.2 “更好”的三个等级

| 等级 | C0 和 C-yaw | C1 | 用途 |
|---|---|---|---|
| **L1 规划级** | 预算内无解 | `plan_ok=true` | 构造阶段的判定，成本较低 |
| **L2 执行级** | 无解，或严格执行失败 | strict-pick-v3 严格执行成功 | case 成立的正式证据 |
| **L3 成功率级** | 多次执行成功率低 | 多次执行成功率明显更高 | 后续接入；次数和门槛待定 |

此外 S1 必须**能从 S0 到达**。构造阶段先检查地面上存在一条无碰撞路径；阶段四再做真实的连续导航。

### 2.3 移动类型和 case 归因

每个通过比较的组合，都记录两个标签：

**移动类型**（参考 [lastmile case 构建方案](<../../../lastmile case 构建方案.md>) 2.3 节）：

| 移动类型 | 含义 | 处理 |
|---|---|---|
| `yaw_only` | 原地转向就能解决 | 不算“移动后更好”，只保存为对照 |
| `same_edge` | 沿同一条边平移就能解决 | 不算 case1；**单独保存为“同边平移类”**（归因为“够不着”时记作 case1-S），同样经过配对比较和严格执行 |
| `switch_edge` | 必须换到另一条边 | case1 和 case1.5 的要求 |

**case 归因**：起点为什么不好。

| 归因 | 判定 | 对应 case |
|---|---|---|
| 够不着 | C0 中 `reach_ok=false` | case1；case1.5 的 B 侧 |
| 站不下 | A 侧 `standable=false`，且地面有缝但太窄 | case1.5 的 A 侧 |
| 把手朝向 | 只抓把手时失败，抓杯身成功 | case2 |
| 路线被挡 | `reach_ok=true` 但 `plan_ok=false`，移除通道杂物后成功 | case3 |
| 其他 | 移动后更好，但不符合以上任何一种 | 保存为“未归类”，供人工查看是否需要新的 case 类型 |

## 三、新的总体流程

```text
 [离线，一次性]
 A. 机器人能力标定（可达范围表）
 B. 场景几何索引（支撑面、各边、地面带）
 C. 资产库索引（THOR / Objaverse 尺寸、把手标注）
 D. RBY-1 抓取候选生成（按资产缓存）
 CaseSpec（人写，每类一份）
                 │
                 ▼
 1. 前提检索：从数据集中找“场景 + 支撑面 + 目标”候选（程序，毫秒级）
                 │
                 ▼
 2. 原始场景站位图（共用）：按边采样站位 → reach_ok → plan_ok
                 │
       ┌─────────┴──────────────────────────────┐
       ▼                                         ▼
 ┌─────────────── 分支 N：不编辑 ───────┐   ┌─────────────── 分支 E：编辑 ─────────┐
 │ 3N. 从成功站位反推失败起点            │   │ 3E. 按配方生成编辑（程序）             │
 │     在站位图的失败区域里，             │   │     利用原始站位图决定往哪里改         │
 │     挑出合理的 S0                      │   │ 4E. 代理预筛（几何 + 可达范围表）      │
 │                                        │   │ 5E. 物理编辑与静置（现有事务）         │
 │                                        │   │ 6E. 编辑后重新生成站位图               │
 │                                        │   │ 7E. 在新站位图上选择 S0                │
 └───────────────────┬────────────────────┘   └───────────────────┬────────────────────┘
                     └───────────────┬──────────────────────────────┘
                                     ▼
 8. 配对比较：C0 / C-yaw / C1 → 等级 L1、L2 → 移动类型 + case 归因
                                     ▼
 9. 视觉合理性复核（Agent，可选，只看通过比较的组合）
                                     ▼
 10. 冻结 → 数据采集：严格执行、S0→S1 导航示教、VLA 评测
```

**路由规则：**

- 每个候选先走分支 N。原始场景的站位图只算一次，两条分支共用。
- 满足以下任一情况时，转入分支 E：
  - 分支 N 找不到满足条件的 S0；
  - 某类 case 的配额不够（例如 case1.5 很少自然出现）；
  - 需要补充多样性，比如某一类目标或某种桌型太少。
- 分支 E 的编辑**从原始场景出发**，不在其他候选的编辑结果上累积修改。
- 两个分支的结果使用同一套比较、复核和冻结流程，输出格式相同，只是来源标签不同（见第五节）。

**设计原则：越便宜的检查越早做，越贵的计算只给越少的候选。** 不编辑的路线比编辑便宜：不需要静置，不需要重新建站位图，也没有布局是否自然的问题，所以排在前面。

## 四、各模块说明

### A–D. 离线准备

| 模块 | 内容 | 现状与改动 | 运行位置 |
|---|---|---|---|
| **A. 机器人能力标定** | 在 RBY-1 底盘坐标系下，对目标相对位置、躯干高度、抓取朝向做逆运动学采样，得到可达范围表；同时记录底盘足迹、夹爪宽度和开口 | 新增；[rby1.json](../../configs/robots/rby1.json) 目前没有这些量 | GPU 服务器，一次性 |
| **B. 场景几何索引** | 每个支撑面的尺寸、高度、各边外侧地面带的宽度和深度、面上物体 | 扩展现有 `catalog/index.py`（SQLite）和 `scenes/geometry.py` | 2080 可做（静态解析） |
| **C. 资产库索引** | THOR 和 Objaverse 资产的尺寸、能否加载；落地障碍物按足迹分档；杯类资产的把手标注 | 扩展 `catalog/library.py`；Objaverse 需要坐标轴和尺度适配 | 2080 可做；加载验证在 GPU 服务器 |
| **D. RBY-1 抓取候选生成** | 为每个可当目标的资产生成 RBY-1 夹爪的抓取候选，按资产缓存 | **新增**；已确认 DROID 抓取文件不适用于 RBY-1，也没有现成工具或数据 | GPU 服务器，每个资产一次 |

**D 的做法：**

1. **夹爪参数**：从 RBY-1 模型读取手指宽度、长度和最大开口，写入机器人能力配置（与 A 共用）。
2. **几何采样**：在资产碰撞网格表面采样点对，要求两点法向大致相对（在摩擦锥内），两点距离小于最大开口减去余量；再绕两点连线采样多个接近方向和接近深度。
3. **几何过滤**：在 MuJoCo 中单独放置夹爪模型，检查预抓取位姿和抓取位姿下夹爪与物体不穿透。
4. **仿真过滤**：物体放在平面上，夹爪闭合后抬升并做小幅晃动，保留物体不滑落的抓取。这一步只用于筛选候选；任务中是否成功，仍以 strict-pick-v3 在真实场景中的执行为准。
5. **输出**：物体坐标系下的抓取位姿、开口宽度和质量分数，连同资产版本和夹爪配置摘要一起缓存。case2 需要的“只抓把手”子集，由 ① 资产标注给出的把手区域筛选得到。
6. **代码位置**：新增领域模块，建议命名为 `grasping/`，不放进 `workflows/`。

**验收**：先覆盖 THOR 中常见的可抓类别（杯、碗、瓶、罐、水果等）；随机取几个资产，在真实场景的站位上用 strict-pick-v3 执行，确认生成的抓取能真正抓起来。

**CaseSpec**：即定义提议中的操作化定义，存放在 `configs/case_specs/<case>.json`。本版增加三项：
- 归因规则；
- 移动类型要求（case1 和 case1.5 必须 `switch_edge`；case2 和 case3 至少 `same_edge`，并且排除 `yaw_only`）；
- 编辑配方，只供分支 E 使用。

### 1. 前提检索

用 CaseSpec 的前提查询场景几何索引，输出排好序的“场景 + 支撑面 + 目标”候选，并按桌型、房间类型、目标类别打散。不同 case 的前提不同：

- case1：支撑面足够深，目标到某条边的距离可能超出可达范围；
- case1.5：至少三条边外侧是地面；
- case2：场景里有带把手的杯子，或者可以放入杯子；
- case3：台面上已有一定数量的物体。

### 2. 原始场景站位图（两个分支共用）

复用 `stations/sampling.py`、`planning/curobo.py`：

1. 沿支撑面每条边的外侧地面带采样站位：朝向目标，覆盖多个位置和朝向，并做初始化检查。
2. 先对全部合法站位求 `reach_ok`，用逆运动学，速度快。
3. 再对其中一部分站位求 `plan_ok`，用 cuRobo：`reach_ok` 的站位优先，边界附近加密。

输出就是阶段三的站位图，每个站位带有：边、位置、朝向、`standable`、`reach_ok`、`plan_ok`。

### 3N. 分支 N：从成功站位反推失败起点

这是旧管线 7.1 节“成功站位反向配失败起点”的自动化版本：

1. 在站位图中找成功区域 R+（`plan_ok=true`），要求有一定余量，不能只有一个极限点。
2. 在失败区域里，按 CaseSpec 的归因规则挑选候选起点 S0。S0 必须是**合理的起点**：
   - 位于某条边的贴边操作带内，而不是故意停在远处；
   - 朝向目标，head 相机能看到目标；
   - 初始化合法。
3. 检查移动类型：S0 原地转向不能解决；对 case1 和 case1.5，S0 所在边的其他贴边站位也都要失败。
4. 检查 S0 到 R+ 中某个 S1 之间存在无碰撞的地面路径。
5. 只使用纯场景：目标从场景中现有的可抓物体里选（按类别白名单、尺寸、是否有抓取候选筛选），起点 S0 由程序选，不读取 benchmark 的任务、起点或成功标签。

各类 case 在分支 N 中的预期：

| case | 不编辑时的可能来源 | 预期产出 |
|---|---|---|
| case1 | 深桌、长台面、靠里放置的目标 | **较多**；旧管线已有先例 |
| case1.5 | 一侧靠墙或有椅子、但留有窄缝的桌子 | **较少**，主要依赖分支 E |
| case2 | 场景中原本就有带把手的杯子，选择把手背对的一侧作为 S0 | 取决于场景中有多少带把手的杯子 |
| case3 | 原本就杂乱的厨房台面 | 中等 |

### 3E–7E. 分支 E：编辑场景

1. **按配方生成编辑**，直接利用原始站位图决定往哪里改，例如知道成功区域在哪一侧，就把目标往远离另一侧的方向移。按改动从小到大的顺序尝试（参考旧管线步骤 4 的优先级；这里只是尝试顺序，不是最小编辑约束）：

   | 顺序 | 操作 | 主要用于 |
   |---|---|---|
   | 1 | 旋转目标 | case2 |
   | 2 | 在同一支撑面上移动目标 | case1、case1.5 |
   | 3 | 移动或增加台面物体，进入抓取通道 | case3 |
   | 4 | 移动或增加落地障碍物，进入地面带 | case1.5 |
   | 5 | 替换目标资产 | case2（换成带把手的杯子） |

2. **代理预筛**：用几何量和可达范围表排除明显不行的参数组合。
3. **物理编辑与静置**：保持现有事务、静置、支撑、穿透、稳定检查和回滚，直接复用 `construction/compiler.py`、`sampling.py`、`runtime/build_session.py`。
4. **重新生成站位图**：只在受编辑影响的边和区域重算，其他区域沿用原始站位图。如果编辑改变了碰撞世界，受影响的 `plan_ok` 必须重算。
5. **选择 S0**：方法同分支 N 的第 2–4 步。

### 8. 配对比较（两个分支共用）

1. 对 S0 求 C0 和 C-yaw，对 S1 求 C1，使用同一份抓取候选和预算。
2. 按需做反事实对照，都在构建会话中完成并回滚：
   - case3：移除通道内杂物，S0 成功；
   - case2：去掉“只抓把手”的限制，S0 能抓杯身。
3. 先判定 L1；L1 通过后，在 S1 和 S0 上各做严格物理执行，判定 L2。
4. 输出移动类型、case 归因、等级和全部证据。

### 9. 视觉合理性复核（Agent，可选）

具体的输入、检查项、汇总规则和校准方法见 10.5 节。

- 只对通过比较的组合调用，每个组合最多 1 次。
- 输入是固定的一组相机图和程序生成的事实摘要。
- 判断两件事：布局是否自然；有没有程序遗漏的明显错误。
- 对分支 N，重点看 S0 作为起点是否合理；对分支 E，重点看编辑后的布局是否自然。
- 结论为 `implausible` 时淘汰该组合，不触发重新编辑。

### 10. 冻结与数据采集

- 冻结场景版本、S0、S1、站位图、比较结果和来源标签。
- 阶段四：从 S0 连续导航到 S1，到站后抓取，生成示教轨迹；对 VLA 做起点评测。`navigation/` 目前只有 README，是之后的主要开发量。

## 五、数据记录：标明来源

每个冻结的任务都记录：

```text
construction_branch : unedited | edited
                      （不编辑场景，只选起点 | 编辑场景）
edits               : 编辑清单（unedited 为空）
move_type           : yaw_only | same_edge | switch_edge
attribution         : reach | standing | handle | corridor | unclassified
improvement_level   : L1 | L2 | L3
S0, S1, station_map, comparison_evidence
```

这样数据的使用者可以区分：

- 自然分布：`unedited`；
- 合成构造：`edited`。

训练或评测时可以分开统计。

## 六、对 v2、v2.5 各模块的处理建议

| v2 模块 | 处理 | 说明 |
|---|---|---|

| 风险 | 应对 |

## 十、评估：程序化能否完成整套管线，Agent 在哪里有优势

### 10.1 结论

- **主链路完全可以程序化。** 从检索、站位图、选择起点、编辑、静置，到配对比较、严格执行和导航示教，判断依据都是几何和物理量，程序算得更准、更便宜，也可以复现。现有运行已经说明，让 Agent 判断尺寸、坐标、能否站下，效果并不好。
- **Agent 不应当出现在“是否成立”的判定路径上。** 它的优势在**语义层面**：资产理解、布局是否自然、场景语义的组合、任务语言，以及离线分析失败和起草新配方。
- **管线必须在关闭全部 Agent 时也能完整运行。** Agent 作为可选插件接入，每个插件都通过开/关对照（A/B）来证明自己有收益，再决定是否默认开启。

### 10.2 各环节逐项评估

| 环节 | 程序能否独立完成 | 主要难点 | Agent 能否帮上忙 |
|---|---|---|---|
| 机器人能力标定 | 能 | 采样覆盖率和计算量 | 不需要 |
| 场景几何索引 | 能 | ProcTHOR 元数据中支撑关系不一定可靠，需要几何复核 | 不需要 |
| 目标选择（纯场景） | 基本能：按类别白名单、尺寸和是否有抓取候选筛选 | **RBY-1 抓取候选需要自行生成**：已确认现有 DROID 抓取文件不适用于 RBY-1 夹爪 | 可以帮忙判断“这个物体是否适合作为抓取目标”（太大、固定在家具上、易碎等），离线做一次，结果缓存 |
| 资产索引与标注 | 尺寸、能否加载：能。语义：不能 | Objaverse 类别标签较乱；把手、盖子、正面这些部件语义，程序拿不到 | **有明显优势**：对资产的渲染图做视觉识别，标出把手、盖子、类别是否正确；每个资产只做一次，再人工抽查 |
| 前提检索 | 能 | — | 不需要 |
| 站位图、选 S0、配对比较、严格执行 | 能，而且必须由程序做 | GPU 成本 | **不应参与判定** |
| 编辑配方（分支 E） | 几何部分能 | 随机采样得到的布局语义单调，有时不自然（例如浴室用品出现在餐桌上，椅子背对桌子） | **有优势**：选择语义上合理的杂物组合、障碍物种类和摆放方式；几何参数仍由程序采样和验证 |
| 布局是否自然 | 只能靠规则部分近似（房间–类别共现统计、朝向规则） | 整体观感难以写成规则 | **有优势**：看图判断，作为过滤器 |
| S0 是否像合理起点 | 基本能（贴边、朝向、可见） | — | 作用小，可以合并进布局复核 |
| 导航示教（阶段四） | 能（地面占据图 + A* + 控制器；旧管线已有 A* 连续导航的先例） | 控制器调试 | 不需要 |
| 失败归因 | 大部分能（strict-pick-v3 已有逐项指标） | 少数复杂失败难以自动分类 | 可选：看失败视频辅助分类，只作为附加标注 |
| 任务语言描述 | 只能用模板，句式单一 | 指代消歧（同类物体有多个时） | **有明显优势**：生成多样的自然语言指令；由程序检查指代是否唯一 |
| “未归类”样本分析、新 case 类型 | 不能 | 需要归纳 | **有优势**：离线批量分析，起草新 CaseSpec 或配方，人审核后入库 |

### 10.3 Agent 能不能提高多样性

多样性有几个不同的维度，Agent 只在其中一部分有作用：

| 维度 | 主要来源 | Agent 的作用 |
|---|---|---|
| 房屋和布局 | train 集 1 万个房屋，检索时按房型、桌型分层抽样 | 基本没有，**这是最大的多样性来源，靠程序** |
| 起点和站位 | 站位图上的分层采样 | 没有 |
| 机制组合（归因 × 移动类型） | CaseSpec 配额 | 没有；新类型的发现靠离线分析 |
| 目标物体 | 场景中现有物体，以及分支 E 中替换的 THOR/Objaverse 资产 | **有一些**：在 Objaverse 的长尾类别中挑选语义合理的目标 |
| 编辑的语义组合（分支 E） | 配方的随机采样 | **有优势**：可以给出“早餐后的餐桌”“堆着书的书桌”这类主题，组合出语义连贯又各不相同的杂物布局 |
| 任务语言 | 模板 | **明显优势** |

需要注意两点：

1. **大模型的选择容易趋同**，比如反复挑杯子、椅子这类常见物体。所以应当由程序控制配额和分层：程序告诉 Agent 哪些类别已经用得多、这次要从哪个子集里选，Agent 只在子集内部做语义上的挑选。
2. **多样性需要实测。** 建议在 R5、R6 阶段做一次对照：同一批候选分别用纯程序随机采样和“程序 + Agent”生成，比较以下指标：
   - 类别熵；
   - 布局特征的分布；
   - 合理性复核的通过率；
   - 每个 L2 任务的成本。

   用数据决定是否默认开启 Agent，不先入为主。

### 10.4 建议的 Agent 位置

| 位置 | 时机 | 调用频率 | 输出 | 是否影响“成立”判定 |
|---|---|---|---|---|
| ① 资产语义标注 | 离线 | 每个资产 1 次，缓存 | 类别校正、把手/盖子位置、是否适合作为目标 | 否；把手标注需人工抽查后才用于 case2 |
| ② 编辑语义规划（分支 E） | 在线 | 每个候选最多 1 次 | 从程序给出的子集中选资产和摆放主题 | 否；几何由程序采样和验证 |
| ③ 布局合理性复核 | 在线 | 每个通过比较的任务 1 次 | plausible / implausible / unknown | 只能淘汰，不能让不成立的任务通过 |
| ④ 任务语言生成 | 冻结后 | 每个任务 1 次，可批量 | 多条自然语言指令 | 否；程序检查指代唯一 |
| ⑤ 离线分析 | 每批运行后 | 每批 1 次 | 失败聚类、“未归类”样本的模式、新配方草稿 | 否；人审核后入库 |

按 train 集的规模估算，如果每个任务调用 Agent 超过 2 次，每次约 60 s，调用本身就会成为主要成本。所以①和⑤放在离线；②和③只对少量候选调用；④可以批量处理。

**已确认的接入顺序**：先接 ① 资产语义标注（case2 需要）和 ③ 布局合理性复核（R6）；②、④、⑤ 在主链路跑通后，再做 A/B 对照（R9）。

### 10.5 合理性复核（③）的判定方法

**原则：Agent 只逐项打分，不给总体结论；只能淘汰，不能放行；判定规则写在程序配置里，上线前用人工标注的样本校准。**

**职责边界**

- 不交给 Agent：物理稳定、穿透、支撑、起点合法性、目标可见像素、可达、规划、成败、“移动后是否更好”。这些以程序结果为准，Agent 不能推翻。
- 交给 Agent：程序难以写成规则的视觉和语义问题，即“看起来像不像真实家里会出现的样子，有没有明显异常”。
- 调用时机：配对比较达到 L1 之后，每个任务 1 次；只用于淘汰，不触发重新编辑。

**输入（固定，不补图）**

1. 固定相机组：S0 处的头部相机图、支撑面及周围俯视图、每条相关边的斜视图。编辑场景分支提供每个视角的编辑前、编辑后两张图。
2. 编号标记：在图上给目标、被编辑和新增的物体画框并标编号，让 Agent 能明确指出是哪个物体。
3. 程序事实摘要：房间类型、支撑面类别、目标类别；被编辑或新增物体的类别、尺寸和操作；S0 相对桌边的位置和朝向。
4. **不提供**规划结果和成败，避免 Agent 先入为主。

**检查项**

| 编号 | 检查内容 | 适用分支 | 严重程度（初始设置） |
|---|---|---|---|
| P1 | 渲染和资产异常：贴图缺失、尺度明显不对、网格破损、可见穿插、画面全黑 | 两个分支 | 阻断 |
| P2 | 摆放姿态：目标和被编辑物体是否以正常姿态放置（杯子没倒扣或侧躺，椅子没背对桌子或倒地） | 两个分支 | 阻断 |
| P3 | 场所语义：物体出现在这个房间、这个支撑面上是否说得通 | 重点看编辑场景分支 | 明显不合理时阻断，轻微的只标记 |
| P4 | 目标可辨识：头部视角里能否认出目标，有没有同类物体造成指代不清 | 两个分支 | 标记（影响任务语言） |
| P5 | 起点观感：机器人看起来是否像正常走近桌边准备操作，而不是卡在角落或对着墙 | 重点看不编辑分支 | 阻断 |
| P6 | 编辑是否刻意：**和编辑前相比**，编辑后是否明显更不自然（杂物排成直线、椅子正好横着堵住窄缝、台面密度远超正常家庭） | 只用于编辑场景分支 | 先只标记，校准后再定 |

P6 采用编辑前后对比的问法，以抵消 ProcTHOR 原始场景本身不完全自然的基线偏差。

**输出与汇总规则**

Agent 对每项输出 `pass / fail / unknown`、理由、依据的视图和涉及的物体编号。总体结论由程序汇总：

| 情况 | 结论 | 处理 |
|---|---|---|
| 任一阻断项为 `fail` | `implausible` | 淘汰，记录原因 |
| 阻断项中有 `unknown` | `unknown` | 保留，进入人工抽检队列；不补图重试 |
| 阻断项全部 `pass`，只有标记项 `fail` | `plausible` 加标记 | 保留，标记写进数据供使用者筛选 |
| 全部 `pass` | `plausible` | 保留 |

哪些项属于“阻断”写在配置文件里，可根据校准结果调整。

**校准与监控**

1. 金标准样本约 100–200 个任务：包括两个分支的正常样本，以及故意构造的坏样本（倒扣的杯子、放大 3 倍的资产、放错房间的物体、背对桌子的椅子、对着墙的起点）。
2. 按检查项分别统计误杀率和漏检率。不编辑分支的原始场景应当很少被淘汰；一致性差的检查项降为“只标记”，或修改提示词和示例。
3. 同一样本调用两次，结论不一致的判为 `unknown`。
4. 上线初期人工查看全部被淘汰的任务和 5% 被保留的任务，之后逐步降低抽检比例。
5. P1 中能程序化的部分（例如与资产库典型尺寸比较尺度）逐步改由程序检测，以降低成本。

## 十一、已确认事项与剩余问题

已确认（2026-10-07）：

1. 所有构造都围绕“底盘移动后是否更好”，用配对比较判定。
2. 任务构造分为不编辑场景和编辑场景两个分支，不编辑优先。
3. `same_edge` 单独保存为“同边平移类”。
4. 只使用纯场景，不使用 benchmark 的任务、起点或成功标签。
5. 正式运行用 train 集；初步调试用 val-103。
6. 构造阶段用 L1（规划级）判定，正式交付要求 L2（执行级）；L3 的执行次数和门槛留到接入真实执行时再定。
7. DROID 抓取文件不适用于 RBY-1 夹爪，也没有现成的 RBY-1 抓取生成工具或数据，新增模块 D 和里程碑 R1b。
8. Agent 插件先接入 ① 资产语义标注和 ③ 布局合理性复核；②、④、⑤ 在主链路跑通后做 A/B 对照。
9. 合理性复核按 10.5 节的方法判定。
10. v2、v2.5 文档标注“已被本提议取代”后保留原文。

剩余问题：

1. **金标准样本的人工标注**：③ 合理性复核上线前需要约 100–200 个人工标注的任务，① 的把手标注也需要人工抽查。由谁来标、何时开始？

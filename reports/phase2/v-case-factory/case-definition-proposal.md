# Case 描述具体化提议

更新：2026-10-07（第二版，已按确认意见调整）。**本文是提议，尚未修改代码、配置或已有结果。** 范围：case1、case1.5、case2、case3。

详见第八节。

## 摘要

- 现在的 case 描述只是抽象的文字。Agent1 规范化以后，`requirements` 和 `parameters` 仍然是空的，Agent3 只能自己编出世界坐标里的采样范围。运行模式是 `construction_only`，从不检查机制是否真的成立。按这条路线，最后得到符合要求的任务，可能性较低。
- 配置中的描述已经偏离了用户的原始定义：case1 从“距离超出臂展”变成了“不能仅把目标移远”，case3 从“抓取途中调整底盘”变成了“抓取前换方向”。后者现已被确认采用。
- 建议给每类 case 写一份**操作化定义**，写清七项：前提、判定量、成立条件、构造手段、程序筛选、反例、验证方式。判定方法统一用两个站位检查：**reach_ok（够不够得着）** 和 **plan_ok（能不能无碰撞地抓）**。
- 分工回到原方案第六节：程序生成候选、计算判定量，Agent 只在候选里做选择。
- 可行性估计：case1 高，case1.5 中高，case3 中，case2 中低（依赖把手标注和抓法校准）。建议按 case1 → case1.5 → case3 → case2 的顺序推进。

## 一、为什么要具体化

### 1.1 用户原始定义与当前配置不一致

| case | 用户原始定义 | 当前 `configs/case_edits/*.json` 中的 `case_description` | 差异 |
|---|---|---|---|
| case1 | 要抓的物体超出机械臂可达范围，比如机器人已经到了桌边仍抓不到，需要底盘移动过去 | 由几何布局导致工作位置不利，“不能仅把目标移得更远” | **方向相反**。原始定义的本质就是距离超出臂展 |
| case1.5 | 北面太窄无法到达，南面机械臂不可达，到西面操作成功率高 | A/B/C 三侧差异 | 基本一致，方向泛化了 |
| case2 | 把手朝向不对，必须抓把手而不是杯沿，需要底盘移动过去 | 当前管线没有这一类 | 未覆盖 |
| case3 | 抓取路径上会碰撞，需要越过杂乱桌面的物体，抓取途中调整底盘 | 抓取前改变操作方向，存在更有利的路径 | 已确认**先按抓取前换方向**处理 |

[原方案](../../数据采集管线方案与计划.md) 第 561 行写的也是“case1：目标与起点形成距离困难”。“不能只是移远”最早出现在 [修正计划](../../docs/case-to-edit-pipeline-plan.md) 中。

### 1.2 运行证据

- 三次真实运行的 `template.json`（[case1](../../outputs/case_construction/construct-29365f8d6330/template.json)、[case1.5](../../outputs/case_construction/construct-bc802bb13cdb/template.json)、[case3](../../outputs/case_construction/construct-b1bfbe3383e3/template.json)）中，`requirements` 都是 `[]`，`parameters` 都是 `{}`，硬约束只有 `supported_by(target, support)`。`semantic_checks` 是对原描述的改写，程序无法据此检查。
- DSL 谓词只有 `supported`、`supported_by`、`distance_xy`、`distance_3d`、`direction_angle`、`inside_region`（`construction/case_schema.py:10`）。“某一侧能不能站下底盘”“从某一侧够不够得着”“抓取通道有没有被占住”这三类量都无法表达。
- 已接受的 [case1 样本](case-edit-val103-case1-sample000000-walkthrough.md) 的实际编辑是把盐罐挪到锅铲后侧、再转一下方向。台面上的小物件不会改变底盘站位；“后侧受限”本来就是墙造成的。这个样本通过了构造检查，但**很可能并不符合用户原始的 case1**。
- [case1.5](case-edit-val103-case1-5-walkthrough.md) 中，Agent 想把深约 0.47 m 的椅子放进深 0.19 m 的区域，9 个候选全部被拒。原因是 Agent 不知道“A 侧要窄到放不下底盘”对应多大的空间。
- 反过来，早期的 [train_0 distance 样本](case-edit-train0-distance-sample000000-walkthrough.md) 把番茄与机器人的距离从 4.83 m 拉到 5.32 m。机器人站在几米外的空地上，往前走就能解决，这也不是 case1。

结论：问题出在输入缺少**可测量的成立条件**，而不在模型能力；换用更强的模型也无法补上这个缺口。

## 二、具体化原则

1. **每类 case 一份操作化定义**，固定写七项：前提、判定量、成立条件、构造手段、程序筛选、反例、验证方式。定义由人写，每类只写一次；不同场景只换绑定的对象，不重写定义。
2. **分开报告三层结论**，与现有边界保持一致：
   - 构造通过：编辑合法，几何上的代理量满足要求。
   - case 成立：在给定站位上，按 reach_ok / plan_ok 的规则检查成立。
   - 任务成功：真实执行，记录抓取结果。
3. **程序生成候选并计算判定量，Agent 只做选择。** Agent 不再编写世界坐标里的采样范围。
4. **方向使用支撑面的相对边。** “北/南/西”是指支撑面上的三条不同边，不绑定世界坐标的方位。
5. **阈值来自标定，不写死在提示词里。** 臂展、底盘尺寸、夹爪宽度从机器人模型标定后写入配置（当前 [rby1.json](../../configs/robots/rby1.json) 中还没有这些量）。

## 三、共用概念与判定量

| 概念 | 定义 | 实现来源 |
|---|---|---|
| 支撑面的边 `e` | 支撑面水平投影的各条边，以支撑面的局部坐标命名 | 新增；基于现有局部图包围盒 |
| 贴边站位集 `Stations(e)` | 在边 `e` 外侧地面带上采样底盘位姿，朝向目标，要求底盘与边的间距不超过 `edge_gap_max_m`；检查地面、碰撞和限位，标准与现有初态放置相同 | 复用 `stations/sampling.py` 和初态放置检查 |
| 可站立 `standable(e)` | `Stations(e)` 在采样预算内非空 | 同上 |
| **够得着 `reach_ok(s)`** | 在站位 `s`，**不考虑环境碰撞**，带躯干自由度的逆运动学对目标抓取位姿存在解 | 新增；可用 cuRobo 的 IK 求解 |
| **能抓 `plan_ok(s)`** | 在站位 `s`，**考虑完整碰撞世界**，固定底盘 cuRobo 能规划出接近、抓取、抬升、撤离的完整路线 | 复用 `planning/curobo.py`（固定底盘，单臂） |
| 抓取通道 `corridor(e)` | 从边 `e` 指向目标的带状空间：宽度为夹爪宽度加 `corridor_margin_m`，高度从支撑面到目标抬升高度 | 新增几何计算；可改造 `templates.py` 中 case3 的通道检查 |
| 地面带余量 `strip_clearance(e)` | 边 `e` 外侧地面带中，未被家具或物体占据的最大连续宽度和深度 | 改造 `templates.py` 中 case1.5 的 clearance 计算 |

**reach_ok 和 plan_ok 分开，是为了区分失败原因**：

| 情况 | reach_ok | plan_ok | 含义 | 对应 case |
|---|---|---|---|---|
| 距离超出可达范围 | false | false | 去掉所有障碍物也够不着 | case1、case1.5 的南侧 |
| 被障碍物挡住 | true | false | 本来够得着，但路线会碰撞 | case3 的起点 |
| 正常 | true | true | 可以抓 | 各 case 中“更好”的站位 |

两点限制：规划在有限预算内无解，不等于绝对做不到，所以统一记为“预算内无解”，并保存预算和种子；`plan_ok=true` 也不等于真实执行一定能抓起，后者属于“任务成功”这一层。

### 3.1 先决工作：RBY-1 可达范围标定

reach_ok 依赖可达范围。建议在规划机器上对 RBY-1 做一次离线标定：在不同底盘朝向、不同台面高度和躯干取值下采样抓取位姿，得到“台边到目标的最大水平距离”曲线。这条曲线用于两件事：

- 程序预筛：排除尺寸不可能成立的支撑面。
- 构造采样：给出目标应移动到的距离范围。

最终判定仍以逐站位的 reach_ok 为准，标定曲线只用于缩小候选范围。旧管线中的臂展比例没有考虑躯干和完整抓取姿态，不直接沿用（见 [lastmile case 构建方案](<../../../lastmile case 构建方案.md>) 4.3 节）。

## 四、四类 case 的操作化定义

> 四类 case 都是对“底盘移动后是否更好”的不同归因。每类都有两种来源：**不编辑场景**，只在原始站位图上选择起点 S0；**编辑场景**，按配方修改后再选 S0。下表中的“构造手段”指编辑分支；不编辑分支的流程、两个分支的路由和配对比较方法，见 [数据管线重构提议](pipeline-restructure-proposal.md) 第二至四节。

### case1：已经到了桌边仍够不着，需要底盘移动

| 项目 | 内容 |
|---|---|
| 前提 | 目标由支撑面承托；起点 S0 在支撑面某一边 `e0` 外贴边，并朝向目标，即“已经到了桌边” |
| 判定量 | `e0` 上**全部**贴边站位的 reach_ok；其他边贴边站位的 reach_ok 和 plan_ok |
| 成立条件 | ① `reach_ok(S0)=false`；② `e0` 的**整条边**上，所有合法贴边站位的 reach_ok 都为 false，即沿这条边怎么平移都够不着；③ 在**另一条边** `e1 ≠ e0` 上存在合法站位 S1，`plan_ok(S1)=true` |
| 构造手段 | 把目标沿台面移向远离 `e0` 的方向；或选择更深的支撑面。**这里的“移远”正是 case1 的机制**，但要远离的是整条边 `e0`，而不只是 S0 这一点 |
| 程序筛选 | 按标定曲线筛支撑面：目标到边 `e0` 的最短距离超过可达上限，并且到另一条可站立边的距离在可达范围以内。长台面上目标只是离 S0 远、离 `e0` 不远的情况要排除 |
| 反例 | 机器人在空地上，往前走就能够到（例如 train_0 番茄样本）；只是 S0 站得不够贴边；**沿同一条边平移就能抓到，不算 case1**；失败原因是碰撞而不是距离（这属于 case3） |
| Agent 选择 | 选哪个支撑面和目标；选 `e0` 与备选边 |

### case1.5：北窄、南够不着、西可抓

| 项目 | 内容 |
|---|---|
| 前提 | 支撑面至少有三条边外侧是地面，分别记为 A（北）、B（南）、C（西）；起点 S0 在 B 侧贴边 |
| 判定量 | 各边的 standable、strip_clearance、reach_ok、plan_ok |
| 成立条件 | **A**：`standable(A)=false`，且 `strip_clearance(A)` 大于 0、小于底盘尺寸，即“有缝但太窄”，与“紧贴墙、根本没有空间”区分开；**B**：`standable(B)=true`，B 侧贴边站位 reach_ok 全为 false，判定方法同 case1；**C**：`standable(C)=true`，并且存在 `plan_ok=true` 的站位 |
| 成功率高 | 构造阶段的代理量是 C 侧 `plan_ok=true` 的站位数和抓取数多于其他两侧；真实成功率在任务阶段做多次执行比较 |
| 构造手段 | 往 A 侧地面带放入落地物体，比如椅子、凳子、垃圾桶，把余量压到底盘尺寸以下；目标移向靠近 C、远离 B 的位置 |
| 程序筛选 | 程序先算出 A 侧地面带的尺寸，只给 Agent 提供**尺寸能放进去、又能把余量压到要求以下**的资产，避免再出现 0.47 m 椅子放进 0.19 m 区域 |
| 反例 | 只在台面上放小物件；A 侧本来就紧贴墙、没有缝；B 侧失败是因为碰撞而不是距离 |
| Agent 选择 | 支撑面和目标；三条边如何分配 A/B/C；用哪个落地物体 |

### case2：把手朝向不对，必须抓把手，需要底盘移动

| 项目 | 内容 |
|---|---|
| 前提 | 目标是**从 THOR 或 Objaverse 资产库检索出来、并已人工标注把手**的杯类资产（把手的 body 或 geom，以及局部方向轴）；抓取候选只取把手区域，抓杯沿、杯身的不算；“杯里有东西”只作为抓法限制，不需要真的放东西；带盖杯子同样适用 |
| 资产检索 | 来源：本地 THOR 库（Kitchen Objects 下有 Mug 3 个、Cup 30 个，Cup 是否带把手需逐个确认）和本地 Objaverse 子集（类别 mug 49 个；元数据还列出大量未下载资产，可以按需下载）。筛选条件：带把手，可选带盖；尺寸适合 RBY-1 夹爪；能在 MuJoCo 中加载，碰撞几何正常；把手最好是独立的 geom 或网格部件，否则需要人工框选。见 [资产统计报告](<../../../assets_objects_资产统计报告.md>) |
| 判定量 | 把手世界方向与“机器人→目标”方向的夹角 θ；只抓把手时，各站位的 reach_ok 和 plan_ok |
| 成立条件 | ① 在 S0，只抓把手时 plan_ok=false，θ 记录为证据；② 去掉“只抓把手”的限制后，S0 能抓杯身，证明困难来自朝向而不是距离；③ 另一站位 S1 只抓把手时 plan_ok=true |
| 构造手段 | 杯子绕竖直轴旋转，必要时配合小幅平移；复用 `templates.py` 中的 `verified_handle_world_direction` |
| 先决工作 | 接入 Objaverse 检索（当前管线只接入了 THOR 库，见[进度报告](case-edit-progress.md)“Objaverse/向量资产检索未接入”）；从检索结果中人工确认 2–3 个杯子的把手标注；单独校准把手抓法，杯身抓取的成功不能代替 |
| 反例 | 把手朝侧面，但从 S0 也能抓到把手；杯子本身就够不着（这属于 case1） |
| Agent 选择 | 用哪个已标注杯子；放在哪个支撑面；看图确认把手方向和遮挡 |

### case3：抓取路线被杂物挡住，抓取前换方向避开

| 项目 | 内容 |
|---|---|
| 前提 | 目标在支撑面上，S0 在边 `e0` 外贴边 |
| 判定量 | `corridor(e0)` 与其他边的通道被占据的情况；S0 和其他站位的 reach_ok、plan_ok；去掉通道内杂物后 S0 的 plan_ok |
| 成立条件 | ① `reach_ok(S0)=true`：本来够得着；② 带着杂物，`plan_ok(S0)=false`；③ 在构建会话中临时移除 `corridor(e0)` 内的杂物，`plan_ok(S0)=true`，证明是这些杂物造成了失败，事务回滚后不留痕迹；④ 存在另一站位 S1，带杂物时 `plan_ok(S1)=true` |
| 构造手段 | 把已有台面物体移进 `corridor(e0)`，或增加真实小物体资产；其他边的通道保持空 |
| 程序筛选 | 程序给出 `corridor(e0)` 的范围，并按高度过滤候选物体，太矮、伸手时不会碰到的不算；同时检查至少一条其他通道是空的 |
| 反例 | 杂物多但不在通道内；目标被四面封死，没有任何站位能抓；S0 本来就够不着（这属于 case1） |
| Agent 选择 | 挑哪些物体、放在通道内的什么位置；从图上判断布局是否像正常的杂乱桌面 |

> 条件 ③ 的对照只在构建会话中做，不涉及 `Simulation.begin()`，也不违反“开始后不恢复、不传送”的约束。

## 五、程序与 Agent 的分工

| 步骤 | 程序 | Agent |
|---|---|---|
| 解析 case | 加载对应的操作化定义（人写，固定） | Agent1 不再做开放式规范化，只确认 case 类型和任务类型 |
| 选上下文 | 枚举支撑面和边，计算尺寸，按标定曲线预筛，给出排序后的候选 | 从候选中选支撑面、目标和边的分配 |
| 选资产与位置 | 按地面带、通道尺寸过滤资产，生成参数化操作 | 从过滤后的资产和位置槽中选择 |
| 编辑与物理检查 | 维持现有事务、静置和规则检查 | — |
| 机制检查 | 采样站位，计算 reach_ok、plan_ok 和对照，按成立条件判定 | — |
| 视觉复核 | 生成配对图 | Agent4 判断布局是否自然、有没有明显错误，结论只作参考，不覆盖机制检查 |

## 六、对现有管线的改动建议（本文不实施）

1. **配置**：把三份 `case_description` 换成用户原始定义；新增字段 `case_definition`，指向操作化定义文件，例如 `configs/case_definitions/case1.json`。
2. **验证模式**：在 `construction_only` 之外，新增 `mechanism_check`，执行第三、四节的站位检查。不跑这一步的样本，最多只能标为“构造通过”。
3. **新增判定量**：`standable`、`strip_clearance`、`corridor`、`reach_ok`、`plan_ok` 放在 `validation/`；站位采样复用 `stations/`，规划复用 `planning/curobo.py`，编排放在 `workflows/`。遵守 AGENTS.md 的模块职责。
4. **提示词**：Agent2 和 Agent3 的输入从“抽象描述 + 局部图”改为“定义 + 程序候选列表”，输出从“采样范围”改为“候选编号 + 理由”。
5. **已有结果**：不修改、不重新标注。已接受的 case1 样本保持原状，在进度报告中补注“按新定义尚未做机制检查”。

## 七、可行性与推进顺序

| 顺序 | case | 可行性 | 主要依赖 |
|---|---|---|---|
| 1 | case1 | 高：成立条件只依赖 reach_ok 和一次换边 plan_ok；旧管线 `case1-cup-001` 有移动底盘后抓取 3 次试验 3 次成功、并经人工接受的先例，但它是否满足“整条边够不着、需要换边”还需按本定义复核 | 可达范围标定、按边采样贴边站位、reach_ok |
| 2 | case1.5 | 中高：在 case1 的基础上加地面带余量；旧管线已人工批准过北、南、西三面设定 | 落地资产尺寸过滤、strip_clearance |
| 3 | case3 | 中：需要带碰撞的完整规划和去掉杂物的对照 | plan_ok、corridor、对照事务 |
| 4 | case2 | 中低：取决于资产检索、人工标注和把手抓法校准 | THOR / Objaverse 杯类检索、把手标注、把手抓取候选 |

计算资源：标定、reach_ok 和 plan_ok 需要 GPU 上的 cuRobo，建议在 GPU 服务器上运行；定义文件、几何判定量和单元测试较轻，可以在 2080 上完成。

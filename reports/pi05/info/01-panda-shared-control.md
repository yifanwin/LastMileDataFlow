# cuRobo 与 π0.5 共用 Panda RoboCasa 控制层的链路评估

状态：draft  
日期：2026-10-18  
替代：无  
关联：[接入需求](../requirement/01-pi05-integration.md)、[profile 差异评估](../info/01-panda-robocasa-alignment.md)、[执行总结](../delivery/01-requirements-review.md)

## 结论：链路成立，先验证控制一致性与 cuRobo 的实际轨迹

**建议将这条链路作为 Panda 的统一目标，但尚不能直接替换当前 position 执行。** 两路上游分别产生同一 RoboCasa 12D 动作，下游共用动作解释、控制器状态、执行器配置、物理 stepping 和记录。

当前按用户提出的路线 B 细化：`cuRobo → FK → RoboCasa action` 与 `π0.5 → RoboCasa action` 进入同一个 controller。这里明确 FK 与反馈跟踪的边界；默认执行的切换仍待物理验证。

π0.5 到 RoboCasa 控制层的动作语义已有参考依据；主要工程不确定性在 cuRobo 一侧：其关节轨迹转换为末端动作后，OSC 不保证复现原关节姿态。任务空间跟踪、底盘协调与实际碰撞表现需要物理验证。

本轮完成源码核对、接口推导与少量代数示例，没有运行模型或机器人。下面的参数来自本地参考实现，不代表 checkpoint 对应版本已经确认。

## 1. 两条链路在未归一化的 RoboCasa 动作处汇合

| 环节 | cuRobo 示教链 | π0.5 推理链 | 共用内容 |
|---|---|---|---|
| 输入 | 当前真实状态、任务与规划场景 | 三相机、16D 状态、语言指令 | 同一 Panda 本体与观测定义 |
| 上游输出 | 关节/底盘参考轨迹 | 归一化动作块 | 上游保持各自职责 |
| 生成执行动作 | 参考轨迹 + 当前实测状态 + 控制目标 → 12D 动作 | 配套统计反归一化 → 12D 动作，依次取用动作块 | 相同动作字段、顺序与物理含义 |
| 动作处理 | 限幅、夹爪与 mode 映射 | 同样处理 | RoboCasa 动作解释与必要限制 |
| 控制 | 设置本周期目标，随后按低层时钟反馈控制 | 同样处理 | OSC、底盘、torso、夹爪及控制器状态 |
| 执行与记录 | 真实 stepping、任务判定、观测/动作记录 | 同样处理 | 既有 Simulation 与 AttemptRecorder 链路 |

“共用”不表示每个 tick 同时接收两路动作。按当前需求每次运行选择一个后端。此方案限于 Panda；RBY-1 可以共用 π0.5 推理核心和执行生命周期，但保留自己的本体动作约定。

### 路线 B 的具体方法：FK 提供参考，跟踪器生成动作

**FK 不直接产生 RoboCasa action。** 正向运动学将 cuRobo 的参考关节配置转换为末端参考位姿；跟踪器再利用当前状态与 controller 目标，将位姿参考转换为该周期的动作。简写链路中的 `FK → action` 包含这一步反馈求解。

| 输入来源 | 处理 | 输出 |
|---|---|---|
| cuRobo 同一参考点的臂关节、底盘与规划高度 | FK 与规划坐标系转换 | 末端、臂安装中心、底盘和高度参考 |
| 上述参考 + 实测状态 + controller 当前目标 | 按 mode 求末端增量，同步求底盘/torso 命令，附夹爪意图 | 本周期 RoboCasa 12D action |
| π0.5 预测 | 配套输出变换、反归一化、动作块取样 | 同一协议的 RoboCasa 12D action |
| 任一路的 action | 同一个 controller 设置目标、逐物理步反馈执行 | PandaOmron 实际运动与下一观测 |

具体执行顺序如下：

1. **构建同一 Panda RoboCasa profile。** 两路使用相同本体、相机、物理参数、controller 配置与初态规则。controller 留在仿真主进程，独立 π0.5 venv 只负责推理。
2. **cuRobo 规划关节与底盘轨迹。** FK 可提前批量计算参考位姿，随后由跟踪器按执行进度消费。夹爪和阶段意图来自示教流程，不能仅靠 FK 推出。
3. **每个动作周期重新生成 action。** 使用同一参考点的完整配置，再结合实测状态和 controller 目标求动作；反馈变化时动作随之变化。不能预先将整条轨迹固定转换成动作序列，再宣称闭环跟踪。
4. **π0.5 提供另一种动作来源。** 三相机、状态与语言经模型产生动作块，逐项送入同一 controller，不经过 FK 或 cuRobo 跟踪器。
5. **公共执行只解释 action。** 在动作边界更新一次目标，每个物理步更新实际控制。两路共用限幅、夹爪与 mode 映射，不按动作来源设置不同增益或姿态辅助。
6. **公共记录捕获真实执行。** 训练数据使用实际观测与实际下发 action；规划参考、预测请求和 ctrl 作为诊断保留，不将 FK 位姿直接当作训练动作。

FK 使用 cuRobo 运动学或独立的计算数据，不能为求 FK 临时改写正在执行的 `sim.data.qpos`。现有初态 FK 检查是起点，底盘/torso 变化和 controller TCP 固定变换也须核对。

实施只需明确现有 cuRobo 规划、Panda 参考轨迹到 action 跟踪、Panda RoboCasa controller 三个职责。跟踪逻辑与 controller 分离；FK 无需另起服务。

## 2. 共用控制层必须保留哪些语义

### 动作边界固定为 RoboCasa 12D，内部目标与实际 ctrl 分开

外部动作顺序沿用本地 openpi-robocasa：末端平移 3、末端旋转 3、夹爪 1、底盘 3、torso 1、mode 1。模型内部的 32D padding 在策略输出处理中移除，不传给本体控制。

控制层对两路动作实施同样的阈值和输入范围处理，再更新控制目标。OSC 产生的关节力矩、底盘速度 ctrl 和夹爪 ctrl 是下一层输出，不替代训练动作标签。

已有 `RobotCommand` 表示绝对位置目标，不适合强装这组动作。建议保留它服务原 position profile，在 Panda 的候选 RoboCasa profile 内增加明确的 12D 动作入口；无需创建通用动作插件框架。

### 目标只在动作边界更新，反馈控制在物理步更新

本地 `robosuite/robots/wheeled_robot.py` 的 `control()` 仅在 `policy_step=True` 时调用 `set_goal()`，随后每个物理步继续运行控制器。`environments/base.py` 也明确将后续物理步设为 `policy_step=False`。

建议保持这一结构：接收一次动作 → 设置一次目标 → 每个物理步读取反馈、更新力矩或速度控制、推进物理 → 记录实际结果。不能把增量动作在每个物理步重复累加，也不能像当前 position 路径一样将一次计算出的力矩保持整个动作周期。

同一 Simulation 中只有一份控制器目标状态。需要保留末端目标、mode、夹爪内部目标及底盘初始朝向等实际控制状态；快照复制遵守现有“执行前初始化，执行后不重置”的约束。每个独立 episode 初始化一次；同一 episode 从导航进入操作时保持连续，不重新初始化控制器来消除误差。

### 零动作不能统一解释为停车保持

在 `desired` mode 下，末端零增量保持上一目标；在 `achieved` mode 下，零增量将目标设为当前实测末端。夹爪经 Gym 映射后也有自己的开闭语义。

因此到站保持、闭爪保持和推理动作块结束不能统一发送全零向量。上游需要生成明确的保持动作：底盘速度为零、夹爪维持任务意图、末端按 mode 保持目标、torso 依据其控制约定保持高度。π0.5 正常预测的 mode 仍按参考协议执行，不由 cuRobo 的规则覆盖。

## 3. cuRobo 轨迹如何转换成 RoboCasa 动作

### 先保持原规划结果，再改变跟踪方式

本地 `V2Planner.points()` 已将 cuRobo 原生时间采样重定时到 `control_hz`；`PlanResult.positions` 没有独立时间戳。当前 `follow_points()` 可以反复追同一参考点，并用关节误差判断到达。

首版建议继续消费这批参考点，以既有动作周期推进参考；误差过大时保持参考点、继续反馈跟踪，并受既有 attempt 预算限制。这样无需先扩展轨迹数据格式，但执行耗时可能大于原规划时长，不能宣称严格复现其时间参数。

推进及末端到达应改用末端位姿、底盘和高度的实际误差，保留现有物理接触与任务判定；关节误差作为诊断。OSC 不追踪规划的 7D 关节姿态，不能继续要求每个关节到达原目标才结束。

### 末端增量必须反解实际控制器的目标更新

设参考位姿在臂控制器坐标系中为 `(p_ref, R_ref)`。`p_anchor, R_anchor` 按 mode 选取：`achieved` 取本周期实测值，`desired` 取控制器保留的上一目标。

对本地默认对称缩放，平移动作满足 `a_pos = (p_ref - p_anchor) / s_pos`；旋转动作满足 `a_rot = Log(R_ref × R_anchorᵀ) / s_rot`。其中 `Log` 将旋转矩阵转换成轴角向量；旋转乘法顺序来自本地 OSC 的左乘更新，不能用欧拉角直接相减。尺度必须读取实际 profile，不能写死为所有权重通用常数。

本地默认 OSC 的平移尺度为每轴 0.05 m、旋转尺度为每轴 0.5 rad，对应输入范围 `[-1, 1]`。需要超过范围时，上游分段或放慢参考推进，记录实际动作；不能裁剪后仍标记完整参考点已跟踪到达。

**代数示例，非 rollout 结果：** 实测位置 0.600 m、上一目标 0.610 m、参考位置 0.620 m，平移尺度 0.05 m。在 achieved mode 动作为 **0.4**，desired mode 为 **0.2**。将 0.4 错用于 desired mode 会把目标推到 0.630 m，偏离参考 **10 mm**。同样，desired mode 的 0.2 动作若重复设置五次目标，会累积 **50 mm**，而正确的一次更新为 **10 mm**。

cuRobo 侧可按已有导航/操作阶段显式选择 mode；同一轨迹段内不要随跟踪误差反复切换。动作转换读取控制器的实际目标，不在跟踪器中独立维护第二份末端目标。具体阶段选择在参考版本核对和物理对照后确定。

### 底盘、升降和机械臂必须使用同一个参考进度

参考轨迹中的关节角和底盘位姿共同决定世界末端目标。生成臂控制器相对目标时，应使用**同一参考点的参考 base/torso 姿态**消除基座运动，再按当前 mode 求增量；同时依据实际底盘反馈生成速度命令。

若把未来世界末端目标先相对当前未移动的底盘编码，然后再让底盘移动，同一底盘位移可能同时进入臂动作和底盘动作。最小例子是底盘前进 10 mm、臂关节保持：臂的基座相对目标应保持不变；不能再要求臂相对底盘额外前进 10 mm。实际控制器 origin 使用臂安装中心，需要连同 torso 和 TCP 偏置一起转换，不能用项目 pivot 粗略替代。

底盘控制建议使用参考速度与位置误差反馈生成所需速度，再逆向处理参考实现的轴、朝向和 ctrlrange 缩放。本地存在普通和 legacy 两种变换，必须按最终 profile 对应实现，不凭通用 `Rz(-yaw)` 公式替换。

本地 torso 配置未显式写 `input_type`，所调用的通用关节位置控制器默认为 delta，且从当前实测高度构造目标。因此当前候选中的保持动作需要按实际 profile 求 `a_h = (h_ref - h_measured) / s_h`，不能直接填高度或假定填零会回到上一高度目标。cuRobo 规划可以继续固定本段高度，π0.5 的 torso 通道则应完整执行。

### A* 导航也需适配同一控制层

当前 `navigate()` 发送绝对底盘目标并保持关节角；它不能原样用于候选速度底盘与 OSC。A* 路径仍可保留，但导航跟踪需生成同协议的底盘动作，并在基座参考系保持末端、torso 和夹爪意图。

保持末端不保证整条臂姿态不变，因此现有“保持姿态整机包络”的导航碰撞判断也需要用实际臂运动检查。先验证固定底盘操作，再验证移动协调，最后检查完整导航到操作链路。

## 4. π0.5 侧不经过 cuRobo 轨迹跟踪器

π0.5 侧按本地 RoboCasa 配套配置完成三图像处理、16D 观测、mean/std 归一化与 tokenization，输出反归一化后的动作块。每个动作由共用控制层执行一个动作周期；参考示例每块取前 5 步重观测，候选配置先沿用并明确记录。

模型子进程只负责推理，控制器与仿真留在项目主环境。首版同步推理即可：模型计算时仿真时钟不前进，实际墙钟耗时仍计入既有预算。无需引入异步控制线程、两个模型同时驻留或实时动作块修补机制。

不能用 cuRobo 的阶段逻辑重写 π0.5 的 mode、torso 或底盘输出来追求成功率。两路共用必要的动作范围和映射，保持各自上游决策可解释。

## 5. 共用公式仍不足以证明物理 profile 一致

| 当前项目中的差异 | 候选 RoboCasa profile 的处理 | 尚需确认 |
|---|---|---|
| Panda `prepare_spec()` 将臂改成位置伺服，将底盘改成位置执行器 | 从原 factory 配置构建独立 RoboCasa profile：臂/torso 由对应控制器输出，底盘保留对应速度执行器 | 实际力矩、速度与执行器限制 |
| 主动将底盘和 torso 的关节摩擦置零 | 按参考最终模型核对，不沿用 position 的清零逻辑 | 接触与静止响应 |
| Panda 当前使用 body gravcomp，OSC 又有偏置补偿 | 按参考组合配置重力与偏置补偿，避免重复补偿 | 静止姿态和力矩对照 |
| 项目 Panda 物理步长 4 ms，本地 robosuite 默认 2 ms | 建议候选先用参考的 2 ms、20 Hz 动作周期；主 stepping 按 profile 驱动 | checkpoint 的实际仿真参数及控制稳定性 |
| 旧快照已固化 actuator 与 timestep | 初始化前构建候选 profile 的新场景/快照 | 不在已开始 episode 中修改共享 MjModel |

2 ms 时每个 20 Hz 动作周期恰为 25 个物理步。若以后选择 4 ms，应记录为对照配置，并继续使用项目时钟余数机制保持平均频率；不能只因策略同为 20 Hz 就声称响应一致。此参数变化仅针对候选 Panda profile，不改变 MolmoBot 已有 100/20/4 ms 约定。

建议从参考实现移入必要控制逻辑并直接接入当前 `MjModel/MjData`，保留算法、配置与许可；不为此构造完整 Kitchen 环境、相邻仓库 Robot 生命周期或第二个仿真器。静态动力学数据与每步动态量要按原参考含义更新，不能将旧的 ctrl 数组当作控制器状态。

## 6. 最大限制是关节姿态与碰撞，不是动作维数

Panda 7 个臂关节对应 6D 末端任务存在冗余。原关节轨迹经 FK 转换后不再约束肘部姿态；本地 OSC 的零空间力矩跟踪初始化关节姿态，未跟踪 cuRobo 每个参考关节姿态。

因此不能直接继承 cuRobo 对原关节路径的碰撞判断。单靠实际接触后停止也无法证明原路径约束得到满足。代表性任务中应同时检查 TCP 跟踪与实际关节路径/障碍物间距，判断偏差是否影响原规划的可执行性。

首版建议保持参考 OSC 零空间逻辑。若验证发现它无法满足规划场景需求，再评估用规划关节姿态驱动零空间；一旦这样做，便引入 π0.5 原始动作中没有的外部姿态参考。不能只在 cuRobo 示教时偷偷增加该输入，再假定部署控制相同。届时需明确 π0.5 部署是否也可生成相同参考，或退回保留 position、使用匹配的新训练目标的方案。

现有 pregrasp 与 approach 阶段可能在执行前串联规划，实际关节偏离较大时，不能继续把下一阶段的计划起点当作真实状态。应依现有规划预算从实测状态重新连接或重规划；失败按真实结果报告，不重置或传送到计划点。

## 7. 微调数据记录实际下发动作，保留控制条件

训练样本使用同一时刻的三相机、16D 状态、指令与该状态下实际提交的 RoboCasa 12D 动作，下一状态来自真实 stepping。反归一化后、公共动作处理前的请求动作与实际提交动作分别保留；实际 ctrl 和原始关节状态继续由现有记录链保存。

模型的完整预测块是推理诊断，未执行的后续动作不作为执行样本。发生裁剪、部分周期终止或记录不完整时，按已有实际执行边界处理，不能将未执行命令扩成正常整周期标签。

共用执行协议只解决训练与部署解释动作的一致性。cuRobo 可能提供 π0.5 未见过的 mode 分布、接触策略或初始姿态，仍需用真实示教与微调结果评估。checkpoint 的统计与新数据的统计按训练方案选择，不因字段一致就视为同分布。

## 8. 最小改动范围与确认顺序

| 现有位置 | 候选改动 | 可保留部分 |
|---|---|---|
| `config.py`、`runtime/control/panda_omron.py` | 新增明确 Panda RoboCasa profile，按参考准备执行器、相机及控制状态 | 原 position profile 作为当前对照；本体资产与命名适配 |
| `runtime/simulation.py` | 目标设置与逐物理步控制更新分开，按 profile stepping | 单一生命周期、停止回调和记录回调 |
| `runtime/execution/context.py`、`navigation.py` | cuRobo/A* 参考到 RoboCasa 动作跟踪，修改对应到达判断 | 任务阶段、预算、规划入口与任务判定 |
| `policies/` 与 VLA rollout | π0.5 本地服务、Panda 观测和分块动作，按后端分派 | MolmoBot 服务与已有行为 |
| `data/recorder.py` 及导出 | 明确 16D 状态/12D 动作布局，适配实际 ctrl 更新的记录 | 一次真实执行记录，不另建平行轨迹链 |

先做以下少量验证，再确认是否迁移默认 profile：

1. **控制一致性**：同一本体、状态和动作下，对照参考实现的目标更新和 ctrl；核对关键旋转顺序、mode、torso、夹爪和 2 ms feedback。无需全任务才能发现接口错误。
2. **固定底盘操作**：一条既有 Cup pick 规划经候选链执行，与当前 position 结果对照 TCP、关节姿态、实际接触和任务结果。保留既有物理成功条件。
3. **移动协调**：一段已有底盘—臂联合轨迹与短导航，检查基座运动是否重复计入、末端是否跟随，以及实际整机碰撞表现。
4. **真权重推理与样本重放**：小规模 π0.5 zero-shot；从新记录取实际动作在对应初态重放，核对目标与可重复的执行表现，明确仿真条件与误差。控制层验证与任务成功分别给结论。

若控制一致但 cuRobo 经 OSC 跟踪持续破坏所需关节路径，则不确认“全部迁移”。可以先完成 Panda π0.5 的 RoboCasa profile，并将示教控制方案保留为待决项；不能为统一外观隐藏失败。若前述检查支持迁移，再同步新场景、标定、采集和运行说明，最后进入正式微调数据准备。

## 5. 单个资产的内部构成

以 `Kitchen Objects/Bowl/Prefabs/Bowl_1/` 为例：

```
Bowl_1/
├── Bowl_1.xml            6.4 KB   主模型
├── Bowl_1_prim.xml       6.4 KB   与主模型仅浮点尾数不同
├── Bowl_1_mesh.xml       18 KB    网格碰撞体版本
├── Bowl_1_old.xml        8.5 KB   旧版导出
└── Bowl_1_bowl_1/
    ├── Bowl_1_bowl_1_0.obj         视觉网格 0
    ├── Bowl_1_bowl_1_1.obj         视觉网格 1
    └── Bowl_1_bowl_1_0/…_collision_N.obj   凸分解碰撞块
```

Prefabs 层还并行放了一份**整模副本**：

```
Bowl_1.json   碰撞/关节元数据
Bowl_1.obj    合并后的整模
Bowl_1.mtl
```

也就是说，每个资产同时存在“整模 OBJ”和“分件 OBJ + MJCF”两套几何表达。加载走 MJCF，整模 OBJ 主要用于预览或外部工具。

### OBJ 文件角色分布（90,609 个）

| 角色 | 数量 | 说明 |
|---|---:|---|
| `*_collision_*.obj` | 78,305 | 凸分解碰撞块（含 RoboTHOR 环境构件的碰撞网格） |
| 视觉分件 | 10,341 | 被主 XML 的 `<mesh file=…>` 引用 |
| Prefab 层整模 | 1,694 | `<asset_id>.obj` |
| Master 整模 | 242 | `_Master_Prefabs/` 中的母版 |
| 原始环境构件（非碰撞） | 27 | RoboTHOR 场景搭建用的视觉网格 |

碰撞块数量远大于视觉分件，说明物理侧使用了较细的凸分解；单个 `_mesh.xml` 可引用数十个碰撞块（如 Dresser_205_1 有 78 个 `MeshCollider`）。

## 6. XML 变体对照

每个资产目录最多有 4 个 XML 变体。对 1,694 个资产逐一扫描：

| 变体 | 命名 | 数量 | 作用与差异 |
|---|---|---:|---|
| 主模型 | `<id>.xml` | 1,694 | 当前标准入口；`contype` 由 class 决定（动态/结构/视觉三套 default） |
| prim | `<id>_prim.xml` | 1,696 | 与主模型结构相同。855 个字节完全一致，839 个仅浮点舍入不同；仅 2 个存在结构差异（Doorway_1、Doorway_Double_4 的 prim 多 1 个 joint） |
| mesh | `<id>_mesh.xml` | 1,696 | 用 `<mesh>` 碰撞体替换 box 原语，引用 `_collision_N.obj` |
| old | `<id>_old.xml` | 1,359 | 旧版导出：`contype="1"`、显式 `specular/shininess/scale`、显式关节全参数；335 个资产没有此文件（另有 3 个 `_old_old` 重复文件） |

结论：**优先使用 `<id>.xml`**；`_prim` 可作为等价备份；`_mesh` 用于需要精确碰撞的场景；`_old` 仅作历史对照，不要依赖其存在性。

### 主模型与 mesh 变体的碰撞体差异（Bowl_1）

| 项目 | `<id>.xml` | `<id>_mesh.xml` |
|---|---|---|
| 视觉 geom | 2 个 mesh | 2 个 mesh |
| 碰撞 geom | 20 个 box 原语 | 50 个 mesh geom |
| 碰撞来源 | iTHOR 手工/自动原语 | 凸分解后的 collision obj |
| 优点 | 稳定、便宜 | 形状贴合 |
| 缺点 | 近似 | 网格多、求解慢 |

## 8. 元数据文件

### 8.1 每资产 `<asset_id>.json`（1,692 份）

位于 Prefab 目录下、与资产目录同级。这是 iTHOR/ProcTHOR 的 prefab 元数据，不是 molmo_spaces 文档中展示的“语义资产元数据”。

实测 schema 只有两个顶层键：

```json
{
  "bbox_center": {"position": "(0.00000, 0.04307, 0.00000)"},
  "meshes": [
    {
      "parentName": "Bowl_1_root",
      "meshName": "bowl_1",
      "parentRelativePosition": {"x": 0, "y": 0, "z": 0},
      "parentRelativeScale":    {"x": 1, "y": 1, "z": 1},
      "parentRelativeRotation": {"x": 0, "y": 0, "z": 0, "w": 1},
      "primitiveColliders": {"myPrimitiveColliders": [ … box + position + rotation … ]},
      "placeableZoneColliders": {"myPlaceableZones": [ … ]},
      "jointInfo": {"jointType": "none", "meshRelativePosition": {…}, "lowRange": {…}, "highRange": {…}}
    }
  ]
}
```

- 1,174 个资产含 1 个 mesh 条目，最多 25 个；
- `jointType` 取值不统一：`none` 2,208、`Rotate` 339、`slide` 397、`rotate` 101、`Slide` 25、`Scale` 2、非法值 `"3"` 1（共 3,073 个 mesh 条目）；
- `bbox_center.position` 是字符串 `"(x, y, z)"`，不是对象，解析时要注意；
- 缺失 2 份 JSON：`RoboTHOR_wall_panel_24`、`RoboTHOR_wall_panel_32_5`。

> 注意：文档中列出的 `category`、`description*`、`synset`、`mass`、`boundingBox` 等字段**在本目录内不存在**。若要使用 `ObjectMeta.annotation(uid)`，需确认 molmo_spaces 的 thor 分支从哪里补这些字段（很可能是场景元数据或另建的映射），不能直接读本目录的 JSON。

### 8.2 `asset_id_to_object_type.json`

- 1,653 条 `asset_id -> iTHOR object type`，覆盖 109 个类型；
- 与磁盘 1,694 个资产对比：
  - **41 个资产目录没有映射**：`Egg_Cracked_*` 30 个、`Cabinet_Corner_*` 2 个、`Cabinet_Straight_*` 4 个、`StoveKnob1/2/3` 3 个、`RoboTHOR_wall_panel_*` 2 个；
  - **映射中的 ID 全部能在磁盘上找到**（包含 `FramePrefabs/` 下的 20 个 `Doorframe_*`）；若只扫描 `Prefabs/`，会误判为 20 条悬空映射；
  - 339 条映射值与目录类型名不同，多数是别名/大小写差异（`ArmChair` vs `Armchair`、`Box` vs `Box_Full`、`Faucet` vs `BathroomSinkFaucet`），不一定是错误。
- `asset_id_to_object_type.json` 是历史生成物，**不能当作 UID 完整清单**；UID 清单应以磁盘上的 `<Prefabs|Prefab|FramePrefabs>/<id>/<id>.xml` 为准。

### 8.3 材质相关

- `material-database.json`：按对象类型列出允许的材质名（如 `Doorway` 下 20+ 种塑料/橡胶材质）；
- `material_to_textures.json`：材质名 -> Unity 风格贴图槽与 PBR 参数（`_MainTex`、`_BumpMap`、`metallic`、`smoothness`、`albedo_rgba`）；
- 这两份是 iTHOR 原始材质体系的映射表，MuJoCo XML 已经把它们烘焙成 `<material>`/`<texture>`，正常加载不需要再读。

## 10. 与 molmo_spaces 资产体系的关系

结合项目文档（Objects / Asset libraries）与本目录实测：

1. **UID 就是目录名**。`Bowl_1` 既是 `asset_id`，也是 MuJoCo body 名、目录名和 XML 文件名。
2. **定位入口**：`locate_uid_package(uid)` 预期返回 `<...>/<Category>/<Type>/<Prefabs|Prefab|FramePrefabs>/<uid>/<uid>.xml`。本目录中每个 UID 都能找到该路径；门框例外，位于 `FramePrefabs/`。
3. **`install_uid(uid)`** 会检查归档/下载状态；本目录已经完整解压，因此应直接命中本地文件，不触发下载。
4. **场景元数据桥接**：`scene_metadata["objects"][body_name]["asset_id"]` 指向这里的 UID。资产本身不含场景信息。
5. **抓取库**：`assets/grasps/droid/20251116` 已就位；`load_pickup_grasps(asset_id, …)` 按 UID 取抓取，不依赖本目录内容。
6. **语义元数据缺口**：本目录只有几何 + 碰撞 + 关节 + iTHOR 类型映射。`ObjectMeta.annotation()` 所需的描述、同义词、质量等字段需要另找来源；`objathor_metadata` LMDB 当前未安装。
7. **许可策略**：文档中的 license policy 主要针对 Objaverse UID；thor 是手工资产，不受该策略影响。

## 11. 使用建议

1. **入口固定用 `<id>.xml`**，不要依赖 `_old` 的存在性，也不要在主/prim 之间来回切换。
2. **区分三类资产**：1,172 个自由刚体（适合抓取）、361 个带关节资产（适合开门/抽屉任务）、161 个静态构件（只做场景碰撞）。
3. **注意根固定资产**：181 个带铰链/滑轨的资产没有 free joint，加载后不能整体移动，适合固定在家具位置。
4. **碰撞精度开关**：需要精确接触时换用 `_mesh.xml`，但几何体会从 box 原语变成几十个 mesh，求解成本明显上升。
5. **纹理去重**可回收约 0.5 GB，且不影响加载（共享 `Textures/` 已覆盖全部 229 个纹理名）。
6. **不要用 `asset_id_to_object_type.json` 做完整性校验**，用磁盘扫描结果；如需类别标签，可基于该表 + 规则补齐 41 个缺失项。
7. **RoboTHOR 子树按需启用**：128 个资产可以正常加载，但原始环境构件（outer_boundary、ceiling_vent、ShelvingUnit 等）不是标准资产，建议排除在 UID 清单之外。
